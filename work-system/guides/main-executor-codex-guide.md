# main / executor / Codex 协作操作指南（最小可执行版）

## 目的

这份指南用于约定当前阶段 `main`、`executor` 与 `Codex` 的最小协作方式，优先保证专项能够顺畅推进，而不是追求一次性设计出完整架构。

当前目标：
- 让 `main` 保持专项主控与日常协作能力
- 让 `executor` 承接需要 `Codex` 深度参与的专项执行任务
- 让有价值结果稳定回写到共享 workspace，避免人工搬运和信息散失

## 基本原则

1. `main` 负责专项主控，不负责长时间阻塞等待 `Codex`
2. 进入 `Codex` 深执行阶段的任务，切到 `executor` 处理
3. `main` 与 `executor` 共享 workspace，因此有价值结果直接写回专项文件
4. `Codex` 是代码/设计执行能力，不承担专项 owner 角色
5. 当前阶段先采用可运行的工作法，后续再决定是否升级为 SOP 或 skill

## 角色分工

### main

负责：
- 与用户持续对话
- 澄清目标、边界、成功标准、衡量口径
- 判断当前任务是否需要进入 `Codex` 深执行
- 对 `executor` 回写的结果做专项级收口
- 继续推进复盘、反哺、任务优先级与下一步判断

不负责：
- 长时间盯住 `Codex` 执行过程
- 承担需要持续读代码、改代码、追执行状态的任务

### executor

负责：
- 承接需要 `Codex` 深度参与的专项执行任务
- 直接调用 `Codex`
- 推动代码分析、方案形成、详细设计、实现、验证等执行工作
- 将有价值结果写回共享 workspace 的专项文件
- 将阶段性结论回交给 `main`

不负责：
- 独立决定专项目标和成功标准
- 取代 `main` 做整体专项 owner

### Codex

负责：
- 在目标项目目录中执行代码分析、设计、实现、验证
- 作为专项执行能力参与任务推进

不负责：
- 维护专项级长期上下文
- 承担专项总控和最终业务判断

## 什么时候留在 main

以下情况优先留在 `main`：
- 讨论专项目标
- 澄清背景、边界、约束
- 判断成功标准和衡量口径
- 讨论是否立项、是否继续、是否转向
- 对执行结果做专项视角收口
- 产出复盘结论、反哺项、后续推进建议

## 什么时候切到 executor

以下情况切到 `executor`：
- 需要读项目代码并定位入口
- 需要做详细技术分析
- 需要通过代码分析形成优化方案、隔离方案或改造建议
- 需要让 `Codex` 连续推进设计或实现
- 需要进行多轮代码修改与验证
- 需要在项目目录中持续工作，而不希望阻塞 `main`

简单判断规则：

> 一旦任务开始明显进入“读代码 / 改代码 / 连续执行”的节奏，就切到 `executor`。

## executor 调用 Codex 的方式

当前阶段：
- `executor` 直接通过 `acp` 对接 `Codex`
- 不额外再套抽象执行层
- 不要求 `main` 在主会话里同步等待整个执行过程

原则：
- `executor` 负责判断是否已进入深执行区，并决定何时触发 `acp -> Codex`
- `main` 只关心阶段性结果和专项价值

## executor 何时应触发 acp -> Codex

进入 `executor` 后，满足以下任意两条，默认应触发 `acp -> Codex`：
- 需要连续读取多文件代码上下文
- 需要跨模块定位调用链、依赖关系或关键入口
- 需要基于代码证据形成优化方案、隔离方案、改造建议或实施判断
- 需要真实执行命令、修改代码、验证行为或检查运行结果
- 预计本轮不会在一两次短分析内结束，而是会进入持续推进节奏

以下情况可先不触发 `Codex`：
- 只是整理已有结论
- 只是把已有结果改写成便于 `main` 回收的反馈
- 只是做是否值得继续的浅层初筛

一句话规则：
> `main` 决定要不要切到 `executor`；`executor` 决定要不要继续触发 `acp -> Codex`。

## 什么结果必须写回共享 workspace

只要符合以下任一条件，就必须写回专项文件：
- 已形成阶段性技术判断
- 已找到关键代码路径
- 已形成修复方案或设计草案
- 已完成重要代码改动
- 已得到值得后续复用的经验或反哺项
- 已暴露出影响专项推进的关键风险

不要求把所有过程聊天都写回。

要求回写的是：
- 有价值的判断
- 有复用价值的结论
- 对后续推进有直接帮助的信息

当前阶段优先采用“共享区回写”机制：
- `executor` 不必每轮都单独给 `main` 发一条消息
- 但只要已有阶段性成果或专项进展，就应明确触发一次正式回写
- 当前约定的自然触发词包括：`更新专项进度`、`回写专项进展`、`记录阶段性成果`、`补充执行结论`、`同步这轮结果`
- 一旦出现这些表达，默认按“需要正式回写共享区”处理

## 回写内容的最小结构

`executor` 回写专项时，至少包含：
- 本轮任务目标
- 核心发现
- 关键代码路径或实施位置
- 产出结果（分析 / 设计 / 改动 / 验证）
- 风险与不确定点
- 建议下一步

## 项目档案回写失败时怎么办

如果项目档案无法稳定更新（例如 edit 匹配失败、文件内容脏、编码异常），不要反复卡在项目档案重试上。

当前默认降级顺序：
1. 先确认 `Codex` 的阶段性成果已落地
2. 立即补写 deliverable 或执行反馈文件
3. 用 `更新专项进度`、`记录阶段性成果` 等收口信号标明本轮已收口
4. 项目档案回写交由后续 `main` 接管

优先级永远是：
- 先保住成果
- 再做完美回写

## main 如何继续收口

当 `executor` 已回写专项文件后，`main` 负责：
- 将执行结果翻译成专项推进语言
- 判断是否进入下一阶段
- 判断是否需要补材料
- 判断是否需要扩大范围或止损
- 将复盘与反哺内容继续沉淀

## 当前阶段不追求的事情

以下内容当前不作为第一优先：
- `main` 主会话里自动无感接收所有 `Codex` 结果
- 一次性设计完整多层执行架构
- 把还没稳定的流程立即封装成 `skill`

当前阶段优先级：
1. 工作法能跑通
2. 专项能推进
3. 结果能沉淀
4. 再考虑自动化与产品化

## 中江任务作为首个样例

当前首个样例任务：
- `中江病区护士站节点 down 事件：慢接口与三方服务隔离优化`

建议执行方式：
1. `main` 负责定义子任务、目标、成功标准、复盘视角
2. 切到 `executor` 承接 `Codex` 深执行
3. `executor` 将关键分析、修复方案、后续建议写回共享 workspace
4. `main` 再基于专项文件做收口、反哺和后续安排

## 后续升级路径

如果这套工作法连续跑顺：
- 先升级成正式 `SOP`
- 再视复用稳定度决定是否封装成 `skill`

在此之前，以“可执行、可复用、可沉淀”为主，不追求过早抽象。
