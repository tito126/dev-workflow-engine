# SPD 对接插件化试点

## 背景
本次会议围绕 SPD 现有对接模式的复杂性展开。当前系统对接多家厂商的方式较为混乱，随着厂商数量增加，维护成本和复杂度显著上升。已有对接方式同时存在直接调用、混合框架对接等多种分支，整体缺乏统一抽象，不利于后续扩展、维护与问题排查。

会议中重点讨论了参考 `Groovy` 插件化方案，尝试把通用业务逻辑与各厂商特定协议解耦，通过接口代理与插件机制形成更标准化、可扩展的 SPD 对接模式。

## 目标
验证 `Groovy` 插件化方案是否能够作为未来简化 SPD 对接的新方向，形成一个可试点、可评估、可后续推广的技术路径。

## 要解决的问题
- 现有 SPD 多厂商对接方式分支过多，维护成本高
- 厂商继续增加后，复杂度会进一步放大
- 现有模式缺少统一的标准化接口层，难以管理和复用
- 面向不同医院、同一厂商的差异化业务流程，当前难以优雅承接
- 方案如果过度依赖代码与配置，对非开发角色不友好，排查与理解门槛高

## 价值
- 通过统一接口与插件化扩展方式，降低后续 SPD 对接与维护复杂度
- 为不同医院、不同厂商差异化流程提供更清晰的承接机制
- 提升后续扩展性，减少随着厂商数量增加而带来的失控风险
- 若试点成功，可为后续 SPD 相关专项提供一条更可复用的技术路线

## 当前进度
当前已从“方向提出”推进到“方案基本确立 + 标准接口与关键业务逻辑收敛”的阶段。最近一轮会议已进一步明确：新方案正式采用基于现有 `groovy` 能力的插件式适配路线，以标准化插件接口承接不同厂商差异，目标是提升复用性、降低耦合，并减少新医院上线和后续维护复杂度。配置策略上，已从“是否做复杂配置”收敛为“仅保留与业务流程直接相关的关键配置”，避免把复杂度重新转移到配置层。业务逻辑上，已明确高值耗材扫码查询、低值耗材计费核销、物资模式 / 收费项目模式切换、异步核销兼容旧逻辑等关键处理口径；验证路径上，已选定“快享”作为首个验证对象，计划先完整打通库存查询、库房信息获取等核心接口，再评估是否纳入配置中心并作为后续新厂商接入标准路径。下一步重点，已从“方向是否可行”进一步转向“标准接口最小集合如何落地、配置中心如何承接、验证对象如何跑通、以及下轮评审前如何把方案细节收口”。

## 会议结论（2026-03-24）

### 1. 对现有模式的判断
- 现有 SPD 对接模式已经显著复杂化
- 对接厂商越多，后续维护和统一管理难度越高
- 继续沿现有方式堆叠，长期风险较高

### 2. 对 `Groovy` 插件化方案的初步判断
- 核心思想可行：通过接口代理与插件化，将通用逻辑和厂商特定协议解耦
- 支持按医院启用不同插件版本，具备一定灵活适配能力
- 理论上支持不同医院对同一厂商采用不同业务流程（如同步/异步核销）
- 支持热部署，修改配置后无需重新编译部署

### 3. 当前主要顾虑
- 配置逻辑高度依赖代码
- 对产品、实施等非开发角色不够友好
- 缺少直观可视化配置界面，后续理解与排查门槛较高

### 4. 当前推进策略
- 暂不直接大范围推广
- 先打通整体技术流程
- 先在一个新医院试点验证
- 试点验证通过后，再讨论是否推广

- [ ] 选定一个新医院作为试点环境

## 风险与待确认
- 风险: 统一接口虽然能显著降低前端复杂度，但若“高值 / 低值耗材识别”和“库存校验触发时机”在接口契约里定义不清，后续仍可能在前后端各自长出口径分叉
- 风险: 如果“提醒式 / 阻断式”库存校验只停留在业务描述层、没有固化为标准配置参数和明确返回协议，不同医院后续仍可能要求定制分支
- 风险: 虽然插件式路线已基本确立，但若标准接口粒度定义不稳，后续仍可能在插件内部重新长出厂商差异分支，影响复用性
- 风险: 新配置模式虽然已明确要“做轻”，但如果关键业务配置与技术配置边界划分不清，实施阶段仍可能出现理解和落地偏差
- 风险: 异步核销场景当前选择兼容旧逻辑，如果 SPD 接口 / HIS 网关切换策略、回退方式和状态追踪不清，后续容易出现问题定位困难
- 风险: 若“物资模式优先、收费项目模式兜底”的业务规则没有在接口和配置中彻底固化，后续不同医院实现口径仍可能分叉
- 风险: 首个验证对象若只打通接口、不验证真实业务链路闭环，后续推广价值会不足
- 待确认: 标准接口最小集合最终包含哪些能力，以及哪些属于首轮验证必须打通范围
- 待确认: 前端在判断低值耗材时，最终以“未采”还是“价值分类”作为主判断依据，还是采用多字段组合口径
- 待确认: `is_high_value` 字段的最终语义边界、默认值和兼容策略如何定义，才能覆盖现有主流厂商场景
- 待确认: 低值耗材在“全部”列表模糊搜索场景下不查库存、仅在点击记账时触发库存校验，这一规则是否存在医院例外
- 待确认: 高值耗材扫码查询、低值耗材计费核销等前后端交互口径，是否还存在特殊厂商例外
- 待确认: `substance_id` 缺失时切换到“收费项目模式”的规则，应由业务配置控制到什么粒度
- 待确认: 异步核销场景下，调用 SPD 接口还是 HIS 网关的配置维度、优先级和兼容策略如何定义
- 待确认: “快享”作为首个验证对象时，需要覆盖哪些核心接口和最小可验业务链路
- 待确认: 配置中心后续承接的是“业务可配”还是“技术可配 + 业务可配”的混合模式
- 待确认: 下轮方案评审会前，需要输出到什么粒度，才能支持继续拍板
