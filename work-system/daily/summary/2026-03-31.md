## Key Conclusions From Today
- 当前问题更像“慢外部依赖拖住请求线程 / 连接池”的级联问题，而不是本地 CPU 逻辑瓶颈。
- `BannerInfoService` 里 3 段远程调用当前是串行执行的，其中第二段“病案费用汇总”和第三段“中医补充明细”天然更适合视为增强依赖并优先做异步 fail-open。
- 如果中江当前实际走的是 `HTTP` 分支，则这条链路风险最高，因为它额外叠加了药占比、欠费额度、床位、住院次数、MDM 转码和配置查询等附加成本。
- 当前最值钱的小改动已经收口为：
  - `P0`：第二段 / 第三段异步并行 + fail-open
  - `P0`：`(hospitalSOID, transCode)` 集成方式查询加 5~10 分钟缓存
  - `P1`：跳过 HTTP 分支中当前接口未消费的药占比等附加查询
  - `P2`：统一熔断 / 超时 / 线程隔离治理
- SPD 这轮新增的关键结论是：统一接口方案应继续坚持“前端简单、后端承接差异”的方向，高值 / 低值耗材扫码优先通过统一接口承接，由后端用 `is_high_value` 判断类型并触发相应库存校验；`source_type` 配置倾向移除，业务模式判断更多下沉到后端；低值库存校验最终不走每院单独插拔逻辑，而是走“提醒 / 阻断”标准配置参数。
