# 护士站专项开发框架：流程图与模板清单 v1

## 1. 文档目的

本文档用于将《护士站专项开发框架蓝图 v1》进一步落到流程和模板层，回答两个问题：

1. 框架实际如何运转
2. 后续需要沉淀哪些模板与标准件

---

## 2. 总体流程图（文字版）

```text
需求/问题输入
    ↓
主控判断（是否进入专项开发流程）
    ↓
需求澄清与目标收口
    ↓
影响分析 / 风险识别 / 方案设计
    ↓
任务拆解与执行计划
    ↓
[检查点A：是否满足进入执行条件]
    ↓
调用执行引擎（exec -> OpenCode / Codex）
    ↓
代码实现 / 问题修复 / 补测试 / 结果整理
    ↓
结果回收
    ↓
代码审查 / 验证 / 回归检查
    ↓
[检查点B：是否达到交付标准]
    ↓
输出成果 / 回写专项资料 / 沉淀复用资产
    ↓
复盘与经验抽取
```

---

## 3. 分阶段说明

## 3.1 阶段一：需求准入

### 目标

判断当前事项是否进入正式专项开发流程，而不是直接开始编码。

### 输入

- 新需求
- 线上问题
- 性能问题
- 隔离优化任务
- 既有功能扩展诉求

### 输出

- 任务类型判断
- 是否进入正式流程
- 是否仅分析、不执行

### 关键问题

1. 这是稳定性问题、功能扩展、债务治理还是探索性事项？
2. 目标是否明确？
3. 成功标准是否明确？
4. 当前是否值得进入执行？

---

## 3.2 阶段二：需求澄清与设计

### 目标

在写代码前，把“做什么、为什么做、影响什么、怎么验证”先说清楚。

### 输出

- 目标说明
- 范围说明
- 风险点
- 方案草案
- 验收标准

### 可复用 skill 方向

- `brainstorming`
- `writing-plans`
- `systematic-debugging`

---

## 3.3 阶段三：任务拆解与执行计划

### 目标

将事项拆成结构化任务，明确每一步的执行对象和检查点。

### 输出

- 任务列表
- 执行顺序
- 是否需要多 Agent 协作
- 哪一步调用执行引擎
- 哪一步先人工确认

### 关键要求

每个任务都应尽量明确：

1. 目标模块
2. 预期改动
3. 风险点
4. 验证方式
5. 输出物

---

## 3.4 阶段四：执行触发

### 目标

将结构化任务交给执行型 Agent 承担。

### 当前建议驱动方式

`OpenClaw -> exec -> OpenCode / Codex`

### 当前建议原则

1. 没有明确计划，不进入执行
2. 没有明确目标文件/模块，不进入执行
3. 没有明确验收标准，不进入执行
4. 大任务优先拆小，再进入执行

### 说明

这一阶段才是“真正写代码”的开始。

---

## 3.5 阶段五：结果回收与验证

### 目标

避免 agent 宣称“完成”就被当作完成。

### 输出

- 变更摘要
- 风险说明
- 测试结果
- 回归检查结论
- 是否允许进入交付

### 可复用 skill 方向

- `requesting-code-review`
- `verification-before-completion`
- `test-driven-development`

---

## 3.6 阶段六：沉淀与复盘

### 目标

把单次开发变成长期可复用资产。

### 输出

- 专项结果文档
- 问题根因剧本
- 代码改造范式
- 模板补充
- 复盘结论

### 关键问题

1. 这次为什么有效？
2. 哪些做法值得复用？
3. 哪些问题下次要提前规避？
4. 是否真的对稳定性和效率有正向贡献？

---

## 4. 多 Agent 协作流程（建议版）

```text
主控 Agent
  ├─ 收口目标
  ├─ 判断是否进入执行
  ├─ 分派任务
  └─ 汇总结果

分析 Agent
  ├─ 代码定位
  ├─ 调用链梳理
  ├─ 影响分析
  └─ 风险提示

实现 Agent
  ├─ 修改代码
  ├─ 补测试
  ├─ 执行局部验证
  └─ 输出变更说明

审查 Agent
  ├─ 检查是否符合计划
  ├─ 检查实现质量
  ├─ 标记遗漏/风险
  └─ 决定是否回退修改建议

验证 Agent（可选）
  ├─ 运行验证步骤
  ├─ 回归关键链路
  └─ 给出交付建议
```

当前阶段建议优先采用：

```text
主控 Agent -> 执行 Agent -> 审查/验证 -> 回写
```

先跑通最小闭环，再逐步增加角色复杂度。

## 5. 模板清单（建议优先建设）

## 5.1 需求与设计模板

### 1. 需求准入模板

建议字段：

- 事项名称
- 来源
- 任务类型（稳定性/扩展/修复/治理/探索）
- 背景问题
- 目标
- 成功标准
- 是否进入执行

### 2. 需求澄清模板

建议字段：

- 本次要解决什么
- 不解决什么
- 涉及哪些模块
- 风险点有哪些
- 依赖条件有哪些
- 如何判断完成

### 3. 影响分析模板

建议字段：

- 前端页面影响
- 后端接口影响
- 数据库/缓存影响
- 日志/监控影响
- 配置/权限影响
- 回归范围

### 4. 方案设计模板

建议字段：

- 方案概述
- 替代方案
- 为什么选当前方案
- 风险与权衡
- 实施建议

---

## 5.2 执行模板

### 5. 执行计划模板

建议字段：

- 任务拆解
- 执行顺序
- 每步责任 Agent
- 输入输出
- 验证方式
- 检查点

### 6. 执行提示词模板

建议字段：

- 目标
- 范围
- 限制条件
- 目标文件/模块
- 修改原则
- 验证要求
- 输出格式

### 7. 执行结果回收模板

建议字段：

- 改了什么
- 没改什么
- 风险点
- 测试情况
- 需要人工确认的点

---

## 5.3 质量控制模板

### 8. 代码 review 检查单

建议关注：

- 是否符合需求目标
- 是否改动过度
- 是否引入额外复杂度
- 是否补了必要测试
- 是否保留了可观测性
- 是否有潜在回归风险

### 9. 验证检查单

建议关注：

- 需求目标是否满足
- 关键路径是否回归通过
- 边界场景是否确认
- 日志是否足够定位问题
- 性能/稳定性是否受影响

---

## 5.4 沉淀模板

### 10. 专项复盘模板

建议字段：

- 背景
- 目标
- 实际执行过程
- 成功点
- 失败点
- 经验教训
- 可复用结论

### 11. 根因剧本模板

适用于：

- 高频 bug
- 典型故障
- 性能问题
- 反复出现的现场问题

### 12. 改造范式模板

适用于沉淀：

- 某类接口优化范式
- 某类前后端联动改造范式
- 某类日志增强范式
- 某类隔离治理范式

---

## 6. 后续 skill 建设建议

在模板逐步稳定后，可继续往本地 skill 演进，优先考虑：

1. 护士站需求澄清 skill
2. 护士站影响分析 skill
3. 护士站执行计划 skill
4. 护士站 review / 验证 skill
5. 稳定性专项复盘 skill

这类 skill 不必一开始就自动化很强，先保证模板与方法论稳定。

---

## 7. 当前落地建议

建议按以下顺序推进：

1. 先固化蓝图
2. 再补对比文档
3. 再补流程图与模板清单
4. 选一个真实需求跑 MVP
5. 根据实际执行结果，反向修正文档与模板
6. 再决定是否安装和深度接入外部 skill 框架

---

## 8. 当前结论

对于护士站专项开发框架来说，流程和模板不是辅助材料，而是框架真正落地的起点。

如果没有流程图和模板，Agent 只是“能干活”；
如果有了流程图和模板，再加上执行引擎和回写机制，才开始形成真正可复用、可协作、可持续优化的开发框架。
