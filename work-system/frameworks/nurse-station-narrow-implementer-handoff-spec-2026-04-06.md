# 护士站实现任务超窄 handoff 规范（2026-04-06）

## 1. 文档目的

本文档用于定义护士站专项开发框架中，Controller 向 Implementer 下发任务时，什么叫“超窄 handoff”，为什么必须这样做，以及如何判断一个实现任务是否已经窄到足够安全。

本规范用于解决当前已暴露的问题：

- implementer 任务一次给得太大
- 执行链自己扩散理解和改动面
- 多文件、多责任任务在一次实现中混成一团
- 主控与 review 来不及在中间及时拦截

---

## 2. 一句话定义

**超窄 handoff** 指的是：

> Controller 给 Implementer 下发的任务，必须小到足以在一次实现中保持边界稳定、改动面清晰、review 可以及时接手，而不是要求执行链自己再做大量边界判断。

换句话说：

- 实现者负责执行
- 不负责继续拆分大任务
- 不负责自己决定是否顺手把别的文件一起做了

---

## 3. 为什么必须超窄

## 3.1 当前真实问题已经证明

在 `1543024` 这次真实链路中，一次 handoff 同时要求实现链去做：

1. 主搜索区前移
2. 参数映射保持
3. 仅已出院显示
4. 更多搜索去重

表面看是同一需求，实际上已经同时包含：

- 主搜索区 UI 改动
- 弹层条件逻辑改动
- 场景控制
- 参数链路保持

这对当前执行链来说过大，结果是：

- `homeHeader.vue` 方向部分找对
- `searchComp.vue` 明显发散
- 结构被污染
- 实现必须中止

所以这不是抽象规范，而是被真实失败验证过的必要约束。

---

## 4. 什么叫“足够窄”

一个 implementer 任务，至少应满足以下条件中的大多数：

1. 主要只解决一个明确子目标
2. 改动文件数很少，优先 `1` 个，最多 `1~2` 个高度耦合文件
3. 场景边界清楚，不需要执行者再自己解释需求
4. 验证点清楚，可以在当前子任务后立刻 review
5. 失败后容易回滚和收口，不会把多个维度一起污染

如果一个任务做不到这些，就不应该直接交给 implementer 一次完成。

---

## 5. 超窄 handoff 的判断标准

## 5.1 推荐标准

优先满足：

- **一个子任务 = 一个主目标**
- **一个主目标 = 一个主要文件改动面**

## 5.2 可接受范围

### 最优
- 只改 `1` 个文件
- 或 `1` 个主文件 + `1` 个极强耦合的小配套文件

### 谨慎可接受
- `2` 个文件，但职责边界必须非常清楚
- 且两个文件必须服务同一个子目标，而不是两个不同子目标

### 默认不接受
- 同时改 UI 主区域 + 弹层逻辑 + 参数转换 + 多处配置
- 同时解决展示、去重、验证、收尾
- 实现者需要自己判断“顺手一起做掉是不是更方便”

---

## 6. 必须拆任务的场景

出现以下任一情况时，必须拆成多个 implementer task：

1. **涉及两个以上不同职责文件**
   - 例如：页面主结构文件 + 弹层组件文件 + request 参数文件

2. **同一需求包含多个不同子目标**
   - 例如：前移展示 + 去重 + 参数改造

3. **一个改动需要先验证结构，再继续第二步**
   - 例如：先确认 UI 插入点，再处理重复展示

4. **任何一个子步骤失败都会污染后续判断**
   - 例如：如果第一步插入点都没做稳，第二步去重就失去判断基准

5. **review 无法在中间阶段明确给出通过/不通过**
   - 这种情况说明 handoff 还是太大

---

## 7. `1543024` 的正确拆法示例

围绕 `1543024`，推荐拆成：

### Task A
只处理 `homeHeader.vue`

目标：
- 把时间区间组合条件前移到主搜索区
- 只在“已出院”场景显示
- 不碰 `searchComp.vue`

### Review A
检查：
- 插入点对不对
- 是否只在已出院显示
- 是否未破坏主搜索区结构

### Task B
只处理 `searchComp.vue`

目标：
- 去掉 `outAreaOrHospitalDischage` 的重复展示
- 不改主搜索区逻辑

### Review B
检查：
- 是否真的去重
- 是否没有误伤其他筛选项

### Task C
统一 verification

目标：
- 验证交互、场景、参数链路

这就是超窄 handoff 的典型形态：

- 每步目标单一
- 每步可 review
- 错了容易收口

---

## 8. Controller 下发 implementer 时必须包含什么

超窄 handoff 至少必须包含：

1. **子任务目标**
2. **明确 in scope**
3. **明确 out of scope**
4. **指定文件范围**
5. **当前不要碰哪些文件**
6. **本步停止条件**
7. **本步交付格式**
8. **本步 review 前不能自行继续的规则**

也就是说，不能只说：

- “把这个需求实现一下”

而要说清：

- “这一步只改哪里，不改哪里，做完后停下，等 review”

---

## 9. Implementer 不应承担的判断

在超窄 handoff 下，Implementer 不应承担：

1. 是否要再拆任务
2. 是否顺手改另一个文件
3. 是否把第二阶段也一起做了
4. 是否自己决定“这应该算通过了”
5. 是否把 review 和 verification 吞并成自我判断

这些都应该由 Controller 和 Review Gate 承担。

---

## 10. 超窄 handoff 的收益

采用该规范后，直接收益有：

1. implementer 更不容易发散
2. review 更早介入
3. 错误更容易收口
4. 主控更容易判断下一步
5. runtime 记录也更清晰，因为每一步的目标和停点都明确

---

## 11. 与 runtime 的关系

超窄 handoff 与 `planning-runtime` 是天然协同关系：

- `task-plan.md`：记录子任务拆解与当前 phase
- `findings.md`：记录 locator 证据
- `progress.md`：记录 implementer 每一步实际做了什么
- `outcome.md`：记录是否进入下一阶段

换句话说：

**没有超窄 handoff，runtime 容器容易记一堆混乱动作；有了超窄 handoff，runtime 才更像阶段化执行轨迹。**

---

## 12. 最终结论

当前护士站框架下，Implementer 不应再接“大而全”的实现任务。

从现在开始，默认规则应改为：

- **能拆就拆**
- **一阶段只做一件事**
- **一阶段结束必须先 review，再决定是否进入下一阶段**

这不是为了流程变重，而是为了让执行链真正稳定可控。
