## 2. 对 `1543024` 的重新判断

## 2.1 它不是不值得进框架，而是不该默认走重链

`1543024` 的价值不是需求本身有多复杂，而是它是一个很好的“流程验证样本”：

- 模块清楚：住院护士站床位卡
- 页面清楚：主搜索区 / 更多搜索
- 行为清楚：把时间区间条件前移
- 场景清楚：仅“已出院”显示
- 非目标也基本清楚：不处理默认勾选且不可编辑

这说明：

> `1543024` 不是“不该进入框架”，而是**不该一上来就被送进偏重的多阶段执行链**。

它更适合被当作一个**中低复杂度、可验证、可拿来校准流程的样本任务**。

## 2.2 真正暴露的问题，不是任务太简单，而是框架缺少前置分流

从当前证据看，`1543024` 跑偏，不是因为“简单任务不值得用框架”，而是因为框架在进入执行前少了一层关键判断：

- 这次是否真的需要 runtime？
- 是否真的需要 locator / implementer / review / verification 全链齐上？
- 是否已经具备足够清晰的 UI 位置、展示条件、交互约束、验收口径？
- 是否应该先做一个 requirement-fit check，再决定是否进 coding？

当前问题是：

> 框架已经有了很多后段角色，但前段缺少“任务级别判断 + 需求清晰度闸门”。

因此一旦用户说“用框架跑一遍”，系统就容易默认走重链，而不是先判断“这次该走哪条链”。

## 3. 当前根因重述：真正卡住的是“需求清晰度闸门”而不是单纯实现能力

结合你补充的最新判断，当前根因需要从“框架太重”进一步收敛成更准确的表达：

### 根因 1：需求沟通产物没有把关键 UI 落点显性化

以 `1543024` 为例，虽然大方向已经明确，但仍缺少对以下内容的前置显性确认：

- 新增控件到底插在主搜索区的哪个位置
- 与现有控件的相对顺序是什么
- 是否需要替换原位置、还是新增后再去重
- 验证时应该对照什么页面结构判断“做对了”

这类信息如果不在需求分析阶段写清楚，后面 implementer 就只能靠猜。

### 根因 2：中间没有“需求适配 review”这一闸门

当前链路更偏向：

- intake → planning → locate → implement → review → verify

但对这类 UI 需求，真正缺的是一个更靠前的闸门：

- intake → **需求适配确认（UI 落点 / 展示条件 / 验收样式）** → planning / coding

也就是说，问题并不只是“实现 agent 不够稳”，而是：

> 在进入实现之前，没有先确认“需求描述是否已经达到可被稳定实现和稳定验证的程度”。

### 根因 3：verification 缺少前置可核对物

你提到“过程中也未与我确认，导致在验证阶段无法形成闭环”，这点非常关键。

说明当前 verification 的问题不是只发生在最后，而是前面就埋下了：

- 没有明确插入位置
- 没有明确页面对照图
- 没有明确控件结构示意
- 没有明确‘完成后我该看什么’

于是最后 verification 只能判断“像不像”，无法判断“是不是”。

这说明护士站框架目前最需要补的，不是继续堆后段 review，而是：

> **把验证所需的最小证据，在需求和 planning 阶段前置出来。**

---

## 4. 结论：框架不该被削平，而该增加“轻 / 中 / 重”三档自适应路由

我同意你的判断：

> 一套成熟框架不应该只适配重任务，而应该能根据任务复杂度和信息完整度自适应。

因此，正确方向不是“放弃框架处理 `1543024` 这类任务”，而是让框架具备三档路由能力。

## 5. 新的任务分级建议

## 5.1 轻任务（Light）

### 典型特征
- 单页面或单模块内的小改动
- 目标位置明确
- 交互变化有限
- 影响范围小
- 验收可以用一句话或一张页面结构说明清楚
- 一般不需要跨多轮探索

### 典型例子
- 把某个筛选条件从更多搜索前移到主搜索区
- 调整显示条件
- 修改一个前端控件的文案、顺序、显隐规则
- 小范围参数映射修正

### 默认链路
- `brainstorming`（轻量版 intake）
- `requirement-fit mini check`
- 直接进入**轻实现链**：locator（可选）→ implementer → verification

### 不默认启用
- 不默认建 runtime
- 不默认启用完整 review-gate 双门
- 不默认多 subagent 串行

### 但必须满足的前置条件
- 页面 / 模块明确
- 新增或移动控件的位置明确
- 展示条件明确
- 非目标明确
- 至少有一句可验证的验收描述

### 失败回退规则
如果轻任务在执行前发现以下任一情况，则自动升级为中任务：
- UI 落点说不清
- 涉及两个以上文件且边界不清
- 参数链路和场景限制无法直接判断
- 验收标准无法写成明确检查项

---

## 5.2 中任务（Medium）

### 典型特征
- 需求本身不算大，但存在跨文件、跨条件、跨角色确认
- 需要先定位再实现
- 需要至少一轮计划和中间 review
- 需求边界还可以收口，但不能直接开改

### 典型例子
- 类似 `1543024` 这种：虽然是纯前端，但涉及主搜索区、更多搜索去重、显示场景限制、参数链路保持
- 一个页面多处联动但影响仍可控的优化
- 小型 bug，但根因并不完全显性

### 默认链路
- `brainstorming`
- **需求适配确认**
- `writing-plans`
- `locator`
- implementer（窄 handoff）
- Gate 1 requirement-fit review
- `verification`

### runtime 规则
- 默认**可不建 runtime**
- 只有满足以下条件之一才建：
  - 需要跨轮推进
  - 需要保留证据链 / findings / outcome
  - 本次任务本身就是流程样板或框架验证样本

### 说明
`1543024` 更适合归到**中任务**，而不是重任务。

它之所以让人感觉“走重了”，不是因为它只能走轻任务，而是因为当前链路缺少中档模式，导致它被直接送进了重链。

---

## 5.3 重任务（Heavy）

### 典型特征
- 多阶段
- 高不确定性
- 需要跨 repo / 跨模块 / 跨角色
- 需要显式证据链
- 需要 runtime 持续跟踪
- 需要 formal review / verification / retrospective

### 典型例子
- 护士站框架自身建设
- 复杂 bug 定位与治理
- 需要 locator / implementer / verifier 分层协作的大改动
- 需要 planning-runtime 承接的多轮执行任务

### 默认链路
- `brainstorming`
- 任务分级判断
- 建 runtime
- `writing-plans`
- `subagent-execution`
- `review-gate`
- `verification`
- `mvp-retrospective`

### 说明
当前护士站框架最完整的一套 skill 组合，本质上就是为重任务设计的；这没有错，但它不能再被当成默认路径。

---

## 6. 关键优化：新增“需求适配确认”层，而不是只调轻重

如果只做轻重分流，但不补“需求适配确认”，问题还会重复。

因此我建议在护士站框架里新增一个前置层，位置放在 `brainstorming` 之后、`writing-plans` 之前。

## 6.1 这一层要检查什么

### UI / 交互类任务必须补齐
- 控件新增 / 移动 / 替换的位置
- 与相邻控件的顺序关系
- 场景限制（在哪些状态显示 / 不显示）
- 是否保留原交互
- 是否需要去重旧入口
- 验收时要看什么页面结果

### 最好产出一种最小结构化结果
可以很短，但必须有：
- 页面：
- 控件：
- 插入位置：
- 显示条件：
- 非目标：
- 验收观察点：

如果这些写不出来，就不该直接进入 implementer。

## 7. 对现有 skill 的具体优化建议

## 7.1 `nurse-station-brainstorming`

### 当前问题
它更擅长判断“任务清不清楚”，但还不够强调：
- UI 落点是否清楚
- 验证所需的页面结构证据是否清楚
- 是否适合 light / medium / heavy 路由

### 建议调整
新增三个必填判断：
- Task level: light / medium / heavy
- UI placement clarity: yes/no
- Acceptance artifact ready: yes/no

并在 Decision 中补：
- Suggested route:
- Need requirement-fit checkpoint before coding: yes/no

---

## 7.2 `nurse-station-writing-plans`

### 当前问题
对复杂任务足够，但对中轻任务偏重，容易默认展开 agent split 和多阶段描述。

### 建议调整
增加一句规则：
- 如果是 light / medium 任务，优先输出最小实现计划，不强制展开完整多角色链。

同时新增一个 section：
- Pre-code confirmation items
  - UI insertion point
  - scene visibility
  - acceptance screenshot / structure hint

---

## 7.3 `nurse-station-review-gate`

### 当前问题
它已经强调 requirement fit 与 code quality 分离，这是对的；但对轻 / 中任务来说过晚。

### 建议调整
把 Gate 1 往前借一层，允许在 coding 之前先做一次 **Requirement-fit mini gate**。

对于 UI 任务，mini gate 重点检查：
- 位置是否明确
- 场景是否明确
- 去重 / 保留逻辑是否明确
- 是否已形成可供 verification 对照的检查项

---

## 7.4 `nurse-station-verification`

### 当前问题
它强调结果验证，但缺少“没有前置验收物时必须判为未完成”的硬约束。

### 建议调整
新增规则：
- 如果没有明确的前置验收点（如控件位置、场景限制、展示对照），不得给出“完成”结论。

---

## 7.5 `nurse-station-subagent-execution`

### 当前问题
适合重任务，但不适合被默认套在所有任务上。

### 建议调整
新增一条显式路由约束：
- 只有 medium / heavy 且已完成 requirement-fit checkpoint 的任务，才建议进入 subagent execution。
- light 任务默认不走 subagent 链，除非用户明确要求或执行面超出主控可直接承接范围。

## 8. 对 `1543024` 的最终归类

## 判断
`1543024` 应归为：**中任务（偏轻）**。

## 原因
- 不是纯聊天即可完成，仍需要代码定位和修改。
- 不是完全 trivial，因为涉及：
  - 主搜索区位置
  - 更多搜索去重
  - 已出院场景限制
  - 参数链路保持
- 但也远未达到需要默认启用完整 runtime-heavy 链的程度。

## 正确路由
建议后续此类任务默认走：
1. `brainstorming`
2. requirement-fit mini check
3. 最小计划
4. locator（若文件未完全确定）
5. 窄 implementer
6. requirement-fit review
7. verification

而不是：
- 一上来建 runtime
- 默认全角色全链路齐上
- 把流程验证样本误当作重任务模板

## 9. 框架层面的真正改进方向

这次最值得保留的结论不是“简单任务别用框架”，而是：

### Keep
- 角色拆分思路是对的
- review / verification 分离是对的
- runtime 对重任务是必要的

### Change
- 不再把完整重链当默认路径
- 在前段增加任务分级判断
- 在 coding 前增加 requirement-fit checkpoint
- 把 verification 所需证据前置到需求 / 计划阶段

### Add next
1. 新增一份“任务分级与路由规则”正式文档
2. 收紧 `brainstorming / writing-plans / subagent-execution / verification` 四个 skill
3. 为 UI 需求新增一个轻量模板：`ui-requirement-fit-check`
4. 把 `1543024` 作为“中任务样板”重新整理，而不是再把它当重链样板

---

## 10. 一句话结论

`1543024` 暴露的不是“框架不适合简单任务”，而是：

> 当前护士站框架缺少任务分级与需求适配前置闸门，导致一个本应走“中任务偏轻链路”的前端需求，被过早送入重执行链；真正要修的不是放弃框架，而是让框架学会先判断任务，再决定走多重。
