# 护士站专项开发框架蓝图 v1

## 1. 文档定位

本文档用于定义一套基于 `OpenClaw` 的护士站专项开发框架蓝图，用于承接后续住院/门诊护士站系统的优化、扩展开发、稳定性治理与开发流程规范化工作。

这不是单纯的 AI 编程插件选型说明，也不是单个 skill 的安装文档，而是一套面向专项执行的协作框架设计稿。

---

## 2. 上层目标

### 2.1 战略目标

服务部门定位：**通过专项优化工作，持续提升护士站系统整体稳定性，最终实现降本增效。**

### 2.2 当前阶段目标

在现有 `OpenClaw` 框架基础上，搭建一套面向护士站系统开发与治理的专项开发框架，实现：

1. 提升开发效率
2. 规范后续开发流程
3. 结合多 Agent 协作承接需求开发
4. 复用成熟 skill 与现有机制
5. 沉淀可复用的开发成果、经验和范式
6. 反哺系统稳定性优化与长期降本增效

### 2.3 判断成败的核心标准

这套框架是否成功，不以“技术栈是否先进”作为主要判断，而以是否推动以下结果作为判断标准：

1. **稳定性提升**：线上问题减少、重复故障减少、问题定位更快
2. **开发效率提升**：需求推进更顺、返工更少、跨人协作效率更高
3. **流程规范化**：开发过程更一致、质量控制更明确、交付更可控
4. **成果可复用**：历史方案、分析过程、修复剧本、模板资产可以持续复用
5. **综合降本增效**：通过减少重复劳动、返工、运维消耗，产生可感知业务收益

---

## 3. 为什么需要这套框架

当前护士站开发场景存在几个典型问题：

1. 多数需求并非全新建设，而是基于已有功能持续扩展
2. 历史功能演进中部分场景缺乏统一开发规范
3. 研发能力参差不齐，代码质量与修改方式不一致
4. 系统历史 BUG 较多，稳定性压力持续存在
5. 开发成果容易停留在单次交付，缺少结构化沉淀与复用

因此，当前需要的并不是“再引入一个更会写代码的模型”，而是一套能够：

- 在编码前约束需求与方案
- 在执行中规范任务拆解与质量控制
- 在执行后形成验证与复盘闭环
- 将专项经验沉淀成可复用资产

的开发执行框架。

---

## 4. 框架核心思路

### 4.1 总体原则

本框架遵循以下原则：

1. **稳定性导向优先于单次交付速度**
2. **流程约束优先于自由发挥**
3. **系统化分析优先于经验式试错**
4. **验证闭环优先于“感觉已经修好”**
5. **结果沉淀优先于一次性完成**
6. **吸收成熟方法论，但不整包照搬外部框架**

### 4.2 框架定位

这套框架的定位不是替代现有开发工具，而是成为：

- `OpenClaw` 之上的专项开发协作层
- 多 Agent 协作的任务编排层
- 成熟 skill 的组织与路由层
- 开发结果的沉淀与复用层

---

## 5. 整体分层设计

建议将框架拆为五层。

### 5.1 目标与路由层

负责：

- 接收需求或专项目标
- 判断这是稳定性治理、功能扩展、故障修复、隔离优化还是探索性工作
- 明确本次任务是否进入正式开发流程
- 决定是否需要调用执行型 Agent

在当前体系中，这一层建议由 `OpenClaw 主会话` 承担。

### 5.2 需求澄清与设计层

负责：

- 澄清目标、边界、风险、成功标准
- 判断属于新增、扩展、修补还是债务治理
- 明确影响模块、改动范围、前后端边界、数据影响、日志与监控要求
- 输出可供执行的设计说明或任务草案

这一层适合吸收以下成熟 skill 的方法：

- `brainstorming`
- `writing-plans`
- `systematic-debugging`（当问题驱动时）

### 5.3 执行编排层

负责：

- 将任务拆分为适合执行 Agent 承担的小任务
- 决定采用单 Agent 执行、串行多 Agent 协作，还是分阶段人工确认
- 维护任务上下文、输入输出与检查点
- 决定每一步是否进入代码执行

这一层是框架的关键层，当前可由 `OpenClaw + 模板 + 任务规范` 先行实现，后续逐步演进为更自动化的多 Agent 编排机制。

### 5.4 代码执行层

负责：

- 读代码
- 定位问题
- 修改代码
- 运行必要测试或验证命令
- 输出执行结果与变更说明

### 5.5 验证与沉淀层

负责：

- 对执行结果做 review / 验证
- 判断是否满足需求与稳定性目标
- 形成复盘、模板、案例、剧本、检查单等复用资产
- 将可迁移经验回写到工作系统、memory 或专项资料中

---

## 6. 代码执行到底发生在哪一层

### 6.1 关键判断

这套框架中，**真正的代码执行发生在“代码执行层”**，而不是发生在 skill 本身。

换句话说：

- `OpenClaw` 负责主控、路由、编排、记忆、沉淀
- skill 负责提供流程规范、分析方法、执行模板
- `OpenCode / Codex / 其他 coding agent` 负责真正读写代码

### 6.2 当前最现实的驱动方式

当前阶段建议采用：

`OpenClaw 主控 -> 任务分析/计划 -> exec 调用 OpenCode / Codex -> 回收结果 -> review/验证 -> 沉淀复用`

其中：

- `exec` 是执行器启动方式
- `OpenCode / Codex` 是代码执行引擎
- 多 Agent 协作属于执行编排层的组织方式
- skill 是上层工作流约束和方法库

### 6.3 为什么要显式区分“进入执行”

框架中应明确区分三种状态：

1. **仅分析**：只做澄清、方案、影响分析，不进入代码执行
2. **准备执行**：任务已形成，但尚未调用执行引擎
3. **进入执行**：目标明确、文件范围明确、验收标准明确，才正式调用 `exec`

这样可以避免“还没想清楚就开始改代码”的问题。

## 7. 多 Agent 协作在本框架中的位置

### 7.1 多 Agent 不是目标，是执行手段

本框架不是为了“上多 Agent”而上多 Agent。

多 Agent 的作用是：

- 分离不同角色
- 降低单个 Agent 同时承担所有任务时的混乱
- 提高并行度与审查质量
- 让执行结果更可控

### 7.2 建议的角色分工

可先定义以下角色：

1. **主控 Agent**
   - 负责目标澄清、任务收口、是否进入执行、结果汇总
   - 建议由 `OpenClaw 主会话` 承担

2. **分析 Agent**
   - 负责代码定位、影响分析、调用链梳理、风险点识别

3. **实现 Agent**
   - 负责按任务修改代码、补测试、整理变更说明

4. **审查 Agent**
   - 负责按计划与标准检查实现结果，指出风险与遗漏

5. **验证 Agent（可选）**
   - 负责测试执行、日志/监控点校验、回归项确认

### 7.3 当前阶段的建议策略

当前阶段不建议一开始就做复杂自动编排，而应先采用：

- `主会话 + 执行型 Agent` 的最小协作链路
- 必要时再增加分析 / review 角色
- 先跑通“单任务闭环”，再扩展到并行多 Agent

即：

`main -> executor -> review -> 回写`

而不是一开始就构建复杂多 Agent 平台。

---

## 8. 对成熟 skill 的吸收策略

### 8.1 适合优先吸收的能力

建议优先吸收以下 skill / 方法：

1. `brainstorming`
   - 用于需求澄清、边界确认、方案比较

2. `writing-plans`
   - 用于将需求拆成清晰可执行的小任务

3. `systematic-debugging`
   - 用于 BUG 排查、根因分析、避免经验式试错

4. `verification-before-completion`
   - 用于确保问题真的被修复，而不是主观判断

5. `requesting-code-review`
   - 用于形成统一的 review 清单

6. `test-driven-development`
   - 用于提升改动质量，减少扩展开发中的回归风险

### 8.2 不建议直接整包照搬的部分

以下能力可以关注，但不建议初期重度依赖：

1. `subagent-driven-development`
   - 方法上有价值，但依赖较成熟的编排基础

2. `using-git-worktrees`
   - 对并行开发有帮助，但适合作为后续增强项

3. 过度自动化的流程联动
   - 当前阶段若规范和模板未先稳定，自动化只会放大混乱

---

## 9. 产出沉淀与复用机制

这套框架必须把“复用”设计为内建能力，而不是事后补充。

### 9.1 建议沉淀的资产类型

1. 需求澄清模板
2. 影响分析模板
3. 执行计划模板
4. 代码 review 检查单
5. 测试/验证检查单
6. 常见问题根因剧本
7. 典型改造范式
8. 专项复盘总结
9. 可复用的自定义 skill

### 9.2 推荐沉淀路径

每次正式专项或较完整任务结束后，至少回写：

- 做了什么
- 为什么这么做
- 哪些地方有效
- 哪些地方失败或代价高
- 下次遇到类似问题应直接复用什么

这样才能把“单次执行”逐步沉淀成“可复用能力”。

---

## 10. 框架最小可行闭环（MVP）

建议先实现以下最小闭环：

1. **需求准入**
   - 明确目标、成功标准、影响范围

2. **任务拆解**
   - 形成结构化计划与执行顺序

3. **执行触发**
   - 通过 `exec` 调用 `OpenCode / Codex`

4. **结果回收**
   - 收集执行结果、变更摘要、风险说明

5. **验证确认**
   - 用统一检查单确认是否真的完成

6. **沉淀回写**
   - 形成可复用模板、案例或专项资料

只要这 6 步跑通，就已经不是“散装 agent 使用”，而是一套真正可演进的开发框架。

---

## 11. 当前版本的明确结论

### 11.1 结论一

`superpowers` 值得研究，尤其适合作为“流程设计样板”和“skill 组织方式”的参考。

### 11.2 结论二

本框架的真正底座不应是外部插件，而应是：

- `OpenClaw` 作为主控与记忆底座
- 现有成熟 skill 作为方法库
- `exec + OpenCode / Codex` 作为当前阶段的代码执行引擎
- 多 Agent 协作作为逐步演进的执行机制

### 11.3 结论三

这套框架最终不是为了构建一个“更高级的 AI 开发玩具”，而是为了服务部门定位：

**通过专项持续提升护士站系统稳定性，并以开发效率提升、流程规范、成果复用为抓手，最终实现降本增效。**
