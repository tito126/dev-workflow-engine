# 面向当前 OpenClaw 体系的最小记忆改造方案 v1

## 1. 文档定位

本文档用于在当前 `OpenClaw + memory + work-system` 体系基础上，设计一套**最小改造方案**，吸收 `planning-with-files` 的有效思想，但不推翻现有结构。

本方案重点解决的不是“记更多东西”，而是：

1. 让当前目标更稳定地被持续追踪
2. 让错误经验从“事后总结”变成“执行前约束”
3. 让上下文在多轮协作、多 Agent 协作中更轻、更稳
4. 让当前工作状态更清晰，减少断片和重复判断

---

## 2. 当前体系的基础判断

当前体系已经具备较强的连续性基础：

1. `memory/YYYY-MM-DD.md` 已承担日常连续性记录
2. `MEMORY.md` 已承担长期记忆与高层判断沉淀
3. `work-system/` 已开始承接项目、日总结、交付物、框架文档等正式工作流记录
4. `memory_search` 已具备语义召回能力，可解决“找不到旧上下文”的大量问题

因此，本次优化**不应从头重建记忆系统**，而应聚焦补齐当前最缺的一层：

**执行态工作记忆层（working memory layer）**

也就是：

- 当前到底在推进什么
- 为什么推进
- 这轮执行必须遵守什么约束
- 哪些坑已经踩过，不能再踩
- 下一步是什么
- 什么叫“算完成”

---

## 3. 本次优化的核心判断

### 3.1 一句话结论

这次优化不是为了让系统“更复杂”，而是为了在现有体系上补一层：

**轻量、显式、面向执行的工作上下文层。**

### 3.2 吸收 `planning-with-files` 的四个核心思想

建议只吸收以下四个思想，而不整包照搬：

1. **目标锚定**：当前正在追的目标要单独钉住
2. **错误持久化**：错误经验要能在下一轮执行前被主动加载
3. **上下文轻量化**：当前任务上下文要比长期记忆更小、更聚焦
4. **执行态显式化**：当前状态、下一步、完成定义要能一眼看清

---

## 4. 当前体系的主要痛点

## 4.1 记忆强，但“当前任务锚点”还不够硬

当前系统已经能较好找回历史记忆，但“本轮最重要的目标与约束”常常分散在：

- 聊天消息
- `memory/YYYY-MM-DD.md`
- `MEMORY.md`
- 项目档案
- 临时交付文档

结果是：

- 进入新一轮协作时，需要重新拼装上下文
- 容易知道“之前聊过什么”，但不够快地锁定“当前最该做什么”

## 4.2 错误有沉淀，但未必在执行前生效

当前已经有不少高价值经验教训，例如：

- Codex 调用必须显式传 `cwd`
- 避免 ACP 路径的不稳定性
- 台账类文件禁止整体覆盖
- 提醒默认不走 `cron`

但这些规则目前主要散落在：

- `TOOLS.md`
- `MEMORY.md`
- daily memory

问题在于：

**写下来了，不等于本轮任务开始时一定会被准确激活。**

## 4.3 正式工作流在增强，但执行工作集仍偏重

当前 `work-system/` 已开始形成项目、交付物、流程、模板等正式层，但执行时仍缺一个“当前只看这几个文件就够”的最小工作集。

结果是：

- 正式资料越来越多
- 真正进入执行时，反而容易上下文切换成本变高

## 4.4 失败案例更像知识，还没完全变成机制

目前大量失败经验已被记录，但要真正降低重复犯错，需要进一步把它们变成：

- 可装配
- 可复用
- 可在任务开始前主动读取

的执行规则。

---

## 5. 最小改造原则

本次改造遵循以下原则：

1. **不替换** 现有 `memory/`、`MEMORY.md`、`work-system/`
2. **不制造过多新层级**，避免维护成本反噬
3. **不削弱** `memory_search` 的语义召回优势
4. **只增加一层轻量执行态文件**
5. **优先改造活跃任务与持续项目**，不追求全盘一次性重构

---

## 6. 最小改造后的目标结构

建议在 `work-system/` 下增加两类轻量目录：

```text
work-system/
  active-context/
  rules/
```

说明如下。

### 6.1 `work-system/active-context/`

用于存放**当前活跃事项的最小执行上下文**。

每个活跃事项一个文件，建议命名：

```text
work-system/active-context/<topic>.md
```

例如：

- `work-system/active-context/nurse-station-dev-framework.md`
- `work-system/active-context/bingqu-hushi-gaowei-xiufu.md`
- `work-system/active-context/log-inspect-evolution.md`

这类文件不是长期档案，而是**运行态工作集**。

### 6.2 `work-system/rules/`

用于沉淀**高频可复用的执行规则卡**。

每条规则一个文件，例如：

- `work-system/rules/codex-exec-boundary.md`
- `work-system/rules/ledger-files-precise-edit-only.md`
- `work-system/rules/reminder-routing-default.md`

这些规则卡的作用不是长期叙事，而是：

**在任务开始时，按场景快速装配本轮约束。**

---

## 7. 新增文件的职责边界

## 7.1 `memory/YYYY-MM-DD.md`

继续承担：

- 当天发生了什么
- 临时连续性记录
- 对话中的重要事件
- 尚未完全结构化的信息

**不要求**它承担“当前任务唯一真相源”。

## 7.2 `MEMORY.md`

继续承担：

- 长期稳定的偏好
- 高层判断
- 成功标准
- 可跨项目复用的重要原则

**不建议**承载当前任务的实时推进状态。

## 7.3 `work-system/projects/active/*.md`

继续承担：

- 项目档案
- 阶段进展
- 风险
- 里程碑
- 下一步

它是**正式项目层**，不是最轻执行层。

## 7.4 `work-system/active-context/*.md`

新增承担：

- 当前目标
- 当前阶段判断
- 本轮关键约束
- 禁踩坑
- 下一步
- 完成定义
- 关联项目/交付物/提醒

它是**执行层的最小工作上下文包**。

## 7.5 `work-system/rules/*.md`

新增承担：

- 可复用执行规则
- 错误持久化
- 某类任务的边界约束
- 何时适用 / 何时不适用

它是**机制层的经验卡片库**。

---

## 8. `active-context` 文件模板建议

建议每个活跃事项统一采用以下结构：

```markdown
# <事项名称>

## 1. 当前目标
- 这轮要推进什么
- 为什么现在推进

## 2. 成功标准
- 做到什么算阶段完成
- 关键衡量口径是什么

## 3. 当前阶段判断
- 现在处于：分析 / 计划 / 执行 / 验证 / 沉淀
- 当前最关键的卡点是什么

## 4. 本轮硬约束
- 这轮必须遵守的规则
- 不能越界做什么

## 5. 禁踩坑
- 已知容易重复犯错的点
- 本轮特别要避免的行为

## 6. 当前下一步
- 下一步具体动作
- 谁来做 / 用什么方式做

## 7. 关联资料
- 关联项目档案
- 关联交付物
- 关联提醒
- 关联规则卡

## 8. 最近更新
- YYYY-MM-DD: 本轮最新判断
```

这个模板的目标不是写得完整，而是：

**让下一轮进入这个事项时，不用重新拼装上下文。**

---

## 9. `rules` 规则卡模板建议

建议每条规则统一采用以下结构：

```markdown
# <规则名>

## 1. 适用场景
- 哪类任务会触发这条规则

## 2. 问题表现
- 过去踩过什么坑

## 3. 根因
- 为什么会出这个问题

## 4. 执行约束
- 本轮必须怎么做
- 明确禁止什么

## 5. 何时不适用
- 哪些情况下不能机械套用

## 6. 参考案例
- 对应的 memory / 文档 / 项目记录
```

这样做的好处是：

规则不再只是“记得有这么回事”，而变成可以被主动引用的执行资产。

## 11. 与现有体系的具体衔接方式

## 11.1 与 `memory_search` 的关系

本方案不是替代 `memory_search`，而是与它分工：

- `memory_search` 负责：**从历史中找回相关上下文**
- `active-context` 负责：**让当前活跃事项尽量不需要大范围找回**

也就是说：

`memory_search` 解决“想不起来时去捞”

`active-context` 解决“当前就别再散了”

## 11.2 与项目档案的关系

项目档案继续作为正式记录；
`active-context` 则是项目当前执行窗口的压缩版。

可以理解为：

- 项目档案 = 完整 dossier
- active-context = 当前作战面板

## 11.3 与 Daily Focus / Daily Summary 的关系

后续可将 `active-context` 作为 `今日聚焦` 和 `今日总结` 的上游输入之一。

这样会带来一个明显好处：

提醒、重点事项、项目推进，不再只是时间驱动，而是能和当前目标锚点自然联动。

---

## 12. 这次优化能给你带来什么

这是本方案最关键的部分。

## 12.1 你会更快进入状态

现在每次续接一个持续事项，常常要重新拼：

- 之前聊过什么
- 已经形成了哪些判断
- 这轮到底推进到哪

加了 `active-context` 之后，进入状态会从“先翻很多材料”变成“先看当前作战面板”。

**直接收益：**

- 更少断片
- 更少重复解释
- 更少重新收口

## 12.2 你会更少重复踩同类坑

现在规则已经很多，但比较散；未来把高频规则抽成规则卡后，执行前更容易装配到本轮上下文里。

**直接收益：**

- 减少重复犯错
- 减少“明明记过但这轮没用上”的情况
- 多 Agent 协作时边界更一致

## 12.3 你会更容易看清“当前最重要的推进目标”

你现在的系统很强，但有一个风险：文件越来越多后，容易“什么都重要”。

`active-context` 的本质就是强迫系统回答：

- 当前这一轮最重要的目标是什么
- 什么不在本轮范围内
- 下一步到底是什么

**直接收益：**

- 更少偏航
- 更少任务膨胀
- 更容易把事项从消息流推进成工作流

## 12.4 你会更容易把失败经验变成可执行机制

你已经明确希望沉淀“成功/失败背后的因果解释与可迁移规则”。

规则卡就是把这件事从“复盘愿望”推进到“执行机制”。

**直接收益：**

- 失败不只是被记住，而会影响下一轮动作
- 经验更容易跨任务迁移
- 后续自建 skill 时，规则更容易被收编成 SOP

## 12.5 你会获得一个更适合多 Agent / 多轮协作的轻量中间层

随着护士站专项开发框架继续推进，后面无论是主会话、Codex、OpenCode、审查 Agent，都会越来越需要一个轻量、明确、低歧义的上下文包。

`active-context` 正好就是这层中间件。

**直接收益：**

- 主控更稳
- 执行更聚焦
- review 更有抓手
- 回写更容易对齐目标

---

## 13. 收益边界：这次优化不能神化

需要明确的是，这次优化**不会**直接带来：

1. 模型能力本身提升
2. 自动编排能力突然成熟
3. 所有历史文档自动变得干净统一
4. 不写项目档案也能只靠 `active-context` 长期运转

它真正带来的，是：

**让现有体系在执行层更稳、更轻、更不容易断。**

这是结构性增益，不是魔法增益。

---

## 14. 推荐落地顺序

建议分三步推进。

### 第一步：先建目录和 5 个种子文件

- 建立 `work-system/active-context/`
- 建立 `work-system/rules/`
- 创建前述 3 个 active-context 文件
- 创建前述 2 个规则卡文件

### 第二步：只在活跃事项中试运行

优先用于：

- 护士站专项开发框架
- 病区护士高危问题治理
- 日志巡检工具演进

不做全量历史回填。

### 第三步：和 Daily Focus / 项目档案联动

等试运行一段时间后，再决定是否：

- 将 `今日聚焦` 默认读取 active-context
- 将项目档案模板补一个“当前上下文入口”字段
- 将高频规则卡沉淀进本地 skill / SOP

---

## 15. 当前结论

如果说你现有的 `OpenClaw` 记忆体系，已经解决了：

**“我还能不能记住过去？”**

那么这次最小改造方案要解决的是：

**“我能不能更稳地围绕当前目标持续推进，并且不重复踩坑？”**

这件事对你是值得做的。

因为你现在的瓶颈，已经不再是“有没有记忆”，而是：

- 当前目标是否足够稳
- 当前执行是否足够轻
- 当前规则是否足够可装配
- 当前失败经验是否真的进入下一轮机制

本方案正是为这几个点服务。
