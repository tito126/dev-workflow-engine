# `exec opencode` 稳定性评估与 Wrapper 落地建议（2026-04-07）

## 1. 评估目标

本次评估不是泛泛讨论 `Codex` 或 `OpenCode` 谁更好，而是结合：

1. 现有 `codex-wrapper-design.md` 方案
2. 此前 MVC / MVP 真实运行情况
3. 当前 `exec opencode` 的已知风险点

来判断一个更具体的问题：

> 在后续主控通过 `exec opencode` 承接中大任务时，当前链路是否已经足够稳定，还是需要落地 wrapper 方案。

这里默认把文档中的 `codex` 替换为 `opencode` 来理解。

---

## 2. 先给结论

### 2.1 短结论

**对于小任务，当前裸 `exec opencode` 仍可用；但对于中大任务，不建议继续长期依赖“裸 exec + 轮询”模式。**

### 2.2 正式判断

如果后续你明确要把 `exec opencode` 作为常规执行链的一部分，尤其用于：
- 中任务
- 重任务
- 跨几分钟以上的分析 / 实现 /定位
- 需要稳定收口和可追溯结果的场景

那么：

> **wrapper 方案值得落地，而且我认为已经到了“应该做”的阶段，而不是“可以以后再说”的阶段。**

原因不是因为 `opencode` 本身不可用，而是当前主控链路在“长任务完成通知、结果落盘、低轮询收口”这三件事上仍然没有稳定机制。

---

## 3. 结合此前 MVC / MVP 运行情况，当前裸 `exec opencode` 的真实问题

## 3.1 问题一：完成感知仍然依赖 poll，而不是事件驱动

这点和 `codex-wrapper-design.md` 里描述的问题完全一致，只是 runner 从 `codex` 换成了 `opencode`。

当前裸 `exec opencode` 的完成判定，本质还是依赖：
- `yieldMs`
- `process poll`
- 主控人工判断输出是否已经足够完整

这在短任务上还能接受，但在中大任务上会出现两个问题：

1. **持续轮询**
   - 主控得不断回来问“好了没有”
   - 这本质上是把一个后台执行问题，转成主会话持续盯进程的问题

2. **收口时机容易失真**
   - 结果已足够，但 poll 还在继续
   - 或者进程还挂着，但有价值输出其实已经产生
   - 结果就是你之前明确指出过的：任务明明已经完成，却还在空耗等待

这和之前 Codex 场景里暴露出的“盲目 poll”问题是同构的。

---

## 3.2 问题二：中断与续接的可恢复性不够

裸 `exec opencode` 直接把任务生命周期绑定在当前进程会话上。

于是会出现这些脆弱点：
- poll 节奏不对，会浪费时间
- 当前会话如果被别的任务打断，状态续接成本高
- 如果进程异常退出，只能靠最后一次 stdout 片段猜发生了什么
- 主控无法天然区分：
  - runner 仍在运行
  - runner 已结束但结果未读取
  - runner 已失败
  - runner 已超时

### 本质
当前执行状态主要存在于：
- 进程本身
- poll 返回文本
- 主控短期记忆里

而不是一个正式状态容器里。

这会直接削弱 MVC / MVP 场景里你想要的“可追溯、可复盘、可工程化”的能力。

---

## 3.3 问题三：结果与状态没有解耦

当前裸 `exec opencode` 的常见状态是：
- stdout 混合了过程日志、最终结果、异常信息
- 主控需要自己从一长串输出里判断哪部分是最终可用结论

这在实验期没问题，但在正式框架里有三个坏处：

1. 不利于追溯
2. 不利于复盘
3. 不利于主控统一处理成功 / 失败 / timeout / killed 等状态

而你现在要构建的是一套成熟框架，不是一次性临时脚本协作。

因此“状态与结果分离”已经不是锦上添花，而是工程化底线。

---

## 3.4 问题四：长任务稳定性不只是 runner 稳不稳，更是主控能不能不被拖进等待地狱

这点很关键。

有时外部 runner 本身其实工作正常，但主控层如果没有：
- 明确状态文件
- 明确完成通知
- 明确结果落盘
- 明确异常收口方式

就仍然会在大任务场景中表现为“不稳定”。

所以：

> 当前 `exec opencode` 的主要不稳定点，不一定来自 `opencode` 本体，而是来自其外围执行管理层还没成型。

这恰恰说明 wrapper 方案的价值很高。

---

## 4. `codex-wrapper-design.md` 方案是否适用于 `opencode`

## 4.1 结论

**适用，而且几乎可以直接平移。**

把方案里的：
- `codex exec`
- `codex-runs/`
- `Codex done: <id>`

替换成：
- `opencode run` 或当前稳定的 `exec opencode` 调用形式
- `opencode-runs/`
- `OpenCode done: <id>` 或统一 runner-neutral 文案

即可。

## 4.2 为什么适用

因为文档真正解决的不是 `codex` 专属问题，而是**本地 runner 的执行治理问题**：
- 如何落盘 prompt
- 如何记录状态
- 如何保存结果
- 如何完成通知
- 如何让主控改为通知驱动而不是轮询驱动

这些问题对 `opencode` 一样成立。

---

## 5. 是否需要落地实现

## 5.1 我的判断

**需要，而且建议尽快落地一个最小可用版。**

不是因为现在已经完全不可用，而是因为：

- 你已经明确后续会用 `exec opencode`
- 已知风险点正好就是 wrapper 方案要解决的核心问题
- 护士站框架本身也正在从“流程样板”走向“正式执行系统”

如果还继续长期停在裸 `exec opencode`：
- 小任务还行
- 中大任务会反复遇到轮询、收口、续接、追溯问题
- 每次都得靠主控临场救火，而不是靠机制兜底

这和你想要的“成熟通用框架”方向是冲突的。

---

## 5.2 但不建议一步做到很重

我不建议一上来就做特别完整的重系统。

更合理的是先实现一个 **MVP 版 opencode wrapper**，只解决四件最关键的事：

1. prompt 落盘
2. status 落盘
3. result 落盘
4. 完成后触发 wake / 通知

只要这四件成立，就已经能把当前“裸 exec + poll”模式明显抬升一个档次。

## 6. 推荐的最小落地形态

## 6.1 目录建议

建议使用：

```text
C:\Users\pc\.openclaw\workspace\opencode-runs\
```

每个任务生成：
- `<id>.prompt.txt`
- `<id>.result.md`
- `<id>.status.json`

## 6.2 wrapper 入口

建议对应命名为：
- `opencode-run.ps1`

## 6.3 状态枚举

继续沿用文档方案即可：
- `running`
- `done`
- `failed`
- `timeout`
- `killed`

## 6.4 通知机制

建议仍沿用文档思想：
- wrapper 不直接给用户发消息
- wrapper 只发短通知 / wake
- 主会话收到通知后再读 `status + result`

这是非常对的边界，不建议改。

---

## 7. 与当前护士站 / MVC 运行方式的关系

如果后续护士站框架中存在：
- 主控 session
- 外部 `exec opencode` 作为分析 / 实现执行器
- 中大任务需要跨轮或至少跨分钟级等待

那么 wrapper 的价值会进一步放大：

### 对 MVC / MVP 的直接收益
- 主控不再被高频 poll 拖住
- 任务有正式状态容器
- 结果可落盘供 retrospective / framework review 使用
- 异常退出时能留下结构化状态
- 后续可以自然接入 runtime / work-system 的证据链

换句话说，wrapper 不是独立的小工具，而是：

> 外部执行器进入护士站正式框架的基础设施层。

---

## 8. 最终建议

## Keep
- 小任务场景下，当前裸 `exec opencode` 仍可作为临时快捷路径保留
- 主控掌握授权与最终回复的职责边界，继续保留

## Change
- 中大任务不再默认裸跑 `exec opencode + poll`
- 开始引入 `opencode-run.ps1` 作为统一入口
- 状态 / 结果 / prompt 三件套分离
- 主控从轮询驱动转为通知驱动为主、低频兜底检查为辅

## Add next
1. 先实现 `opencode-run.ps1` MVP 版
2. 约定 `opencode-runs/` 目录和文件格式
3. 选一个真实中任务跑通完整链路
4. 再决定是否补超时、清理、归档等增强能力

---

## 9. 一句话结论

如果后续你准备正式使用 `exec opencode` 承接中大任务，那么当前裸 `exec + poll` 的稳定性还不够；`codex-wrapper-design.md` 提出的方案对 `opencode` 同样成立，而且已经值得尽快以 MVP 形式落地。
