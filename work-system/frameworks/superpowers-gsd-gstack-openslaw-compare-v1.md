# `superpowers` / `GSD` / `Gstack` / 当前 OpenClaw 路线对比 v1

## 1. 文档目的

本文档用于对比几类与 AI 开发协作、skill 体系、多 Agent 开发框架相关的方案，重点判断它们对护士站专项开发框架建设的参考价值。

本文不以“谁更先进”作为评判标准，而以是否有助于以下目标作为判断依据：

1. 持续提升护士站系统整体稳定性
2. 提升开发效率
3. 规范开发流程
4. 支撑多 Agent 协作
5. 沉淀可复用成果
6. 最终服务降本增效

---

## 2. 对比对象说明

### 2.1 `superpowers`

定位为：面向 coding agent 的技能包 + 软件开发工作流方法论。

核心特点：

- 用 skill 约束 agent 的工作方式
- 强调 brainstorming、plans、TDD、review、verification
- 支持多类 coding agent 宿主
- 更偏“工程执行流程模板”

### 2.2 `GSD`

当前语境下，可视为一类强调**目标驱动、任务拆解、分阶段推进**的 Agent 开发/协作思路。

如果后续确认其具体定义或产品实现，可以进一步细化。

当前先将其作为“偏目标驱动 + 分阶段执行”的代表方案来参考。

### 2.3 `Gstack`

当前语境下，可视为一类强调**多层能力堆栈、组件化组织、多 Agent/多能力组合**的框架思路。

如果后续有具体仓库或实现，再进一步做精确分析。

当前先将其作为“偏架构组织与能力编排”的代表方案来参考。

### 2.4 当前 `OpenClaw` 路线

即：以 `OpenClaw` 作为主控与记忆底座，结合现有 skills、memory、共享文档体系，以及 `exec + OpenCode / Codex` 等执行引擎，逐步形成护士站专项开发框架。

---

## 3. 总体判断

### 3.1 一句话结论

- `superpowers`：更适合作为**开发流程与 skill 组织方式的参考样板**
- `GSD`：更适合作为**目标驱动与任务推进方法**的参考
- `Gstack`：更适合作为**多层能力组织与多 Agent 编排结构**的参考
- `OpenClaw` 当前路线：最适合作为**护士站专项开发框架的实际底座**

### 3.2 核心判断

如果目标是建设一个真正贴近护士站系统、能落地到专项执行、并持续服务稳定性提升的开发框架，那么：

**不应直接投奔某个外部框架，而应以 `OpenClaw` 为底座，吸收 `superpowers / GSD / Gstack` 的有价值部分。**

## 5. 分项分析

## 5.1 `superpowers`

### 优势

1. **工程流程很完整**
   - 从 brainstorming 到 plans、TDD、review、verification，形成较完整闭环

2. **非常适合矫正“上来就写代码”的坏习惯**
   - 对历史包袱多、扩展开发多的系统尤其有价值

3. **skill 组织方式成熟**
   - 对后续自建 skill 库有参考价值

4. **对执行型 Agent 使用方式有明确约束**
   - 更接近“工程经理 + 规范化开发流程”而非“代码生成器”

### 局限

1. **不是护士站专项框架本身**
   - 它解决的是 coding agent 怎么更规范地开发，不直接回答你部门级目标如何落地

2. **代码执行仍依赖外部宿主与引擎**
   - 不能替代 `OpenCode / Codex`

3. **如果直接整包照搬，容易出现流程过重或与本地体系脱节**

### 在本项目中的定位建议

建议作为：

- skill 设计参考
- 流程规范参考
- 执行编排思路参考

不建议直接作为护士站框架的唯一主系统。

---

## 5.2 `GSD`

### 优势

1. 强调目标导向，而不是仅关注局部编码动作
2. 适合做专项推进和阶段性拆解
3. 对“需求 → 任务 → 交付”的推进链路有启发价值

### 风险

1. 若缺少具体执行与验证机制，容易停留在管理层语言
2. 若与代码执行层结合不深，可能变成“计划很好，落地很虚”

### 在本项目中的定位建议

建议作为：

- 目标管理方法参考
- 专项任务拆解方式参考
- 阶段推进与里程碑管理参考

不建议直接替代本地执行框架。

---

## 5.3 `Gstack`

### 优势

1. 容易启发“底座层 / 编排层 / 执行层 / 记忆层”的架构设计
2. 对多 Agent、多组件组合有较强参考意义
3. 有助于把框架思路从“单工具使用”提升到“能力系统设计”

### 风险

1. 若过早追求 stack 化，容易超前设计
2. 可能会把问题引向“架构很好看”，但现场交付反而变慢

### 在本项目中的定位建议

建议作为：

- 系统分层设计参考
- 多 Agent 编排结构参考
- 长期架构演进方向参考

不建议在当前阶段就重投入做复杂抽象。

---

## 5.4 当前 `OpenClaw` 路线

### 优势

1. **最贴现场**
   - 已有 memory、共享文档、技能机制、主会话协作方式

2. **最容易和当前工作链路融合**
   - 可直接承接专项分析、执行、回写、复盘

3. **能直接连接执行引擎**
   - 当前已验证 `exec + OpenCode / Codex` 是现实可用路径

4. **便于成果沉淀**
   - 可直接将执行过程、总结、模板、经验沉淀进现有工作系统

### 局限

1. 默认并不自带成熟开发框架，需要你自己设计上层规范
2. 多 Agent 编排能力当前仍偏手工或半自动
3. skill 体系还需围绕护士站场景进一步定制

### 在本项目中的定位建议

建议明确为：

**护士站专项开发框架的实际底座。**

## 6. 对当前目标的支撑度判断

### 6.1 对“提升系统稳定性”的支撑

- `superpowers`：中高
  - 有助于规范实现与验证，但缺少业务专项层的稳定性治理语义
- `GSD`：中
  - 有助于目标推进，但对稳定性治理的直接抓手有限
- `Gstack`：中
  - 有助于搭框架，但不直接解决稳定性问题
- `OpenClaw` 路线：高
  - 可直接把稳定性专项、日志分析、执行改造、复盘沉淀串起来

### 6.2 对“提升开发效率”的支撑

- `superpowers`：高
- `GSD`：中高
- `Gstack`：中
- `OpenClaw` 路线：高（取决于本地框架设计成熟度）

### 6.3 对“规范后续开发流程”的支撑

- `superpowers`：高
- `GSD`：中高
- `Gstack`：中
- `OpenClaw` 路线：高（需要补齐规范层）

### 6.4 对“成果复用”的支撑

- `superpowers`：中
- `GSD`：中
- `Gstack`：中
- `OpenClaw` 路线：高

---

## 7. 建议的吸收方式

### 7.1 不建议的路径

1. 因为 `superpowers` 很成熟，就直接把它当成最终主框架
2. 因为 `Gstack` 看起来高级，就先做复杂架构设计
3. 因为 `GSD` 强调目标推进，就忽略执行与验证层

### 7.2 建议的路径

1. 以 `OpenClaw` 作为底座
2. 吸收 `superpowers` 的 skill 组织方式与工程流程
3. 吸收 `GSD` 的目标驱动与任务推进逻辑
4. 吸收 `Gstack` 的分层与编排视角
5. 围绕护士站专项场景形成本地化框架

---

## 8. 当前结论

### 结论一

如果只是讨论“哪个推荐是否有问题”，我的判断是：

**推荐 `GSD` / `Gstack` 的方向没有根本性错误。**

### 结论二

但如果问题是“你应该直接把它们作为当前主框架吗”，我的判断是：

**不建议。**

### 结论三

当前更合理的策略是：

- `OpenClaw` 做底座
- `superpowers` 做流程与 skill 样板
- `GSD` 做专项推进方法参考
- `Gstack` 做长期架构分层参考

### 结论四

护士站专项开发框架的核心，不在于采用哪个名词，而在于它能否真正回答：

1. 需求如何进入
2. 什么时候进入代码执行
3. 谁来拆任务
4. 谁来做 review
5. 谁来确认完成
6. 结果如何沉淀并复用
7. 是否真的促进稳定性提升与降本增效
