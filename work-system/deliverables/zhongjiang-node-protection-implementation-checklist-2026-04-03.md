# 中江同类问题避免拖垮节点实施清单版

## 1. 目标

本清单不再围绕单次事故细节展开，而是聚焦一个更直接的目标：

**即使后续再出现慢依赖、局部异常或高频请求堆积，也不能再把病区护士站节点整体拖垮。**

---

## 2. 实施总原则

- 先保护节点，再优化体验
- 先保障核心返回，再补增强信息
- 先做止血机制，再做链路精修
- 先形成统一保护，再避免后续同类问题重复出现

---

## 3. P0：止血实施项（优先最高）

### 3.1 关键请求总超时收口
- [ ] 梳理关键接口当前是否已有总超时控制
- [ ] 为关键链路设置明确总超时上限
- [ ] 超时后统一快速失败或降级返回
- [ ] 验证请求不会再持续挂起几十分钟

**交付结果**
- 一份关键接口总超时配置清单
- 一轮超时触发后的返回行为验证结果

### 3.2 连接池等待止损
- [ ] 检查当前 `Druid` 最大连接数、等待策略、超时配置
- [ ] 设置连接获取等待上限
- [ ] 明确连接池耗尽时的失败行为
- [ ] 验证连接池吃紧时不会无限堆积请求

**交付结果**
- 一份连接池关键配置清单
- 一轮连接池保护生效验证结果

### 3.3 核心链路与增强链路隔离
- [ ] 梳理当前接口返回字段，区分核心字段 / 增强字段
- [ ] 梳理核心返回依赖链路与增强查询链路
- [ ] 拆分主链路与增强链路执行关系
- [ ] 确保增强查询失败不会阻塞核心返回

**交付结果**
- 一份字段分层表（核心 / 增强）
- 一份主链路 / 增强链路隔离说明

### 3.4 非核心字段 fail-open
- [ ] 明确哪些增强字段允许为空
- [ ] 对允许降级的字段补默认行为
- [ ] 明确失败时前端展示口径
- [ ] 验证增强链路失败后核心接口仍可返回

**交付结果**
- 一份可降级字段清单
- 一轮 fail-open 验证结果

### 3.5 单段依赖超时补齐
- [ ] 梳理关键依赖调用点
- [ ] 检查每段依赖是否都已设置超时
- [ ] 补齐缺失超时配置
- [ ] 验证慢依赖不会无限悬挂

**交付结果**
- 一份关键依赖超时清单
- 一轮依赖超时验证结果

---

## 8. 验收口径

这份实施清单最终不是为了证明“问题解释清楚了”，而是为了验证以下结果：

- [ ] 慢依赖再次出现时，请求不会无限挂起
- [ ] 连接池吃紧时，节点不会整体拖死
- [ ] 增强信息失败时，核心接口仍能返回
- [ ] 节点在异常场景下仍能保基本可用
- [ ] 后续同类问题可以复用同一套治理手法，而不是每次重新分析

---

## 9. 一句话结论

**后续治理重点不是继续追一条异常，而是把“请求止损、资源隔离、失败降级、统一保护”真正变成可执行动作。**
