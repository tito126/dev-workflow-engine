# 4.2.2.3 输入、输出

## 4.2.2.3.1 设计说明

本节用于说明预约日程管理模块在典型业务场景下的输入与输出对象，重点描述系统在不同触发条件下接收什么业务数据、输出什么处理结果。

本节仅保留场景化输入输出说明和示例数据，不重复展开接口协议、调用责任、异常处理、幂等机制等内容；相关正式接口定义统一放在 `4.2.2.4 模块接口` 中说明。

本模块当前主要覆盖以下三类输入输出场景：

1. 三方系统推送排班；
2. 日程创建与预约处理；
3. HIS Check In 接诊关联。

---

## 4.2.2.3.2 三方系统推送排班输入输出

### 4.2.2.3.2.1 场景说明

当外部系统（如 HIS、康复、医技、手麻等）已维护排班数据时，可通过推送方式将排班主信息和时段明细同步到门诊护士站系统，供预约日程看板加载与展示。

### 4.2.2.3.2.2 输入内容

输入内容主要包括：
- 来源系统信息；
- 资源信息；
- 排班日期；
- 科室信息；
- 时段明细；
- 外部业务标识。

输入示例如下：

```json
{
  "source": "HIS",
  "resourceId": "ROOM_01",
  "resourceName": "张医生-主任医师",
  "resourceType": "门诊-医生",
  "scheduleDate": "2026-01-27",
  "scheduleNo": "SCH-20260127-001",
  "deptInfo": {
    "id": "D001",
    "name": "心内科"
  },
  "details": [
    {
      "startTime": "09:00",
      "endTime": "09:30",
      "resourceQuantity": 1,
      "businessDataId": "HIS-APPT-001"
    }
  ]
}
```

### 4.2.2.3.2.3 输出结果

系统接收并校验成功后，输出结果包括：
- 生成或更新排班主记录；
- 生成或更新排班时段明细；
- 为日程看板提供可展示的资源排班数据；
- 记录同步状态和处理日志。

输出示例如下：

```json
{
  "code": 200,
  "message": "排班数据处理成功",
  "data": {
    "scheduleId": "SCH_MAIN_001",
    "scheduleDate": "2026-01-27",
    "detailCount": 20,
    "status": "ENABLED"
  }
}
```

---

## 4.2.2.3.3 日程创建与预约处理输入输出

### 4.2.2.3.3.1 场景说明

预约日程管理模块中的日程创建与预约处理主要有两类方式：

1. 基于既有排班时段，通过预约组件完成新增、修改或取消预约；
2. 护士基于固定资源或常规日程资源手动新增日程。

### 4.2.2.3.3.2 方式一：通过预约组件处理预约

#### 输入内容

当用户点击可预约时段或已预约记录时，前端会将当前时段、资源、业务标识等上下文信息传递给预约处理逻辑。

输入示例如下：

```json
{
  "scheduleDetailId": "DET_1001",
  "businessDataId": "HIS-APPT-001",
  "resourceId": "ROOM_01",
  "scheduleDate": "2026-01-27",
  "startTime": "09:00",
  "endTime": "09:30"
}
```

#### 输出结果

处理完成后，系统输出预约结果，并在成功时更新日程/预约记录，必要时同步更新排班时段状态。

输出示例如下：

```json
{
  "code": 200,
  "message": "预约处理成功",
  "data": {
    "reservationId": "RESV_200",
    "status": "RESERVED"
  }
}
```

### 4.2.2.3.3.3 方式二：护士手动新增日程

#### 输入内容

当护士在日程看板中点击“新增日程”并填写表单后，系统接收资源、日期、时段、标题、患者信息（如有）和备注等内容。

输入示例如下：

```json
{
  "resourceId": "RESOURCE_001",
  "scheduleTitle": "张三-复诊",
  "scheduleDate": "2026-01-27",
  "startTime": "09:00",
  "endTime": "10:00",
  "patientId": "PAT_001",
  "businessDataId": "MANUAL-001",
  "remark": "手动创建"
}
```

#### 输出结果

系统完成资源与时间校验后，输出新建成功的日程记录，并同步写入操作日志。

输出示例如下：

```json
{
  "code": 200,
  "message": "日程创建成功",
  "data": {
    "reservationId": "RESV_201",
    "scheduleTitle": "张三-复诊",
    "status": "CREATED"
  }
}
```

### 4.2.2.3.3.4 说明

- 对于基于已有排班时段创建的预约，是否同步更新排班明细状态，应按最终业务规则处理；
- 对于固定资源下的手动新增日程，如不依赖预生成排班时段，则不应强制要求先生成排班数据；
- 已预约数据需记录预约类型，供日程看板按预约类型着色展示。

---

## 4.2.2.3.4 HIS Check In 接诊关联输入输出

### 4.2.2.3.4.1 场景说明

当 HIS 完成患者 Check In 后，会调用我方接口回传当前就诊信息，系统据此生成门诊护士接诊记录，并关联相关预约与医嘱信息。

### 4.2.2.3.4.2 输入内容

输入内容主要包括：
- 患者信息；
- 当前就诊信息；
- 关联排班或预约信息；
- 操作人信息。

输入示例如下：

```json
{
  "scheduleId": "SCH_MAIN_001",
  "patientId": "PAT-001",
  "currentVisitId": "VISIT-20260129-001",
  "currentVisitInfo": {
    "id": "VISIT-20260129-001",
    "date": "2026-01-29",
    "deptId": "D001",
    "deptName": "康复科"
  },
  "operatorId": "OP-001",
  "operatorName": "护士小王"
}
```

### 4.2.2.3.4.3 输出结果

系统处理成功后，输出接诊结果，并形成接诊记录与预约/医嘱的关联关系。

输出示例如下：

```json
{
  "code": 200,
  "message": "Check In 处理成功",
  "data": {
    "checkinId": "CHK_001",
    "status": "CHECKED_IN"
  }
}
```

# 4.2.2.4 模块接口

## 4.2.2.4.1 设计说明

本节用于说明预约日程管理模块涉及的后台接口和前端组件调用协议，重点描述系统之间如何交互、各接口在什么场景下被调用、需要传递哪些参数、返回哪些结果，以及回调、刷新和异常处理的边界。

本节不再重复描述纯场景化输入输出样例；相关内容已在 `4.2.2.3 输入、输出` 中单独说明。

本节接口分为三类：

1. 后台接口；
2. 前端组件调用协议；
3. 我方主动通知三方接口。

---

## 4.2.2.4.2 后台接口

### 4.2.2.4.2.1 三方系统推送排班接口

**接口地址：** `POST /api/third-party/schedule/push`

**功能说明：**
接收 HIS、康复、医技、手麻等系统推送的排班数据，生成或更新资源排班主记录及排班时段明细。

**调用方：**
外部排班系统。

**触发时机：**
外部系统完成排班发布、更新或同步时。

**请求参数：**
- 来源系统标识；
- 资源ID、资源名称、资源类型；
- 排班日期；
- 科室信息；
- 时段明细；
- 外部业务数据ID；
- requestId（如有）。

**返回结果：**
- 是否处理成功；
- 排班主记录ID；
- 排班明细数量；
- 当前状态。

**异常处理：**
- 参数缺失或格式错误时返回失败信息；
- 同步失败时写入 `outp_sync_status`；
- 关键处理过程写入 `outp_schedule_log`。

### 4.2.2.4.2.2 三方系统推送预约数据接口

**接口地址：** `POST /api/third-party/appointment/push`

**功能说明：**
接收三方系统推送的预约数据，并在必要时同时接收医嘱信息与就诊信息，生成预约记录和医嘱关联数据。

**调用方：**
康复系统、HIS 或其他三方预约来源系统。

**触发时机：**
外部系统完成预约创建、同步或变更回写时。

**请求参数：**
- 排班ID、资源ID；
- 预约日期、开始时间、结束时间；
- 患者信息；
- 来源系统信息；
- 医嘱列表；
- 就诊信息；
- requestId。

**返回结果：**
- 是否处理成功；
- 预约记录ID；
- 关联医嘱条数；
- 当前状态。

**异常处理：**
- 需进行幂等校验；
- 失败时记录 `outp_sync_status`；
- 关键操作写入 `outp_schedule_log`；
- 重试与对账策略详见 `4.2.2.5.8`。

### 4.2.2.4.2.3 HIS Check In 接口

**接口地址：** `POST /api/third-party/checkin`

**功能说明：**
接收 HIS 系统回传的 Check In 信息，生成门诊护士接诊记录，并关联预约与医嘱数据。

**调用方：**
HIS 系统。

**触发时机：**
HIS 完成当前就诊的 Check In 后。

**请求参数：**
- 排班ID；
- 患者ID；
- 当前就诊ID与就诊信息；
- 操作人信息；
- requestId。

**返回结果：**
- 是否处理成功；
- 接诊记录ID；
- 当前接诊状态。

**异常处理：**
- 如关联预约或医嘱失败，需记录异常信息；
- 接口处理结果需保留日志；
- 幂等处理与补偿策略详见 `4.2.2.5.8`。

### 4.2.2.4.2.4 三方取消排班接口

**接口地址：** `POST /api/third-party/schedule/cancel`

**功能说明：**
接收三方系统发起的取消排班请求，并根据是否存在关联预约决定后续处理方式。

**调用方：**
三方系统。

**触发时机：**
三方系统取消排班时。

**请求参数：**
- requestId；
- resourceId；
- scheduleDate；
- scheduleNo；
- sourceSystem；
- cancelReason。

**返回结果：**
- 若无关联预约，则返回取消成功；
- 若存在关联预约，则返回“已标记待处理”及相关说明。

**异常处理：**
- 先进行幂等校验；
- 处理结果写入同步状态表与日志表；
- 详细业务过程详见 `4.2.2.5.7`。

### 4.2.2.4.2.5 三方取消预约接口

**接口地址：** `POST /api/third-party/reservation/cancel`

**功能说明：**
接收三方系统发起的取消预约请求，释放对应时段占用，并更新预约记录状态。

**调用方：**
三方系统。

**触发时机：**
患者取消预约或外部系统取消预约时。

**请求参数：**
- requestId；
- businessDataId；
- sourceSystem；
- cancelReason。

**返回结果：**
- 预约取消处理结果；
- 对应预约记录状态。

**异常处理：**
- 幂等校验；
- 释放时段失败时记录异常；
- 详细业务过程详见 `4.2.2.5.7`。

## 4.2.2.4.3 前端组件调用协议

> 本节保留组件调用协议说明，便于与前端、三方组件和需求侧统一交互边界。

### 4.2.2.4.3.1 调整排班组件调用协议

**调用场景：**
护士在日程看板中点击“调整排班”按钮，对当前资源对应的排班进行调整。

**调用入口：**
日程看板资源列表头部的“调整排班”操作入口。

**核心入参：**
- resourceId；
- resourceType；
- scheduleDate；
- clinicZoneId；
- deptId；
- sourceSystem；
- businessDataId。

**核心出参：**
- 是否调整成功；
- 调整后的排班标识；
- 是否需要刷新当前看板。

**调用后处理：**
- 组件返回成功后，前端刷新当前资源对应排班；
- 后端记录日志并按业务规则更新排班数据；
- 如涉及已有预约，则需同步触发逆流程处理或通知逻辑。

### 4.2.2.4.3.2 预约组件调用协议

**调用场景：**
点击可预约时段进行新增预约，或点击已预约记录进行修改、取消预约。

**调用入口：**
日程看板时段色块。

**核心入参：**
- scheduleId；
- scheduleDetailId；
- resourceId；
- resourceType；
- scheduleDate；
- startTime；
- endTime；
- businessDataId；
- reservationId（修改/取消时）。

**核心出参：**
- 是否处理成功；
- reservationId；
- 最新预约状态；
- 是否需要刷新界面。

**调用后处理：**
- 新增、修改、取消成功后，前端刷新看板；
- 后端更新预约记录并记录日志；
- 如涉及三方回调，需同步记录同步状态。

### 4.2.2.4.3.3 跨科室预约组件调用协议

**调用场景：**
在预约界面中处理跨科室预约场景。

**调用入口：**
日程看板中的“跨科室预约”按钮。

**核心入参：**
- clinicZoneId；
- currentDeptId；
- targetDeptId（如已选）；
- resourceId；
- scheduleDate；
- startTime；
- endTime；
- patientId；
- businessDataId。

**核心出参：**
- 是否预约成功；
- 目标预约记录ID；
- 目标科室信息；
- 是否需要刷新当前界面。

**调用后处理：**
- 成功后刷新当前看板及必要的跨科室信息；
- 记录预约日志；
- 如涉及三方交互，需同步写入同步状态表。

### 4.2.2.4.3.4 加号组件调用协议

**调用场景：**
在已满或特殊预约场景下，通过加号组件处理加号预约。

**调用入口：**
日程看板资源列中的加号入口。

**核心入参：**
- resourceId；
- scheduleDate；
- startTime；
- endTime；
- patientId；
- businessDataId；
- reserveMode（正常预约 / 加号预约）。

**核心出参：**
- 是否处理成功；
- 预约记录ID；
- 预约类型或模式；
- 是否需要刷新界面。

**调用后处理：**
- 成功后刷新看板；
- 后端按预约模式写入对应记录；
- 记录日志并保留必要的同步信息。

## 4.2.2.4.4 我方主动通知三方接口

### 4.2.2.4.4.1 场景说明

当护士在界面中取消或修改排班、取消或修改预约，且该业务来源与三方系统有关时，我方需要主动通知三方系统，保证双方状态尽量一致。

### 4.2.2.4.4.2 通知内容

通知内容建议包含：
- 事件类型；
- 资源ID；
- 排班日期；
- 预约或业务标识；
- 操作人信息；
- 操作时间。

### 4.2.2.4.4.3 处理要求

- 回调地址和开关由诊区配置或系统配置统一维护；
- 回调失败时，需写入 `outp_sync_status`；
- 系统需支持后台定时重试；
- 超过最大重试次数后，应标记异常并提示人工处理。

# 4.2.2.5 流程逻辑

## 4.2.2.5.1 设计说明

本节用于说明预约日程管理模块中各类核心业务流程的处理顺序、关键判断点和落库关系，重点描述系统在正向流程、逆向流程以及异常补偿流程中的业务逻辑。

本节不再保留“固定资源通过 cron 自动生成未来可预约数据”的旧方案表述，统一按“外部排班 + 手动补充 + 预约/接诊联动”的当前口径展开。

---

## 4.2.2.5.2 日程看板加载流程

### 4.2.2.5.2.1 流程说明

当用户进入预约日程看板或切换日期、诊区、科室、资源类型等筛选条件时，系统需要重新加载资源、排班、时段明细和预约记录，并按预约类型着色展示已预约数据。

### 4.2.2.5.2.2 处理逻辑

1. 用户选择日期及筛选条件；
2. 系统查询当前条件下的资源信息；
3. 加载对应排班主记录和排班时段明细；
4. 查询对应预约记录；
5. 加载预约类型颜色配置；
6. 前端按资源和时间轴渲染看板；
7. 已预约记录按预约类型颜色展示，可预约时段按可预约状态展示。

---

## 4.2.2.5.3 三方系统推送排班流程

### 4.2.2.5.3.1 流程说明

当三方系统推送排班数据时，系统需要完成排班主记录和排班明细的生成或更新，为预约日程看板提供可用时段基础数据。

### 4.2.2.5.3.2 处理逻辑

1. 接收三方排班请求；
2. 校验必要参数；
3. 根据资源、日期、排班编号判断是新增还是更新；
4. 写入或更新 `outp_resource_sched`；
5. 拆分或更新 `outp_res_sched_detail`；
6. 记录处理结果和操作日志；
7. 供日程看板后续加载使用。

---

## 4.2.2.5.4 护士手动新增日程流程

### 4.2.2.5.4.1 流程说明

当护士基于固定资源或常规日程资源手动新增日程时，系统需要校验资源、日期、时间段等条件，并生成日程记录。

### 4.2.2.5.4.2 处理逻辑

1. 护士点击“新增日程”；
2. 选择资源并填写日期、时间、标题、备注等信息；
3. 系统校验资源是否可用、时间段是否冲突；
4. 校验通过后写入 `outp_schedule_reserved`；
5. 记录操作日志；
6. 返回创建结果并刷新当前看板。

### 4.2.2.5.4.3 说明

若该日程是基于已有排班时段创建，则是否同步更新 `outp_res_sched_detail` 的状态，应根据最终业务规则确定；当前文档阶段应避免将该逻辑写死为唯一处理方式。

---

## 4.2.2.5.5 调用预约组件处理预约流程

### 4.2.2.5.5.1 流程说明

当用户点击可预约时段或已预约记录时，系统通过预约组件处理新增预约、修改预约或取消预约，并将结果回写到我方系统。

### 4.2.2.5.5.2 处理逻辑

1. 用户点击目标时段或预约记录；
2. 前端收集当前资源、时段、业务标识等信息；
3. 调用对应预约组件；
4. 组件完成处理后回传结果；
5. 系统新增、更新或取消 `outp_schedule_reserved` 中对应记录；
6. 按业务规则更新时段状态；
7. 写入日志与必要的同步状态；
8. 刷新看板展示。

---

## 4.2.2.5.6 三方系统推送预约数据流程

### 4.2.2.5.6.1 流程说明

当康复系统或其他三方系统直接推送预约数据时，系统需要完成幂等校验、预约记录写入、医嘱信息关联和处理结果追踪。

### 4.2.2.5.6.2 处理逻辑

1. 接收三方预约推送请求；
2. 使用 `requestId` 进行幂等校验；
3. 写入或更新 `outp_schedule_reserved`；
4. 若请求中包含医嘱信息，则写入 `outp_sched_order_resv`；
5. 写入 `outp_sync_status` 记录同步状态；
6. 写入 `outp_schedule_log` 记录关键处理动作；
7. 返回处理结果。

## 4.2.2.5.7 Check In 接诊关联流程

### 4.2.2.5.7.1 流程说明

当 HIS 完成 Check In 后，系统需要生成接诊记录，并将本次接诊与已有预约、医嘱数据关联起来，为后续业务处理提供统一入口。

### 4.2.2.5.7.2 处理逻辑

1. 接收 HIS Check In 请求；
2. 校验患者与当前就诊信息；
3. 写入 `outpatient_checkin`；
4. 查询并关联对应预约记录和医嘱信息；
5. 写入 `outp_checkin_order`；
6. 记录日志并返回处理结果。

## 4.2.2.5.8 逆流程处理

### 4.2.2.5.8.1 流程说明

逆流程处理用于承接三方取消排班、三方取消预约、三方修改排班，以及我方取消或修改后需要反向通知三方的场景。

### 4.2.2.5.8.2 处理逻辑

#### 1. 三方取消排班
- 接收取消排班请求；
- 判断对应排班是否存在关联预约；
- 若不存在关联预约，则可直接取消或删除排班；
- 若存在关联预约，则应标记待处理状态，并进入后续人工或系统处理流程。

#### 2. 三方修改排班
- 接收修改排班请求；
- 判断影响范围；
- 更新排班及相关展示数据；
- 若影响已有预约，则进入异常处理或通知流程。

#### 3. 三方取消预约
- 接收取消预约请求；
- 根据业务标识定位预约记录；
- 更新预约状态，并按业务规则释放对应时段；
- 记录日志。

#### 4. 我方主动通知三方
- 当护士在界面中取消或修改排班、取消或修改预约时，若涉及三方来源数据，则需向三方发起通知；
- 通知结果写入同步状态表；
- 回调失败时进入重试流程。

## 4.2.2.5.9 幂等、重试与对账处理流程

### 4.2.2.5.9.1 流程说明

当出现三方成功而我方失败、回调失败或双方记录不一致等情况时，系统需通过幂等、重试和定期对账机制降低数据不一致风险。

### 4.2.2.5.9.2 处理逻辑

#### 1. 幂等处理
- `requestId` 作为三方请求唯一标识；
- 若同一 `requestId` 已成功处理，则直接返回已处理结果；
- 若尚未成功处理，则继续执行业务逻辑。

#### 2. 重试处理
- 对失败记录按预设重试策略执行重试；
- 每次重试均更新 `retry_count`、`next_retry_time` 和错误信息；
- 超过最大重试次数后标记为异常，待人工处理。

#### 3. 定期对账
- 系统定期获取三方记录并与我方同步状态进行比对；
- 对于三方有而我方无的记录，按补录或重试逻辑处理；
- 对于状态不一致的记录，按修正流程继续处理。

### 4.2.2.5.9.3 说明

幂等、重试与对账机制是预约日程管理模块的重要保障能力，不仅用于处理三方推送失败场景，也用于支撑后续的异常排查、人工补录和审计追溯。
