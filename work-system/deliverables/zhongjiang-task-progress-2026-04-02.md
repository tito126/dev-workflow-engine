## 1. 问题定义

- **问题名称**：中江病区护士站节点 down 事件——慢接口与三方服务隔离优化
- **现象描述**：病区护士站节点 down，当前收口到费用基础信息相关接口存在明显慢链路风险。
- **影响范围**：核心风险在于高频请求下，外部依赖慢、串行阻塞、无隔离治理可能放大线程占用与节点不稳定问题。
- **当前判断**：这不是一次普通事故分析，而是已经具备继续推进为专项子任务的价值，契合病区护士站研发部围绕性能优化、降本增效、系统稳定性推进后续工作的方向。

- **已确认接口**：`/api/v1/app_inpatient_encounter/inpat_banner_basics_expense/query/by_id`

  - 缺少显式超时 / 熔断 / 线程隔离治理

  - 当前更像是“慢外部依赖拖住请求线程 / 连接池”的级联问题

## 3. 当前判断

- **主因判断**：高频请求路径上，核心余额查询、病案费用汇总、中医补充明细三段远程调用当前串行执行，且没有明确隔离治理，是最值得优先收口的问题。
- **次级放大器**：
  - HTTP 分支风险预计更高
  - 集成方式查询重复且无缓存
  - HTTP 分支存在当前接口未消费的附加查询
- **当前置信度**：
  - 对“问题组合”判断：高
  - 对“线上实际走哪条分支”判断：中低
  - 对“各段耗时占比”判断：中低

## 5. 动作分层

### P0：止血动作

- 第二段 / 第三段异步化并 fail-open
- `(hospitalSOID, transCode)` 集成方式查询加 5~10 分钟缓存

### P1：局部优化

- 跳过 HTTP 分支中当前接口未消费的附加查询
- 优先考虑药占比等纯额外成本调用
- 对非核心空值做兜底，避免次要依赖拖挂主链路

### P2：中期治理

- 统一超时 / 熔断 / Bulkhead 治理
- 按依赖组拆断路器
- 核心查询与增强查询做线程 / 连接池隔离
- 补子调用耗时、超时、降级等可观测性
