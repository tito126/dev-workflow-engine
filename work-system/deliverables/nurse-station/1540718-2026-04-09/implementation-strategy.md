## 1. 当前约束

### 已知事实
- 接口：`/api/v1/execution_aggregate/ipt/cli_order_exec_result/query/by_example`
- 入口：`ExecPlanRestImpl#queryOrderExecPlanResults`
- 数据量级：`EXEC_PLAN` 为**千万级**
- SQL 结构：包含两支查询
  - `EXEC_FLOW_ID` 分支
  - `GOODS_FLOW_ID` 分支
- 两支结果当前通过 `UNION` 合并
- 当前查询时间窗口：2 天

### 强约束
- **业务上不能移除 `GOODS_FLOW_ID` 分支**，因为这是提供给三方的接口能力
- **DBA 不建议继续增加索引**
- 因此方案不能依赖“删掉分支”或“新增索引”作为默认前提

### 已确认的风险点
- `GOODS_FLOW_ID` 分支大概率是最重的扫描来源
- `UNION` 可能带来双分支扫描 + 去重成本
- 可能存在**先全量取数后内存分页**的问题
- 在千万级数据上，盲目并发只会把数据库压力进一步放大

---

## 2. 推荐主方案

### 主方案 A：SQL 结构优化 + 数据库侧分页

这是当前的**首选方案**。

#### 目标
- 不依赖新增索引
- 不移除 `GOODS_FLOW_ID` 分支
- 通过改写查询结构和结果裁剪方式，先把单次查询成本降下来

#### 重点动作
1. **确认 `UNION` 是否可改为 `UNION ALL`**
   - 如果两支结果天然不重叠，改为 `UNION ALL` 可直接减少去重成本
   - 如果存在重复语义要求，则不能强改

2. **把分页前移到数据库侧**
   - 如果当前是先全量查结果再内存分页，必须优先改
   - 在千万级数据下，这一问题的优先级很高

3. **提前缩小双分支扫描范围**
   - 重点看 `GOODS_FLOW_ID` 分支能否在业务条件、时间条件、医院条件上提前裁剪
   - 尽量让结果集在合并前就收敛，而不是先放大后合并

#### 为什么排第一
- 这是最符合当前约束的方案
- 不依赖 DBA 放行新索引
- 不改变三方接口语义
- 比并发更接近根因

---

## 3. 备选方案

### 备选方案 B：时间窗口切片，先顺序拆分

#### 思路
- 既然 2 天窗口已知会触发慢查询，可以按时间片拆成更小范围
- 第一阶段不一定直接并发，可以先**顺序切片**验证单片查询成本是否明显下降

#### 优点
- 不要求删分支
- 不要求加索引
- 在千万级数据下，有机会直接降低单次扫描范围

#### 风险
- 需要额外的结果合并逻辑
- 如果分页逻辑没处理好，可能只是把慢查询拆成多次慢查询
- 如果顺序切片仍慢，最终还是要考虑受控并发

---

### 备选方案 C：受控并发时间切片

#### 思路
- 在主方案 A 无法把单次查询压到目标范围时，再进入该方案
- 对时间窗口切片后，小并发执行，再汇总结果

#### 使用前提
- 已确认 SQL 结构优化空间有限
- 已避免“全量查出后内存分页”
- 已定义线程池、超时、失败片段处理、结果合并规则

#### 风险
- 这是在数据库压力上做换取，不是纯净优化
- 如果并发过高，会明显放大底层压力
- 更适合作为补偿型方案，而不是第一刀

---

## 4. 当前不推荐的方向

### 不推荐 1：直接新增 `GOODS_FLOW_ID` 索引
- 从技术直觉看，这可能有效
- 但当前 DBA 已明确不建议继续加索引
- 所以这不能作为当前默认落地方向

### 不推荐 2：直接删除 `EXEC_PLAN_LINKAGE_ID_FK`
- 目前没有足够的全局使用证据
- 不能为了这个接口就删一个可能被其他链路依赖的索引

### 不推荐 3：跳过 SQL 结构分析，直接上并发
- 这会把“低效查询”并发放大
- 在千万级数据量下风险很大

## 5. 推荐实施顺序

### 第一阶段：最小证据补齐 + 实现准备
1. 精确确认完整 SQL / mapper / 分页实现位置
2. 确认当前是否为内存分页
3. 确认 `UNION ALL` 是否具备语义成立条件

### 第二阶段：首轮代码改动
1. 优先改分页路径（若存在内存分页）
2. 优先改 `UNION` 组织方式（若语义允许）
3. 优先做 SQL 结果集前置收敛

### 第三阶段：必要时再上时间切片
1. 先顺序切片
2. 不够再小并发切片
3. 明确线程数、超时、异常片段处理
