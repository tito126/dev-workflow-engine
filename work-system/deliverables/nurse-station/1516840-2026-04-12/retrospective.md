# 复盘 - 1516840

- 复盘阶段：`retrospective`
- 任务标识：`1516840-2026-04-12`
- 复盘触发点：完成一版实现并与产品演示后，出现“位置可接收、文案不可改写”的明确反馈

## 一、这次真正被验证出的结论

### 1. 正确的不是“我改写得更顺”，而是“产品文案本身就是需求边界”
本轮最关键的反馈不是样式、不是位置，而是：
- 产品**可以接受提示位置调整**
- 产品**不接受对其原始文案的改写**

这说明此类“说明文案优化”任务里，真正的边界不是“意思对就行”，而是：
- 如果产品已经给出正式文案，**原文本身就是需求资产**
- 实现阶段默认不应自行润色、提炼、改写或压缩

### 2. 位置和文案是两套独立验收维度
这次如果只看代码，会误以为任务已基本完成。
但产品反馈把验收拆成了两层：
- **位置层**：可接收
- **文案层**：不可改写，需回到原文

后续类似任务不能再把“文案和位置”混成一次模糊通过，而应在 plan / verification 里分开写清。

### 3. “静态说明方案”方向是对的，但“擅自重写文案”方向是错的
- 方向正确：不做后端配置化，先在页面层用静态说明块承接
- 执行偏差：我把产品给定文案改成了自己的总结版，导致实现后又要回退一轮

所以这次不是方案错，而是**实现约束不够硬**。

## 二、对 nurse-station skill 的可复用改进

### 1. 文案类任务要新增一个硬检查点
后续当任务涉及：
- 说明文案
- 提示文案
- 帮助文本
- 注意事项
- 配置页描述

必须显式判断：
- 当前文案是否已经由产品 / 需求提供正式版本
- 如果有正式版本，是否允许实现者改写

默认规则应改为：
- **有正式文案时，默认不允许改写，只允许原文落地**
- 若要改写，必须拿到用户或产品明确授权

### 2. verification 要把“位置通过”和“文案通过”拆开
以后在 verification / review-gate 里，文案类任务至少要单列：
1. 位置 / 承载方式是否通过
2. 文案内容是否逐字符合要求
3. 是否存在示例缺失、条目缺失、编号缺失

### 3. implementer 阶段要补一个“文案保护”约束
建议未来在 implementer skill 或其派发提示里加入：
- 如果输入里已经给出完整文案，默认视为受保护文本
- 不得为了“更顺”“更简洁”“更像用户话术”而自行重写
- 允许的修改仅限：换行、缩进、编号样式、承载位置调整

## 三、对 YAML 机制的结论

这次复盘顺手也验证了另一件事：
- 多仓扫描是否规范，不应再依赖记忆
- YAML 路由必须前置，且 `draft` 状态必须硬阻断

但 YAML 只解决“扫哪里”的问题，不解决“文案能不能改”的问题。
所以后续 skill 体系至少要分两层：
1. **repo-routing YAML**：约束扫描 / 仓库扩扫
2. **任务约束检查**：约束文案、算法、边界、是否允许改写

## 四、这次任务当前应如何理解

当前最准确的任务状态不是“已收口”，而是：
- 已验证“位置调整”方向成立
- 已验证“前端静态说明块”方案可行
- 但文案层未通过产品验收
- 任务应回到 implementer，用产品原文替换当前改写文案后，再重新做 verification

## 五、可沉淀的后续规则

1. **文案类需求默认不改写产品原文**
2. **位置验收与文案验收必须分开**
3. **产品给了编号案例时，不能擅自压缩成概括性示例**
4. **YAML draft 只能停，不能继续多仓推进**
5. **即使方案方向正确，只要文案边界被破坏，也不能算需求完成**
