# 4.2.2.2.1 核心数据流转图（正文版）

## 4.2.2.2.1.1 图示说明

预约日程管理模块的核心数据流转，建议按“来源层—处理层—数据层—使用层”进行分层表达。

其中：
- **来源层** 用于描述业务数据从哪里进入本系统，包括三方排班系统、三方预约系统、护士端手动新增日程以及后台固定资源配置。
- **处理层** 用于描述系统内部对排班接收、预约接收、手动新增日程、幂等重试、日志追溯等能力的处理动作。
- **数据层** 用于描述各核心表承接的数据边界，不再将数据表与业务动作混画在同一层级。
- **使用层** 用于描述核心数据最终如何支撑日程看板展示、预约/日程状态展示以及预约记录与变更追溯等业务使用场景。

通过分层表达，可以清晰区分“谁产生数据”“系统如何处理数据”“数据最终落到哪些表”“这些数据被谁使用”四类问题，避免旧版图中功能模块、处理动作和数据表混杂在一起导致的表达混乱。

## 4.2.2.2.1.2 核心流转关系说明

### 1. 排班数据流转

三方排班系统负责向本系统推送排班数据。系统接收到排班请求后，对资源、日期、时段等关键信息进行校验，并通过“排班接收与落库”处理链路完成排班数据入库。

其中：
- 排班主记录写入 `outp_resource_sched`；
- 排班时段明细写入 `outp_res_sched_detail`；
- 排班处理过程中的关键动作统一写入 `outp_schedule_log`。

排班主表和排班明细表共同支撑日程看板中的资源排班展示、时段展示以及可预约时段识别。

### 2. 预约数据流转

三方预约系统负责向本系统推送预约数据。系统接收到预约请求后，通过“预约接收与落库”处理链路完成预约记录、医嘱关联和同步状态记录。

其中：
- 预约记录统一写入 `outp_schedule_reserved`；
- 如预约数据中包含医嘱信息，则同步写入 `outp_sched_order_resv`；
- 如涉及幂等控制、失败重试、异常补偿等处理需求，则同步写入 `outp_sync_status`；
- 关键处理过程统一写入 `outp_schedule_log`。

预约数据写入完成后，可用于支撑日程看板中的已预约状态展示、预约类型展示以及预约记录追溯。

### 3. 固定资源配置流转

后台固定资源配置仅承担资源基础定义的维护职责，不再承担自动生成未来排班的职责。管理人员在后台维护固定资源信息后，系统将资源定义写入 `outp_fixed_resource`，并结合诊区基础配置表 `outp_clinic_zone_config` 共同支撑日程看板展示和护士端手动新增日程时的资源选择。

固定资源在本设计中仅作为资源定义和业务归属对象使用，不扩展规则模式、规则版本、cron 配置、自动生成窗口等旧方案字段，也不再基于固定资源自动生成未来排班数据。

### 4. 护士手动新增日程流转

当护士在日程看板中手动新增日程时，系统通过“手动新增日程处理”链路完成资源校验、时间校验和日程落库。该场景下，手动新增的日程记录仅写入 `outp_schedule_reserved`，用于形成系统内的手动新增日程数据。

本场景不联动更新 `outp_res_sched_detail`，即护士手动新增日程不占用、不修改排班明细表中的时段状态。

同时，手动新增日程的关键处理动作统一写入 `outp_schedule_log`，用于后续变更追溯和操作审计。

### 5. 幂等、重试与对账补偿流转

幂等、失败重试、异常补偿、对账修正等能力不属于独立业务来源，而属于贯穿排班推送、预约推送、逆流程处理等场景的横向支撑能力。

系统通过 `outp_sync_status` 统一记录请求唯一标识、处理状态、失败原因、重试次数、下次重试时间等信息，并在需要时驱动补偿处理和人工介入。

涉及补偿处理、异常修正、重试执行等过程中的关键动作，仍需统一写入 `outp_schedule_log`，保证全链路可追溯。

### 6. 日志与追溯流转

`outp_schedule_log` 是预约日程管理模块的统一操作日志承接表，用于记录排班推送、预约推送、手动新增日程、预约修改、预约取消、异常重试、补偿修正等关键业务动作。

`outp_sync_status` 则用于承接跨系统同步状态、幂等控制、失败重试、异常补偿等系统支撑信息。两者共同构成预约日程管理模块的可追溯能力基础。

在使用层中：
- `outp_resource_sched` 与 `outp_res_sched_detail` 主要支撑日程看板展示；
- `outp_schedule_reserved` 主要支撑预约/日程状态展示；
- `outp_sched_order_resv`、`outp_schedule_log`、`outp_sync_status` 主要支撑预约记录查询、日志追溯和异常排查。

## 4.2.2.2.1.3 设计边界说明

为保证本章节设计口径统一，核心数据流转图及其配套正文明确不再包含以下旧方案内容：

1. 基于固定资源规则自动生成未来排班；
2. 固定资源 cron 配置、规则模式、规则版本等扩展设计；
3. 基于 `rule_version` 的排班重建逻辑；
4. 特殊资源（N 天后日程）自动生成方案；
5. 将护士手动新增日程与排班明细状态强绑定的设计口径。

本章节仅保留当前已确认的业务主链路，即：
- 三方排班推送；
- 三方预约推送；
- 后台固定资源配置；
- 护士手动新增日程；
- 幂等/重试/对账补偿；
- 日志与追溯。

## 4.2.2.2.1.4 设计结论

预约日程管理模块的核心数据流转，应围绕“排班、预约、手动日程、支撑能力”四类对象展开：

- 排班数据通过 `outp_resource_sched` 和 `outp_res_sched_detail` 承接；
- 预约和手动新增日程统一通过 `outp_schedule_reserved` 承接；
- 医嘱预约关联通过 `outp_sched_order_resv` 承接；
- 跨系统状态控制通过 `outp_sync_status` 承接；
- 全链路关键操作通过 `outp_schedule_log` 承接。

采用该分层结构后，可以将来源、处理、落库和使用边界清晰拆开，既便于后续画图，也便于后续章节在接口、流程逻辑和时序图中保持一致口径。
