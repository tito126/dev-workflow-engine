# K8s 日志拉取 SOP

适用范围：
- `乐山市人民医院`
- `桐乡市卫生健康局`
- `复旦大学附属妇产科医院（红房子）`
- 以及其他通过 `Grafana / Loki` 拉取日志的 K8s 环境

目标：
- 当用户只用自然语言表达目标，例如：`拉取桐乡最近10分钟日志`
- 系统应按固定顺序补全中间链路，最终产出日志、分析结果与报告

## 一、默认流程

标准顺序：
1. 识别医院
2. 判断是否需要补问集群
3. 打开或创建 Grafana 代理通道
4. 验证代理地址可达
5. 验证 Grafana health
6. 执行第一阶段拉取
7. 本地 analyze 生成 digest 和代表 traces
8. 执行第二阶段 fetch2 拉完整链路
9. 重新 analyze 生成 final digest
10. 按需生成 HTML 报告

## 二、必须补问的场景

### 1. 桐乡市卫生健康局

桐乡是多集群环境，必须先问：
- `第一集群`
- `第二集群`
- `第三集群`

禁止：
- 默认猜集群
- 直接按上次集群执行
- 跳过集群确认直接开拉

## 三、Grafana 入口处理原则

### 1. 不直接迷信配置中的地址

配置文件中的地址，只能视为候选入口，不等于当前一定可用。

### 2. 标准入口应优先是“已验证可达的代理地址”

执行时应优先采用：
- 已通过代理打开
- 已验证 HTTP 可访问
- 已验证 Grafana health 正常

的入口作为标准入口。

### 3. 三类入口要区分

- **配置入口**：配置文件中的候选地址
- **可达入口**：当前环境里实测可以访问的地址
- **标准入口**：本次执行实际应使用的地址

执行时应始终以“标准入口”为准。

## 四、代理与验证顺序

### 1. 打开 Grafana 代理通道

通过 `wxp-tunnel / lockjaw` 为目标集群的 Grafana 节点创建 TCP 通道。

### 2. 验证代理地址可达

至少验证：
- 根地址是否返回 `200` 或可接受响应
- Grafana health 是否可访问

### 3. 只有验证通过，才进入日志拉取

若代理地址不可达：
- 不继续盯本地回环端口打转
- 优先判断是否创建了错误通道 / 代理服务本身不可用 / 目标节点不对

## 五、执行链路

### 1. 第一阶段

拉取：
- `ERROR | 业务处理耗时`

输出：
- 原始日志文件
- 第一阶段 digest
- 第一阶段代表 traces 文件

### 2. 第二阶段

针对代表 traces：
- 拉取完整链路日志
- 追加到原始日志文件中

### 3. 最终分析

重新 analyze，产出：
- final digest
- 按需生成 HTML 报告

## 六、用户输入与系统责任分工

### 用户负责
- 表达目标，例如：`拉取桐乡最近10分钟日志`
- 在必须补问时回答关键参数，例如桐乡集群

### 系统负责
- 识别医院与服务
- 判断是否需要补问
- 打开 Grafana 代理通道
- 验证标准入口
- 跑完整拉取与分析链路
- 产出报告与结果文件

## 七、失败信号与默认排查分支

### 信号 1：本地回环端口不通

不要直接停在这里。
默认动作：
- 检查是否存在可用代理地址
- 检查 Grafana 代理通道是否真的创建成功
- 检查应使用的是不是远端代理地址而不是本地回环端口

### 信号 2：Grafana 地址可访问，但查询失败

默认动作：
- 验证 `/api/health`
- 检查 datasource 是否正确
- 检查 app 名称是否正确
- 检查时间窗是否合理

### 信号 3：links 里有映射记录，但实际访问失败

默认动作：
- 不把映射记录直接当成活入口
- 重新验证该入口是否真的可访问
- 必要时重新创建代理通道

## 八、演示前的最小预演要求

如果任务可能用于答辩、飞书演示、现场展示，必须至少预演一次完整链路：
- 代理打开
- Grafana 可达
- 第一阶段成功
- 第二阶段成功
- 报告产出成功

不能只验证其中一两个步骤就默认整体可演示。

## 九、产物清单

标准产物通常包括：
- `*.log`
- `*_digest.json`
- `*_digest_traces.json`
- `*_final_digest.json`
- `*_report.html`

其中：
- `final digest` 和 `HTML 报告` 更适合演示
- `log` 和 `traces` 更适合排查与复盘
