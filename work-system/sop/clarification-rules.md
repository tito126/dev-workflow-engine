# 信息不明确时的澄清规则

## 目的

当用户新增专项、补充进展或发出不够明确的指令时，先用少量关键问题补齐信息，再决定是否正式入库。目标是既不漏记，也不误记。

## 基本原则

- 只问必要问题，不连发一串盘问。
- 能根据上下文合理判断的，不额外追问。
- 会影响归档、提醒、专项归属、优先级判断的信息，优先确认。
- 如果只是轻微模糊，但不影响临时记录，可以先入临时池，后续再补。
- 默认按自然语言和语义理解触发，不要求用户记固定关键字或指令。
- 用户显式表达如“记录一下”“归到专项”“先别落”“这是一条规则”时，按更强信号处理。
- 如果一句话可能落入多个层级或多个载体，先用一句短问确认，不擅自定稿。
- 规则优先约束助手的判断与路由，不优先增加用户操作负担。
- 不确定时优先轻落点：先入 `memory`、临时池或待验证，而不是直接升格为正式规则或专项。

## 一句话方向型需求的处理规则

如果用户只给出一句较大的方向或概念，而不足以支撑后续提醒、触发词和持续推进，不要直接把它当成明确专项或成熟方案。

例如：
- 做个转写 skill
- 搭一个任务上下文机制
- 做个 Cherry Studio agent 壳

这类情况优先反问，先确认用户意图，再决定是记成灵感、临时事项，还是正式专项。

推荐优先问：
- 你现在是想先记一个方向，还是准备正式推进？
- 这件事更像 skill、专项，还是产品壳设想？
- 你最想解决的核心问题是什么？

## 哪些场景需要澄清

### 1. 新增专项

如果用户说“建个专项”但信息不足，优先确认：
- 这个专项的标准名称是什么？
- 它的核心目标是什么？
- 当前处于什么阶段？
- 近期最关键的下一步是什么？
- 有没有目标时间或关键里程碑？

### 2. 更新专项进展，但归属不明

如果用户说“这个今天推进了很多”但没说是哪个专项，优先确认：
- 这是哪个专项？
- 本次推进最关键的变化是什么？
- 是否会影响下一步、里程碑或风险？

### 3. 风险或阻塞描述不清

优先确认：
- 风险影响的是哪个专项？
- 主要影响进度、范围，还是价值？
- 这是已发生的问题，还是预警信号？

### 4. 提醒事项不清

优先确认：
- 你希望我什么时候提醒？
- 这条提醒关联哪个专项或事项？
- 是一次性提醒还是后续持续跟进？

### 5. 价值表述不清

优先确认：
- 这个专项主要想解决什么问题？
- 最重要的收益是什么？
- 谁会直接受益？

## 推荐提问方式

尽量简短、像协作，不要像审表。

### 新建专项时
- `这个专项我先帮你建档。还差两个关键信息：标准名称和核心目标，给我一句就行。`
- `这个可以作为专项。你再补我两个点：当前阶段、最近下一步。`

### 专项归属不清时
- `这个我先接住。它是归到哪个专项下面？`
- `这条进展我建议入专项档案。你确认一下是哪个专项。`

### 提醒不清时
- `这条要加提醒的话，你希望我什么时候提醒你？`
- `这个提醒是一锤子提醒，还是后面要持续盯？`

### 风险不清时
- `这个我倾向于记成风险。它主要影响哪一块：时间、范围还是可行性？`
- `这条风险先归到哪个专项更合适？`

## 临时兜底规则

如果内容明显重要，但暂时缺少一两个字段，又不适合来回追问：
- 先放入临时工作池
- 状态标记为 `待补充`
- 在后续对话中补齐再转正式档案

## 不要过度提问

以下情况尽量不要追问太多：
- 用户只是想先记一下
- 当下是快速沟通场景
- 问太多会打断工作流
- 缺失信息不会影响先入临时池

## 强触发直达规则

以下表达默认属于强触发，不应先退化成普通对话澄清：
- `今日聚焦`
- `今天聚焦`
- `今天重点`
- `今天先做什么`
- `排一下今天优先级`
- `今日总结`
- `今天总结`
- `收个尾`

处理要求：
- 遇到上述表达，优先直接执行对应流程
- `今日聚焦` 类请求，先读取 `work-system` 中与 daily 判断相关的输入源，再直接生成当天 `Daily Focus`
- `今日总结` 类请求，先读取当天推进、项目变化和临近提醒，再直接生成当天 `Daily Summary`
- 只有在生成正式结果所必需的关键信息明显缺失时，才允许补一句短澄清

特别约束：
- 不要因为“想先多收一点信息”就把强触发请求降级成普通聊天
- 不要只回复引导语而不落档
- 对这类请求，正式文件落档本身就是默认动作，不是额外步骤

## 推荐执行顺序

当指令不明确时，按这个顺序判断：
1. 是否属于强触发并应直接执行正式流程
2. 能否直接理解并正式入库
3. 不能正式入库时，能否先放临时池
4. 只有在目标归属、提醒时间、专项定义等关键点缺失时再追问
