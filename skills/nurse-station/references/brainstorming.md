# brainstorming — 需求澄清

把一个原始的护士站事项转成可持续推进的工作单元，而不是一次性聊天回答。

## 目标

本阶段的核心不是"怎么改代码"，而是先回答：

> 这个任务现在是否已经具备进入持续执行流的资格？

## 产出

至少形成以下内容：

1. 任务类型（功能扩展 / 稳定性修复 / 易用性优化 / 债务治理 / 探索型事项）
2. 业务背景
3. 核心目标 + 明确的非目标
4. 范围与影响模块
5. 成功标准（可验证的锚点）
6. 允许改动层级 / 禁止改动层级
7. 建议验收方式
8. 风险 / 模糊点
9. 外部依赖 / 前置条件
10. 任务级别（light / medium / heavy）
11. 推荐执行路径
12. 是否可进入计划 / 是否可进入代码执行

## 强制检查项

在允许任务进入下一阶段前，必须检查：

- 业务意图是否清晰
- 目标场景是否清晰
- 模块 / 页面 / API 是否足够明确
- 验收条件是否足够明确，能用于后续验证
- 方案是否依赖第三方 / 外部团队 / 外部系统配合？依赖主体是否已明确到可执行？
- 如果依赖方一旦配合就能直接规避本需求，本需求是否仍然成立？
- 当前要推进的是正式优化，还是依赖未明期间的临时兜底？
- 本轮允许改动的层级是哪一层
- 需求分析 / PRD 是否已指向具体实现文件？如果是，这些文件是"已从 API 入口验证过"还是"仅基于代码结构推测"？
- 如果任务涉及"给打印/输出 BO 增加字段"，是否已追问目标 BO 是否是最终响应链的末端？
- 是否存在 BeanUtils.copyProperties 导致字段静默丢弃的风险？

## 文案类任务额外检查

当任务涉及注意事项 / 提示文案 / 帮助说明 / 配置说明 / 页面描述文本时：

1. 当前文案是否已由产品 / 需求给出正式原文？
2. 实现阶段是否允许对原文改写、压缩、润色、概括？
3. 验收时是否要把"位置通过"和"文案通过"拆开判断？

默认规则：如果产品 / 需求已给出正式原文，**默认视为受保护文本**，未经明确授权不允许改写。

## 任务级路由

- **light**：小范围、本地化、足够清晰 + 改动目标已从 API 入口独立验证。如果改动目标仅来自需求分析文档建议、未经独立验证，不应判为 light。
- **medium**：边界可控，但需要定位 / 窄范围实现 / 明确验证。
- **heavy**：多阶段、高不确定性、值得使用运行时跟踪。

## 顺序规则

本阶段是默认的第一阶段。不要因为用户已给了需求号、仓库路径、执行器选择就直接跳过。

只有当用户明确说"已过前置澄清"时，才允许跳过本阶段。

## 集成

完成后：
- 如果还不够清楚，停下来追问
- 如果已经足够清楚，流转到 `references/planning.md`
- 如果涉及代码扫描，必须先确认 YAML 就绪状态
