# verification — 结果验收

对照需求和成功锚点做验收。验证产出的核心价值不仅是"通过/不通过"，还在于为后续 review-gate 和用户交付提供可直接复用的验证证据。

## 核心规则

验证阶段不允许猜测验收依据。必须显式区分三件事：

1. **代码是否完成**
2. **需求是否满足**
3. **效果是否已验证**

这三件事可以同时为真，也可以只成立其中一部分，不能混写成一个笼统的"已完成"。

## 文案类任务额外要求

如果任务包含说明文案、提示文案、帮助文本或产品给定原文，verification 必须拆开检查：

- 位置 / 承载方式是否通过
- 文案内容是否按原文落地
- 示例 / 编号 / 条目是否完整
- 是否出现"位置通过但文案不通过"的情况

只要产品要求保留原文而实现里发生了改写，就不能判定"需求完成"。

## 验证清单

### 需求匹配
- 实现是否匹配已澄清的业务目标
- 是否解决了目标场景，而不是旁支场景
- 是否遵守了非目标边界
- 编码前定义的验收检查点是否被满足
- 若前序阶段已产出成功锚点，是否逐条对照

### 技术匹配
- 参数映射是否被正确保留
- 目标文件 / 模块是否与计划一致
- 是否存在明显回归风险
- 修改的 BO/DTO 是否确认在目标 API 的响应链中
- 是否存在 BeanUtils.copyProperties / BeanMapper 等自动映射环节导致字段被静默丢弃的风险

### 证据等级
- **A**：真实环境 / 真实样本 / 实测结果
- **B**：代码证据 / 静态分析 / 结构化 diff
- **C**：业务口头确认 / 聊天确认

如果只拿到 B / C 级证据，不要把结论写成"效果已验证"。
