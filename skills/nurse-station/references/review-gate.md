# review-gate — 正式评审

把正式评审拆成闸门，按正确顺序执行。评审产出的核心价值不仅是"通过/不通过"，还在于形成可沉淀的评审结论和可复用经验。

## 闸门顺序

### 闸门 0：编码前需求匹配
- 目标场景是否足够明确
- 页面 / 模块范围是否足够明确
- 摆放位置 / 交互预期是否足够明确
- 范围内 / 范围外边界是否足够明确
- 是否已具备后续验证可用的具体验收检查点

如果闸门 0 失败：不进入实现，返回 brainstorming 或 planning。

### 闸门 1：实现后需求匹配
- 变更是否解决了被请求的场景
- 是否保留了已约定的交互模型
- 是否遵守了范围内 / 范围外边界
- 是否引入了需求中没有要求的内容
- 场景限制是否正确
- 结果是否匹配编码前定义好的验收锚点
- 实现所修改的文件是否在目标 API 的实际调用链中
- 文案类任务里，是否出现"位置对了但原文被改写"的情况

如果闸门 1 失败：**不启动闸门 2**，返回 implementer 或 planning。

### 闸门 2：代码质量 / 变更风险
- 实现是否局部化，且没有过度扩张
- 参数映射 / 条件处理是否安全
- 目标文件是否与计划预期一致
- 是否存在明显的可维护性或回归风险
- 如果涉及 BeanUtils.copyProperties / BeanMapper 等自动映射，新增字段是否在目标类中存在

## 证据等级

- **A**：真实环境 / 真实样本 / 实测结果
- **B**：代码证据 / 静态分析 / 结构化 diff
- **C**：业务口头确认 / 聊天确认

若当前只有 B / C 级证据，可以给出"代码可收口"，但不能宣称"效果已验证"。
