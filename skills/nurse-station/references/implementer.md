# implementer — 代码实现

在范围已清楚后做有边界的代码修改。实现产出的核心价值不仅是"改了代码"，还在于输出后续 verification / review-gate 可直接复用的结构化结果。

## 前提

- 需求已澄清
- 任务号已确定
- 基线分支与 worktree 已准备好
- 可能变更的文件已知，或已完成 locator
- 验证方式已识别
- YAML 已存在且 status=ready

如果这些前提不满足，退回对应阶段。

## 规则

- 优先做最小且聚焦的改动，而不是顺手清理一大片
- 不扩大范围：如果发现额外问题，除非用户要求，否则不顺便吸收到本次改动里
- 文案类任务默认不改写产品原文
- 如果任务涉及"给 BO/DTO 增加字段"，编码前必须确认该 BO 是目标 API 响应链中的实际参与者：
  - locator 阶段已从 API 端点追踪过调用链 → 直接复用 findings
  - 从 Controller URL 反向追踪到该 BO → 可接受
  - 仅因为需求分析文档建议该 BO → 不可接受，必须先做一轮 API 追踪
- 如果需求分析文档建议的文件不在实际 API 链路中，必须停下来报告偏差
- 如果在实现过程中出现失败模式或结构性冲突，保留为运行时证据，不要只留在聊天里

## 执行载体

优先级：
1. ACP opencode（优先）
2. exec opencode（用户确认后的降级）
3. 主控直接改码（仅 light 任务或用户明确要求）

若 ACP 阻塞（backend unavailable / timeout / empty output / relay 异常），先报阻塞，等用户确认后再决定。

## 产出

```text
### 实现报告
- 已实现目标：
- 运行时路径：
- 已修改文件：
- 实际改动摘要：
- 未改动部分及原因：
- 已执行验证：
- 风险 / 不确定性：
- 是否可进入评审：
```
