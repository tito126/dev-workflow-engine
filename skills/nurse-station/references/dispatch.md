# dispatch — 子任务派发

定义主控如何把工作派发给执行器（ACP opencode / exec opencode 等），同时避免主控自己吞掉实现工作，或在多个阶段之间反复做人肉转发器。

## 核心原则

主会话是 controller，不是全能执行者。

## 派发规则

- 直接传递任务文本，不要指望执行器自己重新发现全部上下文
- 尽量一次性传足可稳定复用的上下文，不要依赖后续补锅式追加
- 显式传递：仓库路径、任务号、worktree 路径、目标、范围、成功锚点、输出格式
- 如果输入里已包含产品 / 需求给出的正式文案，要显式告诉子执行器该文案是否受保护
- 保持每个执行器聚焦于单一角色（locator / implementer / verifier）
- 结构化输出要求

## 执行载体选择

| 条件 | 载体 |
| --- | --- |
| 任务简单、改动量小、不需要外部工具 | direct edit |
| 需要代码定位 / 分析 / 实现，ACP 可用 | ACP opencode |
| 需要代码定位 / 分析 / 实现，经用户确认后允许降级 | exec opencode |
| 用户明确指定用某个执行器 | 用户指定 |

## ACP 阻塞处理

若 ACP 出现 backend unavailable / timeout / empty output / relay 异常 / child 有落盘但主会话无有效回传：
1. 先汇报阻塞
2. 等待用户确认是否降级到 exec opencode
3. 未获用户确认前，不得主会话直接接管代码分析或改码

## 反模式

不要：
- 默认让 controller 自己做完所有代码分析和实现
- 发送"分析整个仓库"这类过宽 prompt
- 在范围仍模糊时，把定位和编码合成一个任务
- 仅凭 implementer 输出就宣告完成
- 把 ACP 只当成一次性命令通道，而不利用其减少上下文重复的价值
