# dispatch — 执行器派发与交接

定义主控如何把工作整理成可交给执行器的结构化输入，同时避免主控自己吞掉实现工作，或在多个阶段之间反复做人肉转发器。

## 核心原则

主会话是 controller，`codex` / `opencode` / `cc` 等编码工具是默认执行载体。

## 派发规则

- 直接传递任务文本，不要指望执行器自己重新发现全部上下文
- 尽量一次性传足可稳定复用的上下文，不要依赖后续补锅式追加
- 显式传递：仓库路径、任务号、目标、范围、成功锚点、输出格式
- 如果输入里已包含产品 / 需求给出的正式文案，要显式告诉执行器该文案是否受保护
- 保持每个执行器聚焦于单一角色（locator / implementer / verifier）
- 结构化输出要求

## 执行载体选择

| 条件 | 载体 |
| --- | --- |
| 需要生成标准执行输入 | `codex` / `opencode` / `cc` |
| 用户明确指定某个编码工具 | 按用户指定 |

## 执行器异常处理

若执行过程中出现以下情况：
- 工具未启动 / 未正确进入指定仓库目录
- 返回空结果、只给过程不给结论
- 输出与任务范围明显不符
- 只说改了代码，但没有文件 / 验证 / 风险摘要

处理顺序：
1. 先标记为“执行结果不完整”
2. 回退到 planning / locator / implementer 中缺口最大的阶段
3. 补齐结构化输入后，再重新投喂执行器
4. 未补齐前，不得把这类结果当作完成证据

## 反模式

不要：
- 默认让 controller 自己做完所有代码分析和实现
- 发送“分析整个仓库”这类过宽 prompt
- 在范围仍模糊时，把定位和编码合成一个任务
- 仅凭 implementer 输出就宣告完成
- 把执行器当成黑箱，不校验它是否真的基于指定仓库目录和范围工作
