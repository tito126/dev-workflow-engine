# 护士站代码定位

先定位，不实现。定位产出的核心价值不仅是"找到了文件"，还在于输出后续 implementer 可以直接复用的 findings，避免定位结论只在聊天里存在一瞬间就消失。

## 目标

产出一份聚焦的代码定位结果，让实现者可以在尽量少重新摸索的情况下开始工作。

## 必需输入

- 仓库路径
- 目标模块或包
- 需求摘要
- 场景约束
- 已知关键词或业务术语

若前序 brainstorming 或 planning 已产出 shared context summary，优先直接复用，而不是重新从零推断搜索范围。

## 职责

你负责：
- 找到可能的入口文件
- 识别相关组件、钩子、状态存储、配置与接口映射
- 解释当前行为是如何拼装出来的
- 列出可能需要改动的文件
- 暴露风险和未解决问题
- 当任务复杂时，把结果组织得足够结构化，以便纳入运行时发现记录

你不负责：
- 改代码
- 做大范围重构
- 在缺乏证据的情况下宣称实现可行

## 搜索策略

1. 先收窄到目标仓库和目标包 / 模块。
2. 用业务词和技术变体做搜索。
3. 只阅读最相关的文件。
4. 需要时，从界面入口一路跟到参数转换和请求层。
5. 当变更面已经足够清楚，可以支持实现规划时就停止。

## 对 ACP 执行的特殊要求

当本阶段由 `ACP opencode` 承接时：
- controller 应把 planning 产出的 shared context summary 和目标模块直接作为派发输入
- locator 的输出应默认按结构化 findings 格式组织
- 若定位涉及多文件链路追踪，优先在一个 ACP session 里连续推进，而不是分段重喂上下文
- 不要把 ACP 只当成搜索工具，应利用其持续会话能力做多轮递进式分析

## 输出模板

### 定位结果
- 仓库：
- 模块：
- 运行时路径：
- 需要更新的发现章节：
- 可能入口文件：
- 关键关联文件：
- 当前行为拼装方式：
- 可能改动文件：
- 风险：
- 未解决问题：

### 可复用产物
- 定位结果应默认充当 implementer 的共享输入
- "可能改动文件"和"当前行为拼装方式"应供 implementer 直接当切入点
- "风险"和"未解决问题"应供 verification 当检查起点
- 如果任务有 runtime 路径，定位结果应写入 findings 而不是只留在聊天里

## 反模式

不要：
- 在没有模块边界的情况下扫描整个仓库
- 还没给出文件证据就直接跳进实现建议
- 把一次字符串命中当成入口点已证实
- 掩盖不确定性
- 把定位结论只当聊天回答，不沉淀为后续可复用的 findings

## 集成关系

在 `nurse-station-implementer` 之前使用。
如果已有运行时任务，定位结果不应只留在聊天里，而应组织成可纳入运行时发现记录的结构。
自然应与 `nurse-station-writing-plans` 配套使用。
当选择 `opencode` 做定位时，优先走 `ACP opencode`，若 ACP 不可用或本地补丁失效则降级到裸 `exec opencode`。
完整的阶段顺序和产物落地约定，见 `nurse-station-orchestrator`。
