# 护士站代码定位

先定位，不实现。定位产出的核心价值不仅是"找到了文件"，还在于输出后续 implementer 可以直接复用的 findings，避免定位结论只在聊天里存在一瞬间就消失。

## 目标

产出一份聚焦的代码定位结果，让实现者可以在尽量少重新摸索的情况下开始工作。

## YAML 前置配置（强制）

在开始任何扫描前，先读取工作区文件：
`work-system/config/nurse-station-repo-routing.yaml`

执行规则：
1. 在开始任何扫描前，先检查 YAML 是否存在且 `status=ready`。
2. 用户明确给了仓库路径时，可把该路径作为首扫根候选，但不能替代 YAML 就绪校验。
3. 如果 YAML 不存在：不要在 locator 阶段自行猜内容，应回退到 orchestrator，由它创建 `draft` 模板，然后停下要求用户维护。
4. 如果 YAML 存在但 `status` 不是 `ready`、根路径为空、仍是占位值、关键词路由缺失，或无法确定扩扫目标，则必须停下，让用户先维护 YAML。
5. `status=draft` 时，不允许做“先扫一个仓看看”“先做一轮轻量定位”这类侥幸推进。
6. 不允许依赖记忆、历史对话、长期经验去“猜”前端仓或其他仓库位置。
7. 定位结果中必须显式记录：实际扫描了哪些根、首扫根来源于哪里（用户 / YAML）、为什么发生扩扫。

## 必需输入

- 仓库路径
- 目标模块或包
- 需求摘要
- 场景约束
- 已知关键词或业务术语

若前序 brainstorming 或 planning 已产出 shared context summary，优先直接复用，而不是重新从零推断搜索范围。

## 职责

你负责：
- 找到可能的入口文件
- 识别相关组件、钩子、状态存储、配置与接口映射
- 解释当前行为是如何拼装出来的
- 列出可能需要改动的文件
- 暴露风险和未解决问题
- 当任务属于 SQL / 性能优化时，整理需要向用户确认的现场业务问题，而不是只给技术猜测
- 当任务复杂时，把结果组织得足够结构化，以便纳入运行时发现记录

你不负责：
- 改代码
- 做大范围重构
- 在缺乏证据的情况下宣称实现可行
- 在 SQL / 性能优化任务里，未经过用户确认就直接把候选方案升级成代码改动

## 搜索策略

0. API 端点追踪（最高优先级）
   - 如果用户或需求中给出了 API 端点 / Controller URL / 接口路径，必须优先从该入口开始追踪
   - 追踪链路：Controller → Service → Mapper/Repository → BO/DTO
   - 追踪目标是确认最终响应对象是什么，而不是只找中间 BO
   - 如果需求分析文档指向的文件与 API 追踪结果不一致，以 API 追踪结果为准
1. 先收窄到目标仓库和目标包 / 模块。
2. 用业务词和技术变体做搜索。
3. 只阅读最相关的文件。
4. 需要时，从界面入口一路跟到参数转换和请求层。
5. 当变更面已经足够清楚，可以支持实现规划时就停止。
6. 如果首扫根内只命中后端链，但任务明显是页面 / 文案 / 交互类需求，只能按 YAML 中配置的候选前端根做定向扩扫，不能全盘扫。
7. 任何扩扫都要记下“为什么扩、扩到哪里、排除了哪些根”。

## SQL / 性能优化任务的额外要求

如果任务核心是 SQL、分页、count、去重、排序、join、索引匹配、慢查询或性能优化，除常规定位外，还必须：

1. 还原真实调用链与 SQL 结构。
2. 指出性能候选问题属于哪一类：
   - 查询结构
   - 分页 / count
   - 去重 / union 语义
   - join / 过滤条件
   - 排序 / 数据分布
   - 外部依赖或调用方式
3. 明确哪些结论是代码证据，哪些只是推测。
4. 主动形成“需要向用户确认的问题清单”，至少覆盖：
   - 结果语义是否允许变化
   - count / 空页 / 排序口径
   - 性能目标和不可接受阈值
   - 真实高频场景与影响范围
5. 在用户回复这些问题前，不把任务流转成可直接改码。

## 强制执行载体规则 ⚠️

**代码定位 / 分析 / 实现必须优先走 ACP opencode**。

### 优先级顺序
```
ACP opencode（优先）
  ↓ 若 ACP 不可用/补丁失效
exec opencode（降级）
  ↓ 若 exec 也不可用
直接改码（仅 light 任务）
```

### 对 ACP 执行的特殊要求

当本阶段由 `ACP opencode` 承接时：
- controller 应把 planning 产出的 shared context summary 和目标模块直接作为派发输入
- locator 的输出应默认按结构化 findings 格式组织
- 若定位涉及多文件链路追踪，优先在一个 ACP session 里连续推进，而不是分段重喂上下文
- 不要把 ACP 只当成搜索工具，应利用其持续会话能力做多轮递进式分析
- 遵守以下约束：
  - 只做代码定位、调用链核对、SQL/分页/计数逻辑证据收集
  - 不修改任何文件，不生成补丁，不建议直接改码
  - 输出要面向 controller，可直接回填 findings.md
  - 特别关注 SQL / 性能优化任务的 user-confirmation gate：把"还需要用户确认的业务语义/现场口径"单列出来
  - 不要全盘扫描，只看与任务直接相关的文件

## 反模式

不要：
- 在没有模块边界的情况下扫描整个仓库
- 还没给出文件证据就直接跳进实现建议
- 把一次字符串命中当成入口点已证实
- 掩盖不确定性
- 把定位结论只当聊天回答，不沉淀为后续可复用的 findings
- 在 SQL / 性能优化任务里，分析完代码后不向用户追问现场语义和真实场景，就默认进入 implementer
- 用户给了 API 端点，却绕过它去找需求分析文档建议的 BO 类
- 信任需求分析文档的文件建议，但不验证该文件是否在目标 API 的调用链中
- 只检查了"某个 BO 是否有字段"，但不检查该 BO 是否被目标 API 的响应链使用
