# 护士站需求澄清

使用本技能，把一个原始的护士站事项转成可持续推进的执行入口，而不是一次性聊天回答。

## 目标

本阶段的目标不是回答“怎么改代码”，而是先把任务从消息流收敛成一个足够稳定的工作单元，让后续计划、执行、验证可以少重复喂上下文、少靠主控转述、少在中途重新猜题。

它主要解决四类问题：
- 需求锚点还没对齐，就过早进入执行，导致实现器边猜边做
- 多轮推进时，每次都要重新解释业务目标、范围和成功标准
- controller 在子任务之间反复转述，造成信息折损
- 明明是一个中任务，却被当成一次性聊天问题处理，无法形成工作流连续性

因此，requirement-fit checkpoint 的核心作用是先回答：

> 这个任务现在是否已经具备进入持续执行流的资格，以及该如何进入。

## 顺序规则

对于 `nurse-station-*` 相关工作，本技能是默认的第一阶段。

不要因为用户已经给了工作项 ID、仓库路径、执行器选择、模型或初步方案，就直接跳过到计划、定位或执行。

即使请求已经接近执行，也仍然要先做一个简短但显式的需求澄清检查点，用来确认：
- 当前 intake 是否已经足够
- 目标、边界、成功标准是否已经够清楚
- 这是不是一个适合进入持续工作流的护士站任务
- 下一阶段应走 planning、direct edit，还是更轻量的单次处理

只有当用户明确说明该任务已经过了 intake，可以直接进入计划或执行时，才允许跳过本阶段。

## 本阶段产物

本阶段默认应产出一份可被后续阶段复用的结构化摘要，而不只是聊天里的瞬时判断。

至少要形成：
1. 一个稳定任务名
2. 一份简洁的 requirement summary
3. 一个明确任务级别（`light` / `medium` / `heavy`）
4. 一个推荐执行载体
5. 一个建议阶段顺序
6. 一个后续阶段可复用的 success anchors 列表

如果任务属于 `medium` 或 `heavy`，优先把这些内容当成后续 `writing-plans`、`subagent-execution`、`verification` 的共享输入，而不是让后续阶段重新从聊天里抽取。

## 必需输出

至少覆盖以下内容：

1. 任务类型
   - 稳定性修复
   - 功能扩展
   - 易用性优化
   - 债务治理
   - 探索型事项
2. 业务背景
3. 核心目标
4. 明确的非目标
5. 范围与影响模块
6. 成功标准
7. 风险 / 模糊点
8. 外部依赖 / 前置条件
9. 任务级别（`light` / `medium` / `heavy`）
10. 建议执行路径
11. 是否已具备进入计划的条件
12. 是否已具备进入代码执行的条件
13. 建议使用哪种外部执行方式
14. 建议沉淀成哪类持续资产（plan / findings / progress / verification notes）

## 强制检查项

在允许任务进入下一阶段前，必须检查：

- 业务意图是否清晰？
- 目标场景是否清晰？
- 模块 / 页面是否足够明确？
- 期望的交互或行为是否清晰？
- 验收条件是否足够明确，能用于后续验证？
- 当前方案是否依赖第三方 / 外部团队 / 外部系统 / DBA / 产品侧配合？
- 如果依赖外部配合，依赖主体是否已经明确到可执行？
- 如果依赖方一旦配合就能直接规避或消解本需求，本需求是否仍然成立？
- 当前要推进的是正式优化，还是在依赖未明期间的临时兜底？
- 如果任务属于 SQL / 性能优化，是否已区分"代码证据"、"现场业务口径"和"允许采用的优化方向"？
- 是否大概率需要跨轮执行或多阶段推进？
- 是否大概率需要定位 / 实现 / 评审 / 验证等多步协作？
- 是否值得把这次任务转成可持续跟踪的工作流对象，而不是一次性聊天处理？
- 如果可能使用外部执行器，是否应优先使用 `ACP opencode`，以及在 ACP 不可用时是否能降级到 `exec opencode`？
- 当前环境若宣称 `ACP opencode` 可用，应确认 `2026-04-08` 的 Windows ACP 补丁仍然存在；若升级后补丁被覆盖，不要误判为 `opencode` 本身故障。
- 如果还不够清楚，就列出缺失问题，不要靠猜。

## 护士站专属视角

当任务属于护士站工作时，主动从以下一个或多个维度给它分类：

- 稳定性 / 故障减少
- 效率 / 操作简化
- 流程一致性
- 数据正确性 / 展示正确性
- 可观测性 / 便于诊断
- 长期治理 / 可复用机制

## 任务级路由

在进入后续流转前，把每个护士站任务归类为以下三档之一：

- `light`：小范围、本地化、足够清晰，不需要重型编排
- `medium`：边界可控，但需要定位 / 窄范围实现 / 明确验证
- `heavy`：多阶段、高不确定性、值得使用 runtime 跟踪

默认路由：

- `light`：
  - 默认不需要 runtime
  - 默认不需要外部执行器
  - 默认不需要重型子执行链
  - 重点是把需求说清楚，避免过度流程化
- `medium`：
  - 优先进入 `nurse-station-writing-plans`
  - 推荐形成可复用的 plan / findings 结构
  - 如果属于 SQL / 性能优化，默认必须先过 `locator`，由代码分析产出证据与待确认问题，再决定能否进入 implementer
  - 如果需要外部执行器，默认优先使用 `ACP opencode`
- `heavy`：
  - 强烈建议使用 runtime 思维组织任务
  - 默认进入 `nurse-station-writing-plans` 后再派发执行
  - 当选择 `opencode` 时，默认外部执行路径为 `ACP opencode`，若 ACP 不可用则降级到 `exec opencode`

补充约束：
- 当前 Windows 环境下，`ACP opencode` 的可用性依赖 `2026-04-08` 记录的本地 ACP 手动补丁。
- 若 OpenClaw 升级、重装或切版本后再次出现 `backend unavailable`，先检查补丁是否被覆盖，再决定是否降级。

不要把所有“看起来能执行”的任务都当成同一种重型路径处理。

## 可进入计划

只有当以下条件全部满足时：
- 目标问题可理解
- 受影响的模块或仓库方向已知
- 预期行为已经具体到可以拆解
- 至少已有一版草拟 success anchors
- 若方案依赖外部配合，依赖主体与执行条件已明确；否则必须把任务显式改写为“临时兜底”而非默认正式方案

## 可进入执行

只有当以下条件全部满足时：
- 已有计划输出，或任务本身确实极其简单
- 目标仓库 / 模块 / 文件方向已知
- 模糊点不太可能导致返工
- 验证方式已识别
- 若任务对 UI / 交互敏感，所需的 requirement-fit checkpoint 已具备
- 不存在“关键外部依赖尚未明确，但实现方案默认建立在其配合之上”的情况
- 若任务属于 SQL / 性能优化，已先完成代码分析，并已向用户补齐现场业务场景、结果语义与性能目标口径

## 集成关系

完成本技能后：
- 如果任务还不够清楚，就停下来，只追问那些缺失的关键问题。
- 如果任务属于 SQL / 性能优化，不要把 brainstorming 当成可直接改码许可；先流转到代码分析，再由分析结果反向追问用户。
- 如果任务复杂到需要多阶段执行，优先把本阶段产物作为后续共享输入，再进入 `nurse-station-writing-plans`。
- 如果任务是 `medium` 或 `heavy`，且用户希望用 `opencode`，优先走 `ACP opencode`。
- 如果 ACP 不可用或不健康，则降级到裸 `exec opencode`。
- 当前 Windows 环境若 ACP 重新报 `backend unavailable`，先检查 `2026-04-08` 记录的本地补丁是否仍在。
- 不要把基于 wrapper 的执行方式推荐成标准路径或降级路径。
- 如果已经足够清楚，则流转到 `nurse-station-writing-plans`。
- 如果这是一个原因尚不明确的缺陷，则在实现规划前，按需使用系统化定位或调试步骤。

更广义的护士站默认阶段顺序和产物落地约定，见 `nurse-station-orchestrator`。
