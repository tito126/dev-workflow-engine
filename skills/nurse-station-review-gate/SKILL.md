# 护士站评审闸门

把评审拆成明确闸门，并按正确顺序执行。评审产出的核心价值不仅是"通过/不通过"，还在于形成可沉淀的评审结论，避免下次类似任务重复踩坑。

## 核心规则

评审不是一件事。

本技能是护士站顺序流中的下游关卡，不是前序阶段的替代品。

默认的大阶段顺序：
`nurse-station-brainstorming -> nurse-station-writing-plans -> nurse-station-subagent-execution / nurse-station-implementer -> nurse-station-verification -> nurse-station-review-gate`

如果任务涉及提示文案、帮助说明、注意事项、产品给定原文，review-gate 必须把“位置验收”和“文案验收”视为两道独立子检查，不能混成一个模糊的“产品基本接受”。

必须始终拆开处理：
1. **编码前需求匹配小闸门**
2. **实现后需求 / 规格匹配闸门**
3. **实现后代码质量 / 变更风险闸门**

最终决策时，还必须拆开写：
- 代码是否完成
- 需求是否完成
- 效果是否已验证

当前序闸门不满足时，不要启动后续闸门。

## 闸门 0：编码前需求匹配小闸门

当任务对 UI 敏感、属于 medium/heavy，或其他容易漂移的场景时，应在编码前执行本闸门。

检查：
- 目标场景是否足够明确？
- 页面 / 模块范围是否足够明确？
- 摆放位置 / 交互预期是否足够明确？
- 范围内 / 范围外边界是否足够明确？
- 是否已经具备后续验证可用的具体验收检查点？

如果闸门 0 失败：
- 不要进入实现
- 返回到需求匹配检查点、`brainstorming` 或计划阶段

输出：
- 通过 / 不通过
- 缺失锚点
- 返回阶段

## 闸门 1：实现后需求 / 规格匹配

检查：
- 变更是否解决了被请求的场景？
- 是否保留了已约定的交互模型？
- 是否遵守了范围内 / 范围外边界？
- 是否引入了需求中没有要求的内容？
- 场景限制是否正确，例如是否只在特定状态下显示？
- 结果是否匹配编码前定义好的验收锚点？
- 若前序阶段已产出成功锚点，是否逐条对照？
- 文案类任务里，是否出现“位置对了，但原文被改写”的情况？
- 如果产品给了标准案例，是否逐条保留，而不是被压缩成概括性示例？

如果闸门 1 失败：
- **不要启动闸门 2**
- 根据缺口来源，返回实现阶段、`locator` 或计划阶段
- 不允许用“位置可以接受”“大意没问题”来替代正式通过

输出：
- 通过 / 不通过
- 精确缺口
- 返回阶段

## 闸门 2：实现后代码质量 / 变更风险

只有在闸门 1 通过后，才运行本闸门。

检查：
- 实现是否局部化，且没有过度扩张？
- 参数映射 / 条件处理 / 去重处理是否安全？
- 目标文件是否与计划预期一致？
- 是否存在明显的可维护性或回归风险？
- 针对声称的完成程度，是否已经做了足够验证？

输出：
- 通过 / 不通过
- 严重 / 重要 / 次要问题
- 下一步动作

## 评审者心态

- 不要只相信总结。
- 要读实际文件 / 实际变更描述。
- 如果已有运行时证据，先读证据，再决定是否相信最新总结。
- 如果任务使用过外部执行器，优先查看可用的运行证据、结果产物或结构化输出，而不是只看聊天总结。
- 如果前序 verification 已产出结构化验证结论，优先把它当作审查起点，而不是重新从零推断。
- 如果证据不完整，要明确说明哪些点还无法验证。
- 不要把业务匹配和代码整洁混成同一个判断。
- 不要把“业务口径已确认”误写成“效果已验证”。

## 证据等级

- A：真实环境 / 真实样本 / 实测结果 / 上线观察
- B：代码证据 / 静态分析 / 结构化 diff / 文件级证据
- C：业务口头确认 / 聊天确认 / 规则性判断

若当前只有 B / C 级证据，可以给出“代码可收口”或“需求按当前口径可收口”，但不能直接宣称“效果已验证”。

### 可复用产物
评审结论应默认充当任务交付的最终闸门记录。
- "评审结论摘要" 应可被 `work-control` 体系引用
- "代码完成 / 需求完成 / 效果已验证" 必须避免混写成一个状态
- "可沉淀的经验 / 教训" 应在今日总结时同步到 memory
- 如果评审发现系统性问题（如某类需求经常在 implementation 阶段返工），应显式建议改进上游 skill 或流程

## 集成关系

在 `nurse-station-subagent-execution` 之后、最终交付前使用。
当任务被运行时跟踪时，优先审阅 `task-plan.md`、`findings.md` 和 `progress.md`，再做闸门判断。
当任务使用过 `ACP opencode` 或 `exec opencode` 等外部执行路径时，把可获得的计划、结果和运行证据视为评审证据。
若当前结论依赖 `ACP opencode` 执行成功，且环境为 Windows，本地应默认认可 `2026-04-08` 记录的 ACP 手动补丁为已知前提；若升级后链路失效，应先检查补丁是否被覆盖。
如果闸门 0 失败，在任何编码前返回需求匹配检查点或计划阶段。
如果闸门 1 失败，带着需求级纠偏意见退回。
如果闸门 2 失败，带着代码质量级纠偏意见退回。
完整的阶段顺序和产物落地约定，见 `nurse-station-orchestrator`。
