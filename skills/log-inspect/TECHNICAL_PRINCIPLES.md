### 1.2 核心模块

#### 1.2.1 日志拉取模块 (loki_fetcher.py)
- **自适应分片查询**：根据数据密度自动调整查询策略
- **高密度降级机制**：连续命中上限后切换为固定窗口拉取
- **双模式拉取**：
  - 默认模式：递归二分，适合低密度日志
  - 降级模式：固定时间窗口顺序拉取，适合高密度日志

#### 1.2.2 日志预处理模块 (preprocess.py)
- **多格式日志解析**：支持 K8s、传统服务器、工具组等多种日志格式
- **智能错误分类**：基于正则和启发式规则的错误分类
- **慢接口聚合**：按 API 路径聚合，保留代表 trace
- **Trace 上下文补强**：为 Top 慢接口补充完整调用链

#### 1.2.3 慢接口分析模块 (slow_interface_analyzer.py)
- **调用链拆解**：识别数据库、外部接口、缓存等步骤
- **瓶颈定位**：找出耗时最长的步骤
- **优化建议生成**：基于瓶颈类型给出针对性建议

## 2. 核心技术优化

### 2.1 自适应日志拉取策略

#### 2.1.1 问题背景
不同医院的日志密度差异巨大：
- **低密度场景**（如桐乡）：1小时内 ERROR|WARN 约 10-20 万条
- **高密度场景**（如乐山）：1小时内 ERROR|WARN 可达 30-50 万条

传统固定分片策略存在问题：
- 固定大窗口：高密度场景下容易截断数据
- 固定小窗口：低密度场景下请求次数过多，效率低

#### 2.1.2 优化方案

**双模式自适应拉取**：

```python
def query_loki_adaptive(
    grafana_url, datasource_id, query, start, end,
    limit=5000,
    min_chunk_minutes=1.0,
    saturation_threshold=3,
    fallback_window_seconds=10
):
    """
    自适应分片查询，根据数据密度自动切换策略
    
    工作流程：
    1. 先查询整个时间段
    2. 如果返回 < limit，说明没有截断，直接返回
    3. 如果返回 >= limit，说明可能有截断：
       - 如果连续命中次数 < saturation_threshold：继续二分
       - 如果连续命中次数 >= saturation_threshold：切换为固定窗口模式
    """
```

**关键参数**：
- `limit=5000`：单次查询上限
- `min_chunk_minutes=0.25`：最小分片时间（15秒）
- `saturation_threshold=3`：连续命中上限的阈值
- `fallback_window_seconds=10`：降级后的固定窗口大小

**效果对比**：

| 场景 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| 桐乡 1小时 | 5-6分钟 | 4分24秒 | 20% |
| 乐山 1小时 | 超时/失败 | 16分14秒 | 从不可用到可用 |

### 2.2 慢接口 Trace 上下文补强

#### 2.2.1 问题背景
原有方案只保留慢接口的基本信息（API路径、耗时、次数），缺少：
- 代表性 trace 的完整调用链
- 具体的耗时步骤拆解
- 针对性的优化建议

#### 2.2.2 优化方案

**三阶段补强流程**：

1. **聚合阶段**：收集每个 API 的 Top 5 慢 trace
```python
def aggregate_slow_apis(slow_apis):
    for api in slow_apis:
        # 保留 Top 5 最慢的 trace
        stat['top_traces'].append({
            'trace_id': trace_id,
            'duration_ms': duration,
            'timestamp': timestamp,
            'user': user
        })
```

2. **上下文补强阶段**：为 Top 10 慢接口补充完整日志
```python
# 为代表 trace 补充前后文窗口
pending_buffers = {trace_id: [] for trace_id in top_slow_trace_ids}
for line in log_file:
    # 保留前后 TRACE_CONTEXT_PADDING 行
    if line_trace_id in top_slow_trace_ids:
        trace_logs[trace_id].extend(buffer_lines)
        trace_logs[trace_id].append(line)
```

3. **分析阶段**：拆解调用链，定位瓶颈
```python
def analyze_slow_trace(trace_logs, total_time):
    # 识别步骤：数据库、外部接口、缓存、业务逻辑等
    for log_line in trace_logs:
        if matches_database_pattern(log_line):
            steps.append({'category': '数据库查询', 'time': time})
    
    # 找出瓶颈
    bottleneck = max(steps, key=lambda x: x['time'])
    
    # 生成建议
    suggestions = generate_optimization_suggestions(bottleneck)
```

**效果**：
- 慢接口报告从"只有数字"到"有完整调用链和优化建议"
- 开发人员可以直接定位到具体的慢步骤

### 2.3 智能错误分类

#### 2.3.1 问题背景
原有分类过于粗糙，导致：
- "其他异常"占比过高（60-70%）
- 无法快速定位真正的问题
- 缺少友好的错误原因摘要

#### 2.3.2 优化方案

**两层分类策略**：

1. **启发式规则优先**：
```python

    ('sql_error', [r'ora-\d+', r'sqlgrammar', r'resultset']),
    ('auth_error', [r'token', r'认证', r'unauthorized']),
    ('validation_error', [r'must not be empty', r'参数']),
    # ...
]
```

2. **错误原因提取**：
```python

        r'real exception message:(.*)',

        r'(ORA-\d+:[^,;]+)',
        # ...
    ]

```

**效果对比**：

| 分类 | 优化前占比 | 优化后占比 |
|------|-----------|-----------|
| SQL错误 | 5% | 15% |
| 认证问题 | 3% | 12% |
| 参数校验 | 2% | 8% |
| 其他异常 | 70% | 35% |

### 2.4 多环境适配

#### 2.4.1 支持的环境类型

1. **K8s 环境**（桐乡、乐山）

## 4. 技术亮点

### 4.1 自适应策略
- 根据数据密度自动调整拉取策略
- 避免"一刀切"导致的效率或准确性问题

### 4.2 上下文补强
- 不仅统计数字，还提供完整调用链
- 从"知道慢"到"知道为什么慢"

### 4.3 多环境统一
- 一套代码适配 K8s、传统服务器、工具组 API
- 配置驱动，易于扩展

### 4.4 智能分类
- 启发式规则 + 错误原因提取
- 大幅降低"其他异常"占比
