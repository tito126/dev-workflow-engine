# 日志巡检整体工作流程

本文档用于说明：当用户以自然语言提出“拉某医院某服务某时间段日志并生成分析报告”这类需求时，日志巡检工具应如何从入口判断、选择业务线、执行取数、分析并生成最终报告。

全文以“自然语言输入”为起点，拆分为两条独立业务线：

1. K8s / Grafana / Loki 业务线
2. 传统服务器 / tool_api 业务线

目标是把“什么时候走哪条线、每条线具体怎么跑、每一步产出什么、有哪些必须遵守的规则”讲清楚，作为后续操作指南与实现依据。

---

## 1. 总体入口：从自然语言开始

### 1.1 用户输入的典型形式

用户通常不会直接给命令，而是给自然语言需求，例如：

- 帮我看一下乐山市人民医院病区护士站最近 10 分钟的报错
- 拉一下桐乡市卫生健康局病区护士站 14:00 到 14:10 的日志
- 看看红房子这个服务最近有没有慢接口
- 帮我分析某医院某服务某时间段日志并出报告

这类输入通常至少隐含以下几个核心要素：

- 医院 / 客户名称
- 服务名称或业务名称
- 时间范围
- 分析目的（报错、慢接口、完整报告等）

系统的第一步不是立即拉日志，而是先把自然语言解析成结构化信息，再根据环境类型选择正确的业务线。

---

## 2. 入口处理总流程

### 2.1 第一步：提取结构化参数

从自然语言中尽可能提取以下字段：

- `hospital`：医院名称
- `service`：服务名、系统名或业务模块名
- `start_time`：开始时间
- `end_time`：结束时间
- `duration`：时长（如果用户说“最近 10 分钟”）
- `query_goal`：目标，如错误分析、慢接口分析、完整报告
- `cluster`：集群信息（如桐乡这类多集群环境）

### 2.2 第二步：时间标准化

如果用户说的是相对时间，要先换算成绝对时间：

- 最近 10 分钟 -> 当前时间往前推 10 分钟
- 今天下午 2 点到 3 点 -> 标准化为明确的起止时间
- 昨晚 -> 必要时需结合上下文推断；若无法安全确定，再补问

原则：

- 能从上下文明确推断时，直接标准化
- 时间歧义会影响结果时，才补问
- 最终进入取数逻辑的一律应是明确的 `start_time` 和 `end_time`

### 2.3 第三步：医院环境识别

根据 `hospital` 在 `config/environments.json` 或环境配置中判断该医院属于哪种环境：

- `k8s` / `grafana+loki` 类型
- `tool_api` / 传统服务器类型

当前已明确：

#### 已知 K8s 医院

- 乐山市人民医院
- 桐乡市卫生健康局
- 复旦大学附属妇产科医院(红房子)

这类医院优先走 **K8s 业务线**。

#### 已知传统模式医院

- 工具组测试环境医院
- 后续接入 tool_api 生产环境的传统服务器医院

这类医院走 **传统服务器 / tool_api 业务线**。

### 2.4 第四步：判定是否需要补问

在真正开始取数前，需要判断是否存在必须补问的信息。

#### 必须补问的典型场景

1. **医院名不明确**
   - 如用户只说“那个医院”“桐乡那边”但无法唯一定位

2. **服务名不明确**
   - 如用户只说“护士站”，但实际可能对应多个服务

3. **时间范围不明确**
   - 如用户只说“刚才”“昨天晚上”，但无法安全落到确定时间窗

4. **桐乡市卫生健康局未指定集群**
   - 这是强规则，不能自行猜第一集群、第二集群或第三集群

### 2.5 第五步：路由到具体业务线

当结构化参数齐全后，进入业务线选择：

- K8s 医院 -> 进入第 3 章 K8s 业务线
- 传统服务器医院 -> 进入第 4 章 传统服务器业务线

## 3. 业务线一：K8s / Grafana / Loki 日志巡检流程

### 3.1 适用范围

该业务线适用于已经确认走 K8s / Grafana / Loki 的医院环境。

当前明确适用：

- 乐山市人民医院
- 桐乡市卫生健康局
- 复旦大学附属妇产科医院(红房子)

其核心特征是：

- 日志最终通过 Grafana / Loki 查询
- 通常需要先通过 `wxp-tunnel` 或类似通道能力打通现场 Grafana 访问链路
- 支持“两阶段拉取 + 完整链路补全”

### 3.2 这条线的总体目标

K8s 业务线不是只拉原始日志，而是要完成一整套分析链路：

1. 拉取目标时间段内的关键日志（ERROR + 慢接口入口）
2. 先做一次分析，找出代表性 trace
3. 再针对代表 trace 拉完整链路日志
4. 重新分析整合后的日志
5. 输出 HTML 报告

也就是说，这条线是一个 **两阶段取数、两次分析、一次报告输出** 的流程。

---

### 3.3 K8s 业务线详细步骤

#### 第 1 步：确认医院与集群

先判断医院是否属于 K8s 环境。

如果是桐乡市卫生健康局，必须先确认集群：

- 第一集群
- 第二集群
- 第三集群

这是固定规则，不能跳过。

原因：

- 桐乡是多集群环境
- 不同集群的 Grafana / 服务实例 / 日志数据并不等价
- 直接默认某个集群会导致拉错数据

因此，桐乡场景下的流程顺序应为：

1. 识别医院 = 桐乡市卫生健康局
2. 判断未给出集群
3. 先补问集群
4. 拿到集群后再继续后续流程

#### 第 2 步：定位 K8s 环境配置

从环境配置中读取目标医院（及集群）的关键信息，例如：

- `grafana_url`
- `datasource_id`
- `tenant_code`（若需要）
- 服务映射
- 集群配置
- 其他通道信息

这一步的目的是让后续取数过程具备完整环境参数，而不是在命令层临时硬编码。

原则：

- 优先使用配置文件中的已知环境信息
- 不要把 Grafana 地址、端口、datasource 写死在主流程逻辑里
- 医院差异应尽量由环境配置承载

#### 第 3 步：通过 wxp-tunnel 打通访问通道

如果当前环境不能直接访问 Grafana / Loki，需要先通过 `wxp-tunnel` 打通现场代理或隧道。

这一层的作用是：

- 把现场不可直连的服务暴露为本地可访问地址
- 形成类似 `http://127.0.0.1:14828` 或代理地址 `http://172.16.7.39:8000` 的入口

这一步的本质是 **连接层准备**，不是日志分析本身。

成功后应拿到一个可用于查询 Grafana / Loki 的入口地址。

#### 第 4 步：验证 Grafana / Loki 可访问性

在真正跑主流程前，应先确认以下信息是通的：

- Grafana 地址能访问
- datasource_id 正确
- app / service 对应的 Loki 查询标签有效

如果这一步失败，不应盲目进入 fetch。

常见检查点：

- Grafana URL 是否正确
- 通道是否已打开
- datasource_id 是否对应 Loki
- 服务 app 名是否正确

#### 第 5 步：第一阶段拉取 fetch

第一阶段不是拉全部日志，而是拉“问题定位所需的首轮关键日志”。

当前规则为：

- 拉取条件：`ERROR | 业务处理耗时`
- 目标：
  - 捕获异常日志
  - 捕获慢接口入口日志
- 输出：原始 `.log` 文件 + 拉取元信息

为什么这样做：

- 如果一开始就拉全量 INFO / DEBUG，数据量会过大，效率低
- 第一阶段的重点是先识别“有哪些异常类别、哪些慢 trace 值得继续追”

这一阶段应记录并产出：

- 原始日志文件
- 实际拉取时间范围
- 拉取耗时 `fetch_duration`
- 日志条数
- 环境元数据（hospital、service、cluster、datasource 等）

注意：

- `fetch_duration` 必须在这一阶段就保存好
- 后续 analyze / report 若丢失该值，会导致报告中“拉取耗时”不显示

#### 第 6 步：第一次分析 analyze

对第一阶段 `.log` 做预处理与分析，生成 digest 结果。

这一阶段的核心任务包括：

- 日志解析与结构化
- 错误日志分类
- 四级分组
- 慢接口识别
- 代表 trace 提取

当前已对齐的分组思路是按四级分组：

- `category:root_class:api_entry:caller_service`

该阶段的关键产物通常包括：

- `*_digest.json`
- `*_digest_traces.json`

其中：

- `digest.json` 负责承载分析统计结果
- `digest_traces.json` 负责承载后续第二阶段要补拉的代表 trace 列表

#### 第 7 步：生成代表 trace 列表

第一次 analyze 的一个核心输出，是确定“哪些 trace 值得拉完整链路”。

通常包括两类：

1. **异常类代表 trace**
   - 每个异常分组取代表 trace
2. **慢接口代表 trace**
   - 选取 Top N 最慢 trace

这样做的目的，是用有限的第二阶段成本，换取最有代表性的完整链路上下文。

原则：

- 不是把所有 trace 都补全
- 而是补最能解释问题的代表 trace
- 优先保证报告可读性与问题定位效率

#### 第 8 步：第二阶段拉取 fetch2

根据 `*_digest_traces.json` 中的代表 trace，执行第二阶段完整链路拉取。

这一阶段的目标是：

- 针对每个代表 trace，补拉其上下文中的所有日志
- 包括 INFO 等非错误级别日志
- 形成完整调用链路

当前重要规则：

- 第二阶段默认时间窗口为 **trace 前后 ±60 秒**

这是已验证过的经验规则，原因是：

- 之前使用 ±30 秒时，某些慢接口 trace 会少日志
- 已确认 `be25d207c0c04053a3a54d7df3cc271c` 在 ±30 秒下会漏 2 条
- 调整到 ±60 秒后可补齐已知缺失日志

因此，K8s 业务线中第二阶段时间窗口的默认值应固定为：

- `stage2_window = ±60s`

第二阶段输出结果通常是：

- 拉回的完整链路日志 append 到原始 `.log`
- 或形成整合后的完整日志文件

#### 第 9 步：重新分析 re-analyze

在第二阶段把完整链路补回后，必须重新执行 analyze。

原因：

- 第一次 analyze 基于的是首轮关键日志，不是完整链路
- 第二阶段补回 INFO / 上下文日志后，许多统计、详情和时间间隔分析会更完整
- 最终报告必须基于“整合后的日志”生成，而不是只基于首轮摘要

这一阶段会更新：

- 异常详情
- 慢接口详情
- 时间间隔分析
- 完整链路展示
- 代表 trace 内容

#### 第 10 步：生成报告 report

最终根据重新分析后的 digest 生成 HTML 报告。

报告通常包含：

- 基本信息
- 日志质量分析
- 异常统计概览
- 详细异常分析
- 慢接口 Trace 详情
- 完整链路日志展示
- 日志反哺建议

报告生成时要重点确保以下信息完整：

- 医院
- 服务
- 实际拉取时间范围
- 拉取耗时
- 总日志量
- 异常分类
- 代表 trace 完整链路

如果 `fetch_duration` 未从 fetch 阶段正确传递到后续 digest，报告中的“拉取耗时”会缺失。

### 3.4 K8s 业务线标准流程图（文字版）

标准顺序如下：

1. 自然语言输入
2. 提取医院 / 服务 / 时间范围
3. 判断医院属于 K8s
4. 若医院为桐乡，先询问集群
5. 读取环境配置
6. 通过 wxp-tunnel 打通 Grafana / Loki 通道
7. 验证 Grafana、datasource、app 可用
8. 执行第一阶段 fetch（`ERROR|业务处理耗时`）
9. 执行第一次 analyze
10. 生成代表 trace 列表
11. 执行第二阶段 fetch2（±60s 完整链路）
12. 执行第二次 analyze
13. 生成 report
14. 输出 HTML 报告路径与分析结果

---

### 3.5 K8s 业务线必须遵守的规则

#### 规则 1：桐乡必须先问集群

这是强规则。

不能因为用户没说，就默认第一集群或上一次用过的集群。

#### 规则 2：第一阶段拉取条件固定为 `ERROR|业务处理耗时`

不要随意退回到 `ERROR|WARN` 作为默认值。

原因：

- 当前目标是兼顾错误与慢接口
- `业务处理耗时` 是慢接口识别的关键入口

#### 规则 3：第二阶段默认窗口固定为 ±60s

不要把默认值改回 ±30s，除非后续再次经过充分验证。

#### 规则 4：K8s 业务线是“两阶段流程”，不能省略 fetch2

如果只做第一阶段并直接出报告：

- 详细异常上下文不完整
- 慢接口时间间隔分析可能缺失
- 完整链路日志展示会不足

#### 规则 5：fetch 元数据必须贯穿后续流程

特别是：

- `fetch_start`
- `fetch_end`
- `fetch_duration`

缺失这些字段会直接影响报告完整性。

#### 规则 6：若 K8s 医院找不到 31003 或无法走 Grafana 链路，可尝试回退到传统模式

当前已确认策略：

- 对于已知 K8s 医院，如果现场无法通过既定端口或链路走通 Grafana / Loki，可考虑回退到传统模式
- 但前提是该医院在传统模式下确实具备可用的数据链路

也就是说，“K8s 医院”并不意味着绝对不能走传统模式，而是：

- **优先走 K8s 线**
- **K8s 链路不通时，可根据实际环境回退传统线**

## 4. 业务线二：传统服务器 / tool_api 日志巡检流程

### 4.1 适用范围

该业务线适用于不通过 Grafana / Loki 拉日志，而是通过工具组接口、节点下载或运维平台链路获取原始日志包的环境。

当前明确适用：

- 工具组测试环境
- 后续接入生产环境的传统服务器医院

其核心特征是：

- 不从 Loki 实时查询日志
- 而是通过 tool_api 获取日志文件下载地址
- 下载后做本地解压、过滤、分析与报告生成
- 通常不需要 fetch2 补完整链路

---

### 4.2 这条线的总体目标

传统服务器业务线的重点不是“在线查 trace 上下文”，而是：

1. 找到对应服务所在节点
2. 调用接口生成日志下载任务或下载地址
3. 下载日志压缩包
4. 解压后对时间范围做本地过滤
5. 分析并生成报告

也就是说，这条线更像是 **离线日志包分析流程**。

---

### 4.3 传统服务器业务线详细步骤

#### 第 1 步：确认医院与环境类型

先根据医院配置判断该环境属于传统服务器 / tool_api 模式。

如果该医院没有 Grafana / Loki 可用链路，或者环境本身就是传统服务器部署，则进入本业务线。

#### 第 2 步：如为生产环境，先打通运维平台通道

对于生产环境传统服务器，通常不能直接访问工具组或运维平台接口，需要先通过 `wxp-tunnel` 打开代理通道。

这一步的作用是：

- 打通运维平台访问链路
- 获得本地可访问的代理地址
- 为后续调用 tool_api 做准备

因此，这条线在生产环境下的顺序通常是：

1. 先通过 wxp-tunnel 打通运维平台
2. 再调用 tool_api 查询节点与下载日志

如果是测试环境，且工具组地址本身已可访问，则可直接进入下一步。

#### 第 3 步：通过 getServicesByCodeOrAppid 查询服务节点

调用工具组接口：

- `getServicesByCodeOrAppid`

其目标是：

- 根据医院 / 应用 / 服务信息，找到实际部署的服务节点列表

该步骤的输出通常包括：

- 节点 IP
- 环境 ID `envId`
- 服务实例信息
- 可能的机器列表

这是传统服务器模式的关键入口，因为后续日志下载通常依赖“具体节点”。

#### 第 4 步：选择目标节点并调用 getServiceLogs

在拿到节点后，调用：

- `getServiceLogs`

其作用是：

- 为指定服务、指定节点、指定时间窗生成日志下载任务或下载地址

关键点：

- 节点选择必须正确
- `envId` 必须匹配
- 时间参数必须符合接口要求

当前已对齐的一条经验是：

- 需要传递 `endTime`
- 因为工具组已经修复了 endTime 相关问题，后续应按精确时间窗传参

#### 第 5 步：使用正确的类型参数

传统服务器模式下，当前规则要求：

- `type = ms_all`

这是固定规则，不要遗漏。

其目的通常是：

- 获取服务相关的完整日志集合
- 便于后续在本地再做精确时间过滤

#### 第 6 步：获取下载地址并下载压缩包

当 `getServiceLogs` 调用成功后，应拿到下载地址或任务结果，随后执行：

- 下载 zip / 压缩包
- 保存到本地工作目录

这一步的产物通常是：

- 原始压缩文件
- 下载耗时
- 下载来源信息

#### 第 7 步：解压日志包

下载完成后，需要将日志包解压到工作目录。

解压后通常会得到：

- 原始日志文件
- 可能是按天、按服务、按节点拆分的日志

此时拿到的是“下载的整段或整天日志”，并不等于最终要分析的时间窗内容。

#### 第 8 步：preprocess 按时间窗过滤

这是传统模式与 K8s 模式的重要差异之一。

传统模式中，通常是：

- 先下载较大范围的日志
- 再在本地通过 preprocess 对目标时间窗做过滤

当前规则：

- 下载时可能是全天日志
- 真正的时间范围裁剪由 preprocess 完成

因此，preprocess 的职责包括：

- 解析原始日志时间戳
- 过滤到用户要求的开始 / 结束时间范围
- 输出目标时间窗内的结构化日志集合

#### 第 9 步：执行 analyze

当本地时间过滤完成后，进入 analyze 阶段。

这一步与 K8s 模式中的 analyze 目标基本一致，主要是：

- 异常分类
- 根因聚合
- 慢接口分析
- 统计概览
- 代表样本提取

但与 K8s 模式不同的是：

- 传统模式通常不依赖第二阶段按 trace 回补完整链路
- 分析基于“下载并过滤后的目标日志集合”直接展开

#### 第 10 步：生成 report

analyze 完成后，直接进入 report 生成 HTML 报告。

该报告应同样覆盖：

- 基本信息
- 日志量与时间范围
- 错误概览
- 详细异常分析
- 慢接口分析
- 建议项

与 K8s 模式相比，它少了“第二阶段完整链路补拉”的环节。

---

### 4.4 传统服务器业务线标准流程图（文字版）

标准顺序如下：

1. 自然语言输入
2. 提取医院 / 服务 / 时间范围
3. 判断医院属于传统服务器模式
4. 若为生产环境，先用 wxp-tunnel 打通运维平台
5. 调用 `getServicesByCodeOrAppid` 获取节点列表
6. 选定节点与 envId
7. 调用 `getServiceLogs` 获取日志下载地址
8. 使用 `type=ms_all` 下载日志压缩包
9. 解压日志文件
10. preprocess 按目标时间窗过滤
11. analyze
12. report
13. 输出 HTML 报告路径与分析结果

---

### 4.5 传统服务器业务线必须遵守的规则

#### 规则 1：生产环境通常要先打通 wxp-tunnel

不要假设 tool_api 在生产环境下天然可直连。

正确理解应是：

- `wxp-tunnel` 负责连接层
- `tool_api` 负责取数层

#### 规则 2：先查节点，再拉日志

不能跳过 `getServicesByCodeOrAppid` 直接假设节点。

原因：

- 传统服务器模式依赖具体节点
- 不同节点日志可能不同
- 节点、envId、服务实例必须配套

#### 规则 3：`getServiceLogs` 要传精确时间参数，尤其是 `endTime`

这是当前已恢复并确认的行为要求。

#### 规则 4：下载类型固定使用 `type=ms_all`

不要随意更换类型，避免漏日志或下载范围不符合预期。

#### 规则 5：时间过滤以 preprocess 为准

即使下载的是整天日志，最终分析范围也必须严格按 preprocess 的时间窗结果。

#### 规则 6：传统模式通常不走 fetch2

原因是：

- 数据源形态不同
- 以离线日志包为主
- 不依赖 Loki 按 trace 二次回补

所以传统模式的主流程应理解为：

- 下载 -> 解压 -> 过滤 -> analyze -> report

而不是两阶段 trace 回补流程。

## 5. 两条业务线的核心差异

为了避免混淆，下面明确两条业务线的本质区别。

### 5.1 数据来源不同

#### K8s 业务线

- 数据来自 Grafana / Loki 查询
- 第一阶段拉关键日志
- 第二阶段按代表 trace 回补完整链路

#### 传统服务器业务线

- 数据来自 tool_api 下载日志包
- 下载后本地解压与过滤
- 一般不做按 trace 二次回补

### 5.2 时间过滤位置不同

#### K8s 业务线

- 查询时就按目标时间窗直接拉取
- 第二阶段再按 trace 附近窗口补完整链路

#### 传统服务器业务线

- 下载时可能是整天或较大范围日志
- 真正目标时间窗由 preprocess 在本地过滤

### 5.3 是否需要两阶段拉取不同

#### K8s 业务线

- 必须两阶段：`fetch -> analyze -> fetch2 -> analyze -> report`

#### 传统服务器业务线

- 单阶段即可：`download -> preprocess -> analyze -> report`

### 5.4 连接层不同

#### K8s 业务线

- 重点是打通 Grafana / Loki 通道

#### 传统服务器业务线

- 重点是打通运维平台 / tool_api 通道

---

## 6. 推荐的统一执行顺序

无论走哪条线，建议都遵循以下统一思路：

1. 自然语言解析
2. 提取结构化参数
3. 判断医院环境类型
4. 判断是否缺少关键信息
5. 若缺信息，先补问
6. 进入正确业务线
7. 完成取数
8. 完成分析
9. 生成报告
10. 输出结果与报告路径

这样可以保证整个系统的入口一致，而底层执行按环境分流。

## 9. 一句话总结

当用户从自然语言发起日志巡检需求时，系统应先完成结构化解析与环境识别，再根据医院类型进入两条独立业务线之一：

- K8s 环境走 `wxp-tunnel -> Grafana/Loki -> fetch -> analyze -> fetch2 -> re-analyze -> report`
- 传统服务器环境走 `wxp-tunnel/tool_api -> 查节点 -> 下载日志 -> 解压 -> preprocess -> analyze -> report`

两条线的差异核心在于：

- 数据来源不同
- 时间过滤位置不同
- 是否需要第二阶段完整链路补拉不同

只要入口判断正确、规则执行稳定，就能把自然语言需求可靠地落成最终分析报告。
