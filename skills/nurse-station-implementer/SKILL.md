# 护士站实现执行

只有在范围已经清楚之后，才进入实现。实现产出的核心价值不仅是"改了代码"，还在于输出后续阶段可直接复用的结构化结果。

## 进入条件

只有当以下条件全部满足时，才使用本技能：
- 已经过需求澄清检查点，并确认该任务可以继续推进
- 需求意图已澄清
- 范围已收敛
- 仓库路径已知
- 可能变更的文件已知，或已经收窄到足够小的范围
- 验证方式已识别

## 职责

你负责：
- 进行有边界的代码修改
- 保持既定行为与边界不被破坏
- 在可能的情况下做定向验证
- 报告具体结果，以及仍然存在的不确定点
- 输出可供 `verification` 和 `review-gate` 直接复用的结构化实现报告

你不负责：
- 在没有阻塞的情况下重新争论需求意图
- 做大范围仓库探索
- 静默扩大范围

## 输出要求

### 实现报告
- 已实现目标：
- 运行时路径：
- 是否需要过程更新：
- 需要沉淀的错误：
- 已修改文件：
- 实际改动摘要：
- 未改动部分及原因：
- 已执行验证：
- 风险 / 不确定性：
- 是否可进入评审：是/否

### 可复用产物
如果任务属于 `medium` 或 `heavy`，实现报告应同时充当后续 verification 和 review-gate 的输入，而不是只作为聊天里的口头回复。

具体来说：
- 实现报告里的"已实现目标"应对齐前序 planning 的 success anchors
- "风险 / 不确定性"应直接供 verification 当作检查起点
- "已修改文件"应供 review-gate 当作代码质量审查范围

## 规则

- 如果定位得到的文件信息还不够，就停下来并请求先做一次定位。
- 如果需求与当前代码结构冲突，要显式报告冲突，而不是硬做。
- 如果你发现了额外问题，除非用户要求，否则不要顺手吸收到本次改动里。
- 优先做最小且聚焦的改动，而不是顺手清理一大片。
- 如果在实现过程中出现失败模式或结构性冲突，要把它保留下来作为运行时证据，而不是只留在聊天里。

## 对 ACP 执行的特殊要求

当本阶段由 `ACP opencode` 承接时：
- controller 应把 planning 产出的 shared context summary 和 success anchors 直接作为派发输入
- implementer 的输出应默认按结构化实现报告格式组织，方便后续阶段直接引用
- 不要把 ACP 只当成跑命令的管道，应利用其持续会话能力减少"重讲一遍需求"的开销

## 集成关系

在 `nurse-station-brainstorming`、`nurse-station-locator` 和 `nurse-station-writing-plans` 之后使用。
对于复杂任务，应把实现报告视为运行时进展输入，而不是只留在聊天里。
如果本次实现由 `ACP opencode` 承接，且环境为 Windows，应默认把 `2026-04-08` 记录的本地 ACP 手动补丁视为链路前提；若后续链路失效，先检查补丁是否被升级覆盖。
输出应发送到 `nurse-station-review-gate` 和 `nurse-station-verification`。
完整的阶段顺序和产物落地约定，见 `nurse-station-orchestrator`。
