# executor 路由规则（第一版）

这份规则用于把 `main` 的全局统筹职责，与 `executor` 的执行承接职责串起来。

目标不是把所有任务都切给 `executor`，而是在合适的时候稳定切换、稳定续跑、稳定回写。

## 1. 角色定位

### main

负责：
- 专项识别与立项判断
- 目标澄清
- 成功标准与衡量口径收口
- 优先级判断
- 风险识别
- 决定是否切 `executor`
- 对执行结果做专项级收口
- 复盘与方法论沉淀

### executor

负责：
- 承接进入执行阶段的任务
- 代码阅读与代码路径定位
- 通过代码分析形成优化方案 / 隔离方案 / 修复建议 / 实施建议
- 小到中等规模实现与验证
- 多文件上下文分析
- 调用 `Codex` 进行连续执行
- 将结果整理成便于 `main` 回收的反馈

关键补充：
`executor` 不只承接“改代码”类任务，也承接这类“通过代码分析形成方案”的任务，例如：
- 慢接口分析后的隔离优化方案
- 三方服务依赖治理建议
- 技术改造路径评估
- 可疑代码路径与风险边界梳理
- 局部重构前的代码结构摸底

也就是说，凡是需要深入代码与文件上下文，最终产出可以是：
- 方案
- 设计
- 判断
- 风险结论
- 改动
- 验证结果

不要求必须已经进入“直接写代码”阶段。

## 2. 默认留在 main 的任务

以下情况优先留在 `main`：
- 纯目标澄清
- 是否立项 / 是否继续推进的判断
- 优先级与取舍讨论
- 跨专项统筹
- 风险是否值得承担的判断
- 复盘与长期规则沉淀
- 需要直接代表整体协作系统做判断的内容

## 3. 默认切到 executor 的任务

以下情况优先切到 `executor`：
- 需要读代码并定位关键入口
- 需要通过代码分析形成优化方案、隔离方案、修复建议
- 需要连续查看多文件上下文
- 需要让 `Codex` 连续推进分析 / 设计 / 实现 / 验证
- 需要在项目目录中持续工作，而不希望 `main` 被执行细节拖住
- 任务已经进入“分析路径 → 形成技术结论 → 决定是否实施”的阶段

## 4. 一条简单判断规则

满足以下任意两条，`main` 就应主动提醒切 `executor`：
- 需要代码上下文
- 需要多文件连续分析
- 需要技术方案而不只是业务判断
- 需要真实验证命令、日志、脚本或运行行为
- 本轮预计不会在一两次短对话内结束
- 继续留在 `main` 会明显淹没全局统筹能力

## 5. main 切 executor 时必须给出的最小信息

每次切 `executor`，都至少给出：
- 所属专项
- 子任务名
- 当前阶段
- 已确认结论
- 本轮目标
- 约束边界
- 参考文件
- 期望回写内容

不要只说“你继续一下”。

## 6. executor 何时继续触发 acp -> Codex

`main` 决定是否切到 `executor`，但不负责替 `executor` 判断每一轮是否要进一步调用 `Codex`。

进入 `executor` 后，满足以下任意两条，默认应触发 `acp -> Codex`：
- 需要连续读取多文件代码上下文
- 需要跨模块定位调用链、依赖关系或关键入口
- 需要基于代码证据形成优化方案、隔离方案、改造建议或实施判断
- 需要真实执行命令、修改代码、验证行为或检查运行结果
- 预计本轮不会在一两次短分析内结束，而是会进入持续推进节奏

典型触发场景：
- 慢接口与三方服务隔离优化方案
- 代码级性能瓶颈排查
- 技术改造路径评估
- 需要通过代码分析确认是否值得实施的治理任务

以下情况可先不触发 `Codex`：
- 只是整理已有结论
- 只是把已有结果改写成便于 `main` 回收的反馈
- 只是做是否值得继续的浅层初筛

一句话规则：
> `executor` 负责判断任务是否已进入“深执行区”；一旦进入，就调用 `acp -> Codex`，不要停留在浅层整理。

## 7. executor 在共享区中的回写规则

`executor` 与 `main` 共享 workspace，因此当前阶段优先采用“共享区回写”而不是强依赖单独消息反馈。

规则如下：
- 只要 `executor` 已形成阶段性成果、专项进展、关键判断、方案草案、重要风险或下一步建议，就应直接回写到共享区的正式文件
- 当前优先回写位置：对应专项档案，其次是执行反馈文件；必要时再补 `memory/YYYY-MM-DD.md`
- 不要求每轮都单独给 `main` 发一条消息，但必须留下可被识别的收口信号

当前约定的收口信号包括这类自然表达：
- `更新专项进度`
- `回写专项进展`
- `记录阶段性成果`
- `补充执行结论`
- `同步这轮结果`

一旦用户或 `executor` 明确使用这类表达，默认按“需要正式回写共享区”处理，而不是普通聊天。

## 8. 回写失败时的降级收口规则

如果 `executor` 已经拿到了 `Codex` 的阶段性成果，但在正式回写时失败（例如项目档案 edit 失败、文件编码异常、目标文件难以稳定修改），不得长时间卡在反复重试上。

必须立即切换到“降级收口”模式：
- 先停止继续深挖，不再扩大分析范围
- 先保住已有成果，优先写入新的 deliverable 或执行反馈文件
- 如果项目档案不好改，允许暂时跳过项目档案回写
- 必须明确标出：当前结论、关键代码路径、方案草案、风险与未定项、建议下一步
- 留下 `更新专项进度` 或同类收口信号，便于 `main` 后续接管收口

一句话规则：
> `Codex` 结果先保住，再追求项目档案完美回写；不能因为回写失败把整轮任务拖成假死。

## 9. executor 完成后 main 需要能回收的信息

至少要能从共享区回收到这些内容：
- 本轮做了什么
- 当前结论是什么
- 关键代码路径 / 关键文件是什么
- 哪些判断已足够稳定
- 还有哪些风险与未定项
- 建议下一步是继续分析、开始实施，还是暂时收口
