# executor 长执行观察规则

适用场景：`executor` 承接的代码分析、方案形成、实现验证类任务，预计会超过一次短对话或 10-15 分钟。

目标：减少把“正常长执行”误判为“挂住”，同时明确什么时候该继续等、什么时候该介入。

## 1. 先区分三种状态

### 正常长执行
满足任意两条，可先视为正常：
- `executor` 会话 transcript 仍在增长
- 共享区有新 deliverable / feedback / 项目文件变化
- `Codex` 会话仍在追加分析、命令或结果

### 收口卡住
常见表现：
- `Codex` 已产生成果
- `executor` 还活着
- 但长时间停留在回写、edit、文件整理、结果归档阶段

### 真正异常
常见表现：
- transcript 长时间不增长
- 共享区没有新痕迹
- 没有新的 deliverable、反馈文件或收口信号
- 也看不到 `Codex` 继续工作

## 2. 默认等待窗口

### 0-15 分钟
默认按正常长执行处理。
不要因为暂时没聊天回复，就判断挂住。

### 15-30 分钟
做一次轻检查：
- transcript 是否增长
- deliverable 是否新增
- 是否已有阶段性成果

### 30 分钟后
再区分：
- 有产物但没收口 → 视为“收口卡住”
- 完全无新痕迹 → 再怀疑异常

## 3. 不只看回复，要看工作痕迹

优先观察这些：
- `agents/executor/sessions/*.jsonl` 是否继续增长
- `work-system/deliverables/` 是否出现新文件
- 项目档案 / feedback 文件是否新增内容
- 是否出现 `更新专项进度`、`记录阶段性成果` 等收口信号

## 4. 长任务默认要求阶段性成果

如果一开始就判断任务会比较大，handoff 里应明确要求：
- 超过一段时间先给阶段性成果
- 不要无限深挖后才第一次回写
- 先保住中间结果，再决定是否继续下一轮

## 5. 大任务建议拆成两段或三段

不要默认一轮做完“路径定位 + 原因分析 + 方案设计 + 项目回写”。
更稳的方式：
- 第一段：摸清代码路径和问题结构
- 第二段：形成优化方案 / 改造建议
- 第三段：必要时再进入实施准备或验证

## 6. 何时介入

### 继续等
- transcript 在增长
- deliverable 在形成
- 只是暂时没聊天回复

### 提醒收口
- 已有成果文件
- 但迟迟没有结构化结果或共享区回写
- 明显进入“收口慢”状态

### 重新起新轮次
- 当前执行轮次既无稳定回复，也无可靠收口
- 会话本身已失控
- 共享区只有半成品，需要新轮次接管收口

## 7. 当前阶段的默认原则

- 先判断是不是正常长执行
- 再判断是不是收口卡住
- 最后才判断是不是真的挂了

一句话：
> 长执行任务优先看共享区痕迹，不只看有没有及时回消息。
