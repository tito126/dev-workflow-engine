# 执行型 Agent 机制说明

这不是业务专项，而是一项协作能力 / 执行机制。

它服务于住院护士站相关及后续其他业务专项中的执行类工作，目标不是多会话本身，而是为代码维护、优化、隔离改造、验证闭环提供一条更专注的执行通道，并持续反哺“降本增效”。

## 机制定位

### 主会话负责
- 目标澄清
- 专项判断
- work-control 路由
- 风险识别
- 复盘与方法论沉淀

### 执行型 Agent 负责
- 代码阅读与局部理解
- 问题到代码位置的映射
- 通过代码分析形成优化方案、隔离方案、修复建议与实施判断
- 小到中等规模修改
- 技术优化与验证闭环
- 执行结果整理与回写
- 通过 OpenClaw + ACP + Claude Code 承接代码现场工作

## 适用范围

优先服务这类事项：
- 住院护士站系统前后端代码维护
- 局部优化与治理
- 隔离改造
- 技术验证
- 与具体业务专项强相关的执行类任务

不直接替代：
- 业务目标判断
- 优先级取舍
- 跨团队协同拍板
- 是否立项、是否值得做的最终判断

## 当前共识

1. 执行型 Agent 应共享当前 workspace
   - 共享 `work-system/`
   - 共享 `memory/`
   - 共享 `MEMORY.md`
   - 共享技能与材料

2. 执行型 Agent 不作为业务专项管理
   - 它是能力层
   - 业务专项是对象层
   - 由该机制服务具体业务专项，而不是反过来把该机制本身项目化

3. 当前优先走“路径 1”
   - 在同一个 OpenClaw / Gateway 下，尝试为执行型 Agent 提供另一个独立 web 入口
   - 目标效果：主入口连主 Agent，第二入口连执行型 Agent

## 启用条件（当前版）

以下情况优先考虑启用执行型 Agent：
- 已经明确目标、边界和大致验收方向
- 任务进入代码维护、优化、脚本、改造、验证阶段
- 需要通过代码分析形成方案、隔离建议、改造判断或实施路径
- 需要 ACP + Claude Code 提高执行效率

以下情况优先留在主会话：
- 纯目标澄清
- 纯专项判断
- 纯复盘
- 业务价值和优先级尚未收口

## 反哺原则

执行型 Agent 的价值不只在“做了代码”，还在于把结果和经验持续反哺到现有系统。

### 回写层次
- 专项运行状态：回写到对应 `work-system/projects/active/<专项>.md`
- 当天推进痕迹：进入 `memory/YYYY-MM-DD.md`
- 长期稳定经验 / 判断规则：必要时进入 `MEMORY.md` 或 `cognition-system/`

### 最小反哺结构
可使用：`work-system/templates/execution-feedback-template.md`

核心要回答：
- 这次做了什么
- 为什么有效 / 为什么没那么有效
- 风险和不足是什么
- 以后有哪些规则可迁移
- 对“降本增效”具体影响了什么
