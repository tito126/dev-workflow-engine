# 日志拉取链路稳定性教训

这份记录不描述某一次具体操作细节，而是提炼这次桐乡日志拉取卡壳背后的上层规律。

目标不是回答“当时怎么修好”，而是回答：
- 为什么一个跑通过很多次的流程，现场仍然会反复卡壳
- 这些失真会如何在其他专项中重复出现
- 后续应优先建立什么样的协作与判断机制，才能减少类似损耗

## 一、跑通过很多次，不等于机制已经稳定

这次最值得警惕的，不是某个端口不通，而是一个更普遍的问题：
- 流程历史上成功过
- 团队主观上也以为“这条链路是熟的”
- 但一旦进入答辩前预演、飞书演示这类压力场景，流程仍会退化为靠印象拼步骤

这说明：
- **成功过** 只能证明能力存在过
- **稳定复现** 才能证明机制已经形成

对后续专项的警示是：
- 任何“做过很多次”的流程，都不能自动视为稳定资产
- 如果标准入口、判定顺序、异常分支没有被显式固化，它就仍然是脆弱能力，而不是可靠机制

## 二、经验必须沉淀为判定顺序，而不只是步骤记忆

这次并不是完全不知道要用 `wxp-tunnel`，而是判断顺序没有真正固定：
- 先被旧配置中的本地回环端口带偏
- 又把映射记录误当成当前可用入口
- 直到后来才收敛到“代理地址可达性优先”的正确路径

这说明：
- 只记住“会经过哪些步骤”，并不能保证临场稳定
- 真正可迁移的经验，必须表现为：
  - 遇到某类任务时先判断什么
  - 哪些信号一出现就应切换分支
  - 什么条件满足后才能继续执行下一阶段

如果一个流程的经验还停留在“我记得之前这么弄过”，那它本质上仍然依赖情境记忆，而不是机制化理解。

## 三、配置入口、可达入口、标准入口，必须明确区分

这次最有代表性的失真，是把不同层次的“入口”混在了一起。

应明确区分三类入口：
- **配置入口**：配置文件里写着的候选地址
- **可达入口**：当前环境中实测可访问的地址
- **标准入口**：在现场执行中应默认采用的、已经验证可达的入口

这次卡壳说明：
- 配置存在，不代表当前可用
- 历史上跑通过，不代表今天仍然是标准路径
- 只有通过验证的真实入口，才配成为执行链路中的标准入口

这条判断不只适用于日志拉取，也适用于后续所有涉及：
- 代理
- 网关
- 隧道
- 集群接入
- 第三方环境访问

## 四、对固定技术链路，用户应表达目标，系统应补全中间操作

这次还暴露了一个协作层问题：
- 用户说“拉取桐乡最近10分钟日志”时，按理只是在表达目标
- 如果还需要用户反复补充“要先开代理地址、再测 Grafana、再跑完整流程”，说明中间链路还没有真正被系统吸收

后续更合理的协作分工应是：
- 用户表达目标
- 系统负责补全固定链路中的默认动作、验证步骤和收口产物

这背后的上层原则是：
- 重复性高、路径固定的技术任务，不应持续占用用户的过程控制精力
- 用户不该一边提需求，一边承担流程编排与纠偏责任

如果这件事做不到，说明系统还停留在“辅助执行”而不是“稳定接管固定链路”的阶段。

## 五、复盘不能只记报错，要记为什么会走错分支

如果复盘只停在：
- 某端口不通
- 拉取速度慢
- 演示前才跑通

那价值是有限的。

这次真正应该保留的是：
- 为什么一开始会优先盯住本地回环入口
- 为什么没有第一时间切到代理地址验证
- 为什么过去跑通过的经验，没有转化成明确的标准入口规则

这类问题的价值在于：
- 它解释的是**判断为什么失真**
- 而不是只描述**结果为什么失败**

对后续专项的警示作用也更强，因为它能反过来指导：
- 哪些流程该被优先制度化
- 哪些经验不能只停留在“我知道”
- 哪些任务必须在压力场景前做真实预演

## 六、可迁移的协作结论

这次日志拉取链路的教训，后续可以迁移为几条更通用的协作原则：

1. 流程稳定性的判断，不能靠成功次数，要靠是否形成标准入口和异常分支。
2. 经验沉淀优先写成判定顺序，而不是零散步骤。
3. 现场执行默认走“已验证可达”的标准入口，不迷信旧配置和历史印象。
4. 对固定技术链路，用户负责表达目标，系统负责补全中间动作。
5. 复盘应优先追问“为什么会走错判断分支”，而不只是记录错误现象。

这份记录的意义，不在于解决一次日志拉取，而在于提醒后续所有专项：
- **真正危险的，不是没做过，而是以为已经稳定了。**
