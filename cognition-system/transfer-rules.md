# 迁移机制

用于把一个项目中的经验、错误、检查点、方法，迁移到下一个项目中。

## 迁移对象

重点迁移这些内容：
- 立项时遗漏过的关键问题
- 过程里暴露出的偏差和纠偏方式
- 已验证有效的表达方式和推进节奏
- 能复用的模板、清单、检查点
- 对第别判断方式的新认识

## 当前通用规则

### 1. 从项目中抽两类结论
- 项目内结论：这个项目下次怎么做得更好
- 跨项目结论：以后类似项目都该提前注意什么

### 2. 不只迁移结果，也迁移判断过程
不仅要记录“最后改成了什么”，还要记录“为什么原方案不对，后来为什么这样更对”。

### 3. 迁移要落到具体载体
- 项目相关 -> `work-system/projects/active/*.md`
- 日常节奏相关 -> `work-system/daily/`
- 长期协作相关 -> `cognition-system/*.md`
- 长期稳定摘要 -> `USER.md` / `MEMORY.md`

### 4. 对复发问题建立检查点
如果某类偏差反复出现，就不要只写在复盘里，而要转成前置检查问题。

## 新增迁移方向（来自 2026-03-22 讨论）

- 以后在讨论上层机制时，优先把抽象结论压缩成“现象 -> 本质 -> 规则 -> 作用点 -> 收益”的规则卡结构。
- 当一个项目中已经识别出反复出现的协作偏差，应优先沉淀为跨项目检查点，而不是只停留在该项目复盘中。
- 对 `cognition-system` 的分享口径，应以“正在长出来的下一阶段能力”来表达，而非包装成已经成熟的能力。

## 已沉淀的首批检查点

基于“日志猎人”已确认：
- 比赛型/汇报型项目在立项时就要先定价值主线
- 证据资产需要边做边积累，不能到收口时再集中补
- 技术表达要始终服务于价值表达
- 当材料很多但讲不顺时，优先检查主线而不是继续堆内容
- 页面、讲稿、Q&A 最好同步推进，而不是线性补课
- 版本对比应重点提炼“结构职责变化”和“价值表达升级”，而不只看文案增删
