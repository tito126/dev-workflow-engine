## 对 `superpowers` 的分析与判断

今晚已基于 `https://github.com/obra/superpowers` 做了一轮分析。

### 关键结论

1. `superpowers` 本质上不是单个 skill，而是：
   - 一套面向 coding agent 的 skill 包
   - 一套软件开发工作流方法论
   - 一种对 Agent 进行流程约束的工程化体系

2. 它的价值不在于“替代 coding agent”，而在于：
   - 约束 agent 不要一上来就写代码
   - 强化 brainstorming、task plan、TDD、review、verification
   - 提供较成熟的技能组织与执行流程

3. 对当前护士站场景来说，`superpowers` 更适合作为：
   - 开发流程设计参考
   - skill 组织样板
   - 多 Agent 执行约束参考

4. 不适合直接把它当成护士站专项开发框架的最终主系统。

## 关于执行机制的关键澄清

今晚还进一步澄清了一个关键问题：

### 当前 `exec + OpenCode` 和 `subagent-driven-development` 的关系

已明确：

- `exec` 是**启动方式**
- `OpenCode / Codex` 是**代码执行引擎**
- `subagent-driven-development` 是**任务编排方法**

也就是说：

当前已经有“执行器”，但还没有真正成熟的“自动编排器”；
现在更像是**手工编排的多 Agent / 多步执行链路**。

### 当前更现实的执行驱动链

已进一步收束为：

`OpenClaw 主控 -> 需求澄清 / 任务计划 -> exec -> OpenCode / Codex -> 结果回收 -> review / 验证 -> 沉淀`

这条链路很重要，因为它明确了：

- skill 不直接执行代码
- `OpenClaw` 不直接替代 coding agent
- 真正的代码执行发生在“执行层”
- 多 Agent 是组织执行的手段，不是框架目标本身

## 今晚的关键判断收束

### 1. 不是为了“上多 Agent”而上多 Agent

多 Agent 在这套体系中应被定义为：

- 执行手段
- 任务分工方式
- 质量控制手段

而不是框架最终目标。

### 2. 不是为了“装成熟框架”而装成熟框架

`superpowers / GSD / Gstack` 的价值主要在于：

- 提供参考方法论
- 提供 skill 设计样板
- 提供多 Agent 编排思路

真正的底座仍应是当前 `OpenClaw` 路线。

### 3. 成功标准仍然要回到结果导向

后续不能只看：

- agent 会不会写代码
- 多 Agent 是否能跑通
- skill 看起来是否完整

而要重点看：

- 是否降低运维成本
- 是否提升开发效率
- 是否规范开发流程
- 是否让成果可复用
- 是否真正促进护士站系统稳定性提升

这和此前关于“半年后机制是否成功”的判断保持一致：
成功的关键不在于系统有多完整，而在于是否真的持续服务降本增效。Source: memory/2026-03-23.md#L43-L63
