**分析过程**：

   - 由于日志量极大（每秒2000+条），只获取到最后3秒的5000条日志
   - 发现问题：无法获取完整时间段的数据

2. **改进方案**：
   - 使用分批查询（每30分钟一批）
   - 添加过滤条件（只拉取 ERROR|WARN 级别）
   - 成功获取 20000 条日志，覆盖约1.5小时

**分析结果**（8:00-10:00，ERROR+WARN）：

- **总日志数**：20000 条（ERROR: 196, WARN: 19784）
- **错误率**：0.98%
- **错误分类**：
  - NumberFormatException: 41 条（数字格式错误）
  - 404 Not Found: 30 条（标签算法服务）
  - 语法错误: 17 条（返回 HTML 而非 JSON）
  - NullPointerException: 10 条
  - 其他错误: 97 条
- **慢接口**：35 个（>=1秒），最慢 2410ms

**关于 YGC 频率高的分析**：

1. **日志量极大**：
   - 每秒产生 2000+ 条日志
   - 大量日志输出会产生大量临时对象（String、StringBuilder 等）
   - 这是导致 YGC 频繁的主要原因之一

2. **警告日志占比高**：
   - 98.9% 的日志是 WARN 级别
   - 主要是接口耗时警告（框架性能损耗统计）

3. **慢接口较多**：
   - 35 个慢接口可能导致线程阻塞
   - 间接影响内存使用和 GC 频率

**建议**：

1. **调整日志级别**：
   - 生产环境考虑将 INFO 改为 WARN
   - 减少不必要的日志输出（如框架性能损耗统计）

2. **优化慢接口**：
   - 排查耗时超过1秒的接口
   - 优化数据库查询和业务逻辑

3. **监控 GC**：
   - 在 Grafana 查看 JVM 监控面板
   - 确认 YGC 频率和内存使用情况

4. **JVM 调优**：
   - 如果日志量无法减少，考虑增大年轻代（-Xmn）
   - 使用异步日志 Appender

### 技术发现

**Loki 查询限制**：
- 乐山和桐乡的 Loki 都有 5000 条/次的限制
- 对于日志量大的服务，需要：
  1. 分批查询（按时间段）
  2. 使用过滤条件（只拉取 ERROR|WARN）
  3. 才能获取较完整的数据

**分批查询方法**：
```python
# 每30分钟一批，只拉取 ERROR|WARN
query = '{app="xxx"} |~ "ERROR|WARN"'
# 分4批查询2小时数据
# 每批最多5000条，总计可获取20000条
```

### 运维平台下载 URL 分析

运维平台的下载接口格式：
```
http://127.0.0.1:13440/cluster/action/copfile/down?
  filepath=<十六进制编码的文件路径>&
  filename=<文件名>&
  hostid=<服务器标识>&
  fsize=<文件大小>&
  uid=<会话token>
```

**问题**：
- 需要浏览器 session 认证
- uid 参数可能是临时会话 token
- 无法通过简单的 HTTP 请求自动化

**解决方案**：
- 等待工具组提供专用的下载 API
- 或者研究运维平台的登录 API（如果有的话）
