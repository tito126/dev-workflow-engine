### 当前判断
- 这类节点 down 更像是“慢外部依赖拖住请求线程 / 连接池”的级联问题，而不是本地 CPU 逻辑瓶颈。
- 第二段“病案费用汇总”和第三段“中医补充明细”天然适合改成增强型依赖，优先做异步 fail-open。
- 如果中江当前走 HTTP 分支，风险会比 60 / FHIR 明显更高，因为远程依赖和附加查询更多。

### 当前最值得做的小改动
1. 把第二段、第三段改为异步并行 + fail-open
2. 给 `(hospitalSOID, transCode)` 的集成方式查询加 5~10 分钟本地缓存
3. 在 Banner 专用链路跳过 HTTP 分支里当前接口不消费的药占比等附加查询
4. 对欠费额度 `null` 返回做空值兜底，避免非核心配置服务拖挂核心余额查询

### 待确认项
- 中江当前实际走的是 60 / HTTP / FHIR 哪条分支
- 真实慢请求里 3 段调用的耗时占比
- 业务上哪些增强字段允许明确降级为空

### 方法层面的新收获
- 这类事故驱动分析很适合走 `main / executor / Codex` 最小协作链路：主会话做目标收口，executor 做任务承接和结果回收，Codex 负责多文件深度调用链分析。
- 对高频刷新接口，优先检查“同步串行 + 过度取数 + 配置查询无缓存”这三类问题，往往比一开始讨论框架级熔断更快逼近根因。
