## 可提炼到 cognition 的候选资产（日志拉取链路复盘）

### 1. 跑通过很多次，不等于机制已经稳定

这次桐乡日志拉取在答辩前预演中反复卡壳，暴露出一个重要问题：
- **流程曾经成功过**，并不代表它已经被沉淀为可稳定复现、可现场演示、可迁移复用的机制。
- 如果成功条件、入口判定、异常分支没有被显式固化，流程仍然会在压力场景下退化为“靠印象拼接步骤”。

可迁移判断：
- 后续凡是“看起来做过很多次”的流程型能力，都不能直接默认稳定；
- 需要额外检查：标准入口是否明确、异常分支是否明确、默认动作是否明确。

### 2. 经验必须沉淀为“判定顺序”，不能只沉淀为“步骤记忆”

今天不是完全不知道要用 `wxp-tunnel`，而是没有在第一时间按正确顺序判断：
- 先被旧配置中的 `127.0.0.1:16291` 带偏
- 又把 `links` 里的映射记录误当成“当前可直接访问的活入口”
- 直到后来才收敛到：**应优先验证代理地址，再进入 Grafana 与 Loki 拉取**

说明：
- 仅记住“要做哪些步骤”是不够的；
- 真正稳定的经验，必须表现为：遇到某类任务时，先判断什么，再判断什么，失败时切到哪条分支。

### 3. 配置入口、可达入口、标准入口，必须明确区分

这次最关键的认知收获之一是：
- **配置里写着的入口，不等于当前真实可用的入口**；
- **真实可达的入口，才是现场执行时应采用的标准入口**。

这次对比中：
- 桐乡旧配置偏向本地回环模式：`127.0.0.1:16291`
- 红房子跑通的经验则更接近远端代理模式：`172.16.7.39:8012`

可迁移判断：
- 以后凡是涉及环境接入、代理、网关、端口映射的链路，都要先区分这三类入口；
- 不应把“配置存在”误判为“入口可用”，更不能把“历史上跑通过”误判为“现在仍然是标准路径”。

### 4. 对固定技术链路，用户应表达目标，系统应补全中间操作

今天还明确了一条重要协作原则：
- 用户只需要说：`拉取桐乡最近10分钟日志`
- 系统应自行补全：
  - 桐乡多集群必须先问集群
  - 通过 `wxp-tunnel` 打开对应 Grafana 代理端口
  - 验证代理地址可达
  - 进入完整拉取、分析、补链路、出报告流程

可迁移判断：
- 对重复性强、链路固定的技术任务，应持续把中间操作吸收到系统默认行为中；
- 用户输入应尽量压缩为“目标表达”，而不是要求用户复述一整套技术步骤。

### 5. 复盘不能只记“报错”，要记“为什么会走错那条分支”

今天如果只记录“16291 不通”“拉取速度慢”，价值有限。
更值得保留的是：
- 为什么一开始会盯住本地回环端口
- 为什么没有第一时间切到代理地址验证
- 为什么过去跑通过的经验没有形成标准入口规则

可迁移判断：
- 后续复盘时，除了记录故障现象和修复动作，还应额外记录：
  - 当时采用了什么判断路径
  - 这条路径为什么错了
  - 下次出现类似信号时，应怎样更早切到正确分支
