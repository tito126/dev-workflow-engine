### 异常实时告警方案

**问题**：几百家医院，如何实现实时告警？

**推荐方案**：Loki/Grafana 告警 + Webhook

```
生产环境 (几百家)
    ↓
Loki 实时分析日志
    ↓
Grafana 告警规则触发
    ↓
Webhook → OpenClaw Gateway
    ↓
飞书机器人推送告警
    ↓
(可选) 自动触发日志分析
```

**优势**：
- ✅ 真正的实时（秒级延迟）
- ✅ 可扩展到几百家医院
- ✅ 低资源消耗（告警由 Loki/Grafana 处理）
- ✅ 灵活配置（不同医院不同规则）

**实施步骤**：
1. 在 Grafana 配置告警规则（ERROR 频率、特定异常等）
2. 配置 Webhook 通知到 OpenClaw
3. 创建 `alert_handler.py` 处理 Webhook
4. 推送到飞书 + 自动触发日志分析

**混合方案**：
- K8s 环境：Loki 告警（实时）
- 传统服务器：定期轮询高优先级医院（5-10分钟）
- 按需分析：用户主动触发（统一入口脚本）

## 技术笔记

### 统一入口脚本设计模式

**问题**：多步骤工作流程，如何简化用户操作？

**解决方案**：
1. 封装完整流程到单个脚本
2. 支持自然语言参数解析
3. 自动查找配置信息
4. 提供进度反馈
5. 支持多种调用方式（自然语言 / 命令行参数）

**代码结构**：
```python
class LogInspector:
    def parse_natural_language(text) -> params
    def fetch_logs(params) -> log_file
    def analyze_logs(log_file) -> digest_file
    def generate_report(digest_file) -> report_file
    def push_to_feishu(report_file)
    def run(query) -> result
```

### 实时告警架构选择

**错误方案**：轮询所有现场的日志
- ❌ 资源消耗大（几百家医院）
- ❌ 延迟高（5-10分钟）
- ❌ 无法扩展

**正确方案**：利用现有基础设施
- ✅ Loki/Grafana 已经在实时分析日志
- ✅ 配置告警规则，触发 Webhook
- ✅ OpenClaw 只接收通知，不主动轮询
- ✅ 可扩展到任意数量的医院

**关键洞察**：
- 不要重复造轮子
- 利用现有的监控基础设施
- 事件驱动 > 轮询
- 推送 > 拉取
